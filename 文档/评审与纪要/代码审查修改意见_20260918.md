## 一、结论与本轮范围

保留当前 Vue + Python HTTP + SQLAlchemy Core 存储架构。本轮优先恢复功能、纠正错误处理、补齐关键路径验证，不进行全面架构重构。

建议顺序：

1. 修复导出和恢复快照两个已确认故障。
2. 修正 GET/POST 的异常分类与错误响应。
3. 解除独立接口对本体工作区的依赖。
4. 明确项目列表筛选语义，并处理旧调用兼容。
5. 增加相关回归与轻量的一键测试入口。

报告中的 P0/P1/P2 应重新分级：已确认功能不可用列为优先修复；可维护性、REST 风格与目录拆分不列为紧急缺陷。当前未发现足以据此宣称全站不可用或数据损坏的证据。

## 二、必须修复的功能问题

### R1：导出接口直接返回 404（原报告遗漏其实际影响）

**位置**：`workbench/server.py` 的 `POST_ROUTES` 与 `Handler.do_POST`。

**已确认事实**：`/api/export` 的路由值为 `None`。`do_POST` 先执行 `handler = POST_ROUTES.get(path)`，随后按 `handler is None` 返回 404，所以后面的 ZIP 导出分支不可达。隔离调用已复现 `(404, {error: '接口不存在'})`。

**修改要求**：

- 使已注册的导出端点通过路由检查，再经过与其他 POST 相同的 Origin、Content-Type、请求大小和 JSON 解析检查。
- 最小修复可区分“路由键不存在”和“专用二进制处理”；也可注册具名导出处理器。不要为此全面重写响应框架。
- 保留现有下载 URL、ZIP 格式、文件名和前端调用方式。

**验收**：真实隔离 HTTP 请求能下载并打开 ZIP；必要模型内容完整；非法 Origin 仍返回 403；超大请求仍返回 413；不存在的端点仍为 404；导出不修改草稿、发布版本或项目引用。

### R2：恢复快照调用不存在的函数

**位置**：`workbench/model_routes.py::post_restore`。

**已确认事实**：备份阶段调用 `_server_current(identifier)`，该函数不存在。隔离调用已复现 NameError。

**修改要求**：

- 改用现有正确的当前本体读取入口 `current(identifier)`。
- 保留恢复前备份、原本体归属校验、项目状态隔离与 revision 校验。
- 恢复是写入一个新草稿，不得覆盖不可变发布版本。
- 同时核对从校验到写入的 revision 使用：CAS 必须基于已校验的客户端基线，不能在提交前重新读取较新的 token 后直接覆盖他人写入。
- 响应应携带本次提交得到的 revision，不应用随后再次查询到的、可能属于其他提交的 token 代替。
- 当前备份与草稿提交分属两个事务。需明确失败语义：允许留下未使用的恢复前备份，但不能错误返回恢复成功；若合并事务，须验证失败全部回滚。

**验收**：恢复后内容与目标快照一致，产生新 revision；恢复前内容可由备份找回；旧 revision 返回 409 且不改草稿；其他本体的快照被拒绝；损坏 ZIP、缺失必要文件可读地报错；失败不产生半恢复状态；项目草稿和已发布数据保持不变。

## 三、接口边界修正

### R3：异常分类与最小可观测性

**事实**：POST 兜底把未知异常变成 400 并返回 `str(exc)`；GET 也把部分内部异常归为 400，且没有完整的未知异常 JSON 兜底。

**修改要求**：

- 输入不合法返回 400；不存在返回 404；revision 冲突返回 409 并保留 `currentRevision`；发布等业务阻断按现有契约返回 422；数据库暂不可用保留 503；未知程序错误返回 500。
- 不得把所有 `ValueError/KeyError/TypeError/OSError` 都当作用户输入错误。输入错误在解析/校验边界明确识别，内部编程和 I/O 错误另行处理。
- 兼容保留 `error` 文本，增量添加稳定的 `code`，先覆盖通用错误和本轮涉及的路径，不要求一次改完全部业务接口。
- 未知错误客户端返回可理解的通用消息，服务端保留排障信息；日志不得记录密钥、完整请求体或带凭据的数据库 URL。SQLAlchemy 异常可能携带参数，不能未经处理直接输出完整异常内容。
- 可增加服务端生成的 requestId，用于响应与日志关联；已有默认 HTTP 访问日志保留，不宣称当前完全没有访问日志。
- 不改变保存协调器的冲突策略：409 进入冲突状态，由用户决定后续操作，不自动覆盖服务端新内容。

**验收**：分别注入输入错误、业务阻断、数据库不可用和内部异常，检查状态码及响应；409 仍含最新 revision；500 不泄露内部路径、SQL 参数或凭据；失败请求不显示保存成功。

### R4：无关接口不应依赖本体工作区

**位置**：`workbench/server.py::Handler.do_GET`。

**修改要求**：

- 取消所有 API GET 共用的 `workspaces.describe(...)` 前置检查。
- 本体接口在自己的边界验证本体；项目接口根据项目及其固定引用验证；编排列表、模型设置与存储状态等独立接口不要求当前本体有效。
- 先判断路由是否存在，使未知端点稳定返回“接口不存在”。

**验收**：独立接口在无选中本体、附带无关或无效 ontology 参数时仍按自身契约工作；本体专属接口传不存在的本体仍报错；项目不存在、引用版本缺失仍按原约定处理。

### R5：项目列表筛选语义显式化

**位置**：`project_routes.get_projects(query, url_query_present)`。

**事实**：当前只要 URL 有任意 query，就按 ontology 参数过滤；无关查询参数也可能改变结果。该问题成立，但不属于紧急 P0。

**建议契约**：

| 请求 | 预期 |
| --- | --- |
| `/api/projects` | 全部项目 |
| `/api/projects?ontology=<有效ID>` | 指定本体的项目 |
| 附带其他合法参数 | 不因“存在 query”而隐式改变本体范围 |
| `/api/projects?ontology=` | 明确返回参数错误；前端无筛选时省略该参数 |

实施前检查现有调用及接口文档；如已有调用依赖空字符串行为，先兼容或同步修正调用方。无需仅为此新增 `all=1`。

**验收**：覆盖全部、指定本体、空值、无关参数四类请求，确认列表与筛选语义一致。

## 四、报告本身应修订的结论

| 原报告表述或建议 | 修改意见 |
| --- | --- |
| 导出 `None` 占位只是路由可读性问题 | 提升为已确认功能故障：导出必定在前置检查返回 404 |
| 无访问日志 | 改为“有继承的默认访问日志，缺结构化字段和完善异常关联” |
| 409 据 currentRevision 换基线重试 | 当前协调器会进入冲突状态；显式操作才重提，应以当前代码为准 |
| 异常返回 400 会导致保存协调器错误重试 | 当前协调器主要区分 409 与其他错误；不能把潜在语义问题直接写成已证实的重试故障 |
| 缺少 HTTP 契约测试导致恢复故障长期潜伏 | 已有 HTTP 集成测试；缺少关键端点覆盖成立，但长期潜伏及因果需版本历史证据 |
| 项目列表 query 语义列 P0 | 降为普通接口正确性修复 |
| 存储一致性五星 | 改为“设计方向合理，需结合迁移、并发、回滚、备份恢复测试结果判断”；MySQL 运行时仍未验证 |
| 保存延迟明显、列表全量校验慢 | 作为待测性能假设，附数据规模、耗时和调用证据后再决定优化 |
| Python 无类型注解 | 改为“类型约束覆盖不足”，按模块核实，不使用未经完整检查的全称结论 |

## 五、本轮暂不实施的建议

1. **全面 REST 改造**：暂不改现有路径、HTTP 动词、版本前缀或并发令牌位置。正确性和兼容性优先。
2. **强制统一全部响应外壳**：裸数组可以保留既有契约；没有调用故障时，不单为统一 `{items}` 改动前后端。
3. **单文件超过 500 行必须拆分**：不采用硬限制。依据职责、重复逻辑和实际修改冲突拆分，避免小修复扩大成架构任务。
4. **所有端点一次性补全快照测试**：先覆盖导出、恢复、错误分类及筛选；核心写链路逐步扩展。测试应断言业务行为，而不只是字段存在。
5. **直接接入 pytest 并行跑所有旧脚本**：现有脚本有顶层执行、环境变量设置和固定端口，需要先隔离；文件名符合 `test_*.py` 不代表可直接安全收集。
6. **无页面调用方即删除接口**：诊断、管理、导出和集成接口可以没有页面调用方；删除前检查实际调用和兼容要求。
7. **每次小改动都全量重构、全量回归**：按风险选择相关检查，整体验收时完整回归；前端有改动仍按仓库约定执行构建。
8. **新增整套日志/监控平台**：本轮结构化错误与请求关联足够，health/ready 按部署需求另行加入。
