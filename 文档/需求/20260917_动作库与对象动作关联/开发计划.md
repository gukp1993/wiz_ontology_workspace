## 1.5 最终数据协议（阶段 1 冻结）

workflow 与 bindings 均为既有状态的透传字段（`encode_state`/`decode_state` 只转换 ontology，
`_files_from_state` 原样落 bindings.yaml），因此本轮**不改 JSON schema/JSON-LD 转换层**，
`definitionOrder`、`modelFormat.ts` 均不涉及。

### 1.5.1 动作定义（本体 workflow.actions，每条记录）

新格式（本期，`definitionVersion: 2`）：

```json
{ "id": "<系统生成 uuid>", "name": "停止充放电", "description": "请求目标对象停止当前充电或放电",
  "effect": "请求停止充放电，目标功率为 0，以设备反馈确认完成", "definitionVersion": 2, "status": "experimental" }
```

- 必填业务字段仅 `name/description/effect`；`status` 沿用现有枚举（experimental/active/deprecated），默认 experimental。
- 不写 `object_type/inputs/criteria/permission/acceptance/relation_ref`；旧编辑表单不再出现。
- 历史动作（无 `definitionVersion` 或 ≠2）：**原样读写、零丢失**，仍按旧校验（适用对象、effect/criteria/permission/acceptance 必填等）；只读展示，不做自动迁移。旧转新必须显式编辑保存（此时旧字段被新结构替代，变更分类按"待确认"处理）。

### 1.5.2 对象动作关联（本体 workflow.actionAssociations，单一集合）

```json
[ { "objectTypeId": "mg:StorageDevice", "actionId": "4f2a…" },
  { "objectTypeId": "mg:StorageCluster", "actionId": "4f2a…" } ]
```

- 只存显式新式关联；`objectTypeId` 存对象类型 `@id` 原样（含 `mg:` 前缀，与契约 `applicable_objects` 一致），`actionId` 为动作稳定 id。组合（objectTypeId, actionId）唯一。
- 同一动作关联多个对象 = 多行，引用同一份定义，不复制。
- 历史动作的对象关联不落此集合，由其 `object_type` 在内存推导（`effectiveAssociations = 显式集合 ∪ 历史动作 object_type`），供反向引用与项目绑定读取，不回写。
- 发布快照随 workflow.json 原样携带；项目只在显式升级引用后看到新增/修改/移除。

### 1.5.3 项目动作绑定（项目 bindings.actionBindings，每条记录）

```yaml
actionBindings:
  - id: "9c81…"                # 行标识，系统生成
    objectTypeId: "StorageDevice"   # 与 object_bindings.object_type 同规范（bare，不含 mg:）
    actionId: "4f2a…"
    implementation:
      kind: api                # api=调用项目接口 | flow=绑定函数编排
      path: "/api/devices/{id}/stop"  # api 模式必填；仅配置说明，不承诺执行链路
      flowId: "664381dde0b3"   # flow 模式必填；引用既有编排，校验存在且未删除
      roles: "设备运维人员"      # 允许操作的项目角色说明（选填，不宣称已实施访问控制）
      paramNotes: "storageId ← 当前操作设备的项目标识"   # 参数来源说明（选填，无参数可留空）
```

- 绑定存储在项目 bindings 内，天然按项目隔离；组合键 = 项目（存储位置）＋objectTypeId＋actionId，**组合唯一**，不同对象引用同一动作互不覆盖。
- 有效动作与关联来源 = 项目固定引用的**已发布本体版本**（refState）中的 effectiveAssociations；绝不读取本体最新草稿。
- 未知 kind/未知字段原样保留，校验报格式错误但不删除（零丢失）。
- 保存仅写项目草稿；配置完成只显示「已配置 · 未执行验证」，不提供执行。

### 1.5.4 校验与变更分类

- 本体（`workflow.definition_errors`）：v2 动作只校验三字段+状态；新增校验 actionAssociations——objectTypeId 必须是存在的对象类型、actionId 必须存在于 actions（= 删除仍被关联的动作会被拒绝）、组合不重复。历史动作校验路径原样不动。
- 项目（`project_validation._check_action_bindings`）：actionBindings 非法结构/组合重复/对象或动作不在引用版本/组合不在有效关联（**关联失效**）/implementation 缺失或 path、flowId 未填/编排不存在 → error（阻止发布）；未绑定动作不产生任何输出（不阻止发布）；roles/paramNotes 不校验。校验只读，**永不自动删除失效绑定**。
- 变更分类（`contracts.classify`）细化为按记录比较：删除动作 → 破坏性；删除关联 → 破坏性；新增动作/关联 → 兼容；动作内容变化（含业务效果文本）→ 待确认。接口/指标/规则维持现状。

### 1.5.5 新旧读写样例

旧数据读入（不重写）：

```json
workflow.actions: [ { "id": "action.change_system", "name": "调整所属系统", "object_type": "StorageDevice",
  "inputs": [...], "effect": "…", "criteria": "…", "permission": "…", "acceptance": "…", "status": "active" } ]
workflow.actionAssociations: 不存在 → 视为 []
```

新数据保存：

```json
workflow.actions: [ { "id": "8f0c…", "name": "停止充放电", "description": "…", "effect": "…",
  "definitionVersion": 2, "status": "experimental" } ]
workflow.actionAssociations: [ { "objectTypeId": "mg:StorageDevice", "actionId": "8f0c…" } ]
```

项目绑定失效场景：引用版本升级后 `{objectTypeId, actionId}` 不在引用版本 effectiveAssociations → 保留该行、校验报 error、页面标「关联失效 · 历史配置保留」并可查看只读详情后确认移除。

## 3. 技术边界

- 本体保存走现有本体 API，项目保存走项目 API。表单使用当前 `formGuard/formSave` 或实际正在使用的保存协调机制，不能另写 fetch 和第二条草稿存储链。
- 新字段若落在 JSON schema/JSON-LD 转换层，必须同步修改前后端协议、保留未知字段、维护 definitionOrder；workflow 纯字段也要验证保存、读取、发布快照均不会丢失。
- 检查现有 `workflow.actions` 校验及校验问题定位，简化格式不再要求历史的 criteria/permission/acceptance。旧记录仍按旧版本处理。
- 关联查询使用稳定 ID，不以中文名称或数组位置作为键。接口绑定身份应为项目ID、对象类型ID、动作ID三元组合。
- 复用项目现有函数编排列表与引用权限范围，不新增另一套编排库；本期只绑定，不执行。
- 项目角色文本只是配置说明。保存配置不得声称服务端权限已经实施。
- 本体草稿变化不能直接更新项目引用版本。失效配置不得自动删除。
- 所有真实 `ontology/` 数据只经正式 API 写入；自动化测试使用临时根目录和独立端口。
