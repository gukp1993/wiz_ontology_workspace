## 1. 本轮实测与真实数据发现（P1）

### P1-1 生成进度感知弱：「已等待 X 秒」永远不显示

- **现象**：抽取阶段长时间只显示「抽象本体定义 · 处理中」与「等待第 N 批返回（还有 X 批未完成）」，等待时长永不出现，超过 60 秒的安心提示也不出现。
- **根因**：后端心跳**从不写 `waitedSeconds`**。
  - 前端渲染逻辑完整存在：`BuildProgressPage.vue:190`（读取）、`:199`（拼「已等待 X」）、`:203-207`（>60 秒提示）；类型声明见 `types.ts:129-132`。
  - 后端心跳 payload 只有 5 个键：`pipeline.py:191-196`（`done/total/facts/candidates/waitingPosition/waitingCount`）。
  - 全仓 grep `waitedSeconds` 仅命中两处**注释**（`pipeline.py:1293`、`BuildProgressPage.vue:7`），**无任何写入语句**——注释与实现不符。
- **附加事实**：心跳值（等待第几批 / 还有几批）在等待期恒定，前端文案逐字不变；批次日志只在整批结束才追加一行（`pipeline.py:1309-1331`），单批 1–4 分钟内无新行 → 视觉上完全冻结。
- **测试覆盖**：`tests/` 对 `waitingPosition`/`waitingCount`/`waitedSeconds` **零断言**（全仓 grep 仅命中实现与前端文件）。
- **用户可见性**：可见。
- **建议**：心跳处已有 `last_heartbeat` 与 `time.monotonic()`（`pipeline.py:148`、`:188-196`），补写 `waitedSeconds` 即可；符合既有纪律「秒数一律用服务端心跳值，不做本地倒计时」（`BuildProgressPage.vue:193`）。

### P1-2 返回任务列表没有直接入口

- **现象**：从生成页回任务列表需连点三次，且按钮文案不指路。
- **路径实读**：进度页只有「← 返回范围」（`BuildProgressPage.vue:389`）→ 范围页「← 返回物料」（`BuildScopePage.vue:494`）→ 物料页「← 生成任务」（`BuildMaterialsPage.vue:514`，即 `backToBuildTasks`，`App.vue:552`）。
- **步骤条不含任务列表站**：`BUILD_STEPS` 只有 物料 / 确定范围 / 生成 / 评审初稿 / 保存新本体（`App.vue:501-504`），且仅在已选任务时渲染（`App.vue:1134-1136`）。
- **任务列表行也没有「查看进度」按钮**：四个操作分别是「继续/查看任务」「停止」「查看已创建本体」「删除」（`BuildTasksPage.vue:335-340`）。任务失败回到 `scope` 状态后，用户想再看进度只能重新走一遍向导。
- **用户可见性**：可见。
- **建议**：步骤条前置「任务列表」一站；或任务列表行对 `generating`/`review` 状态给直达入口（`App.vue:525`、`:552-553` 已具备阶段跳转能力，仅缺状态→阶段映射）。

### P1-3 单批模型调用超时导致整轮失败（含实测时间线）

- **现象**：3 批中 2 批成功（55 个候选已落库），但整轮显示 **失败**。
- **机制链**：
  1. 单批失败 → 记入 `failed_batches`（`pipeline.py:1307-1312`）；
  2. **任一批失败即抛 `PipelineError`，整个 run 标 `failed`**（`pipeline.py:1352-1365`；终态写入 `runner.py:149-151`）；
  3. 单批超时预算 = `max(provider 配置, 60 + 10×批内条数)`，上限 900 秒（`pipeline.py:70-77`）；20 条/批 → **260 秒**；
  4. 连接类错误最多 2 次尝试，**第二次超时减半**（`pipeline.py:220-231`）——重试反而比首次更短；
  5. 260 + 130 = **390 秒**才判失败。
- **实测吻合（实读）**：真实 run `58df79f4-94d7-4a0f-a3b7-58fa9e8c374e`，`created 05:27:51` → `updated 05:34:23`，墙钟 **392 秒**，与公式吻合。日志实读 6 行：批 1 完成 25 个 / 批 2 失败（无法连接接口）/ 批 3 完成 30 个。
- **模型侧波动（实测）**：同规格请求健康时 89.0 秒，线上批 1 实际 232 秒，批 2 挂住吃满超时。
- **用户可见性**：可见（体感为「大部分成功却算失败」）。
- **建议（需产品决策）**：① 把「部分批次失败」表达为**部分成功**状态而非 `failed`（需同步接口文档 08 与 `protocol.py:97` 的状态枚举，改动面较大）；② 重试不缩减超时预算，或允许配置重试次数（`pipeline.py:220`、`:230`）；③ 失败文案已含「已完成 X 批候选保留」（`pipeline.py:1361-1365`），可再强化。

### P1-4 输入事实里混入大量低价值元数据（实测 31%）

- **实测（实读）**：一份约 8 KB 的 JSON 材料产出 **110 条事实**，其中 **34 条（31%）是低价值叶子值**，样本含 `"1.0"`、`"true"`、`"zh-CN"`、空字符串——属 JSON 元数据（版本号、语言标签、布尔标记）。
- **传导路径（代码判定）**：这些事实同样占用 `model_facts` 的 500 条名额（`pipeline.py:50`、`:1200-1205`）与批内 20 条的位置（`protocol.py:27`），因模型须逐条产出候选 JSON，**直接抬高输出 token 与耗时**；同时无业务语义，会被抽成无意义候选或干扰同批质量。
- **代码现状**：过滤只发生在检索层（关键词命中与依赖扩展，`retrieval.py:211-333`），**没有任何按取值形态/信息量过滤事实的机制**；检索的「保守保留、不丢材料」原则（`retrieval.py:6-7`、`:311-329`）与此处的输出成本诉求直接冲突。
- **用户可见性**：可见（表现为慢 + 候选含噪声）。
- **建议**：在解析层（`parsers/`）或检索层增加**弱信息量叶子值过滤/降权**（长度极短的标量、布尔字面量、语言标签、空串），并按既有 `notes` 可见性纪律如实注记数量（`pipeline.py:600-606`），避免静默丢材料。**涉及「不丢材料」原则边界，需用户确认。**

### P1-5 输出 token 有一半是「思考过程」（实测）

- **实测（真实模型调用，请求规格与线上单批一致）**：

  | 指标 | 数值 |
  |---|---|
  | `prompt_tokens`（输入） | 2432 |
  | `completion_tokens`（输出计费） | 3889 |
  | 其中 `content` 正文（真正的 JSON） | 3007 字符 ≈ **1927 token** |
  | 其中 `reasoning_content` 思考过程 | 8676 字符 ≈ **1961 token（占 50%）** |
  | 耗时 | 81.0 秒 |

- **响应 `message` 实际字段**：`content` / `reasoning_content` / `role`——模型（GLM-5.3-Flash）每次都先输出一大段英文推理，再给 JSON。
- **思考原文节选**：`"The user wants me to extract ontology candidate definitions from the given facts... Let me analyze the facts: 1. Metadata facts: uri, name, version, language..."`——**它在逐条复述我们喂进去的元数据**。
- **影响**：思考是计费的、耗时的，且不产生任何业务价值；输出总量与耗时约有一半来自这里。
- **用户可见性**：间接（表现为慢与额度消耗）。
- **建议**：抽取属「照抄 + 归类」型任务，可要求模型直接输出（提示词加约束）；或对抽取环节改用非推理模型；或把思考预算做成可配置项。

### P1-6 输出 JSON 的格式骨架占近一半（实测）

- **实测（按 55 个候选逐个字段统计，重建模型输出）**：

  | 组成部分 | 占比 |
  |---|---|
  | **JSON 结构骨架**（字段名、括号、引号、逗号） | **47.9%** |
  | evidence 证据引用 | 22.0% |
  | definition 业务定义 | 9.4% |
  | fields | 7.2% |
  | key | 6.0% |
  | evidenceStatus | 3.5% |
  | type / name | 4.1% |

- **细化事实**：`factId` 形如 `bf-018d128e5e0dff29e1ca3554`（**27 字符**），一个批次引用 72 次，合计 1944 字符 = **输出的 14.3%**；真正的业务内容（definition + fields + name）合计不足 20%。
- **用户可见性**：间接（表现为慢与额度消耗）。
- **建议**：协议层压缩——数组代替对象、短键名、证据只传 factId 后缀（前缀在同一批次内可推断）。

### P1-7 源材料本身可能已是本体，存在「拆了再拼」的冗余（实测）

- **实测（源文件实读）**：该 8 KB JSON 顶层键为 `uri / name / version / language / source_graph / generated_from / validation / classes / object_properties / data_properties / known_issues_found`，`generated_from` 写明「人工精修（基于 semantica OntologyGenerator 草稿 + 92 条关系全量核对）」——**这是一份已经建好的本体**。
- **加工链**：该本体 → 解析成 **110 条事实**（`jsonLeaf` 54 + `jsonArraySummary` 56）→ 模型重新组装回本体 → 55 个候选。
- **噪声证据（实读候选名单）**：抽取结果里出现 `实体`、`属性`、`规则`、`边界`、`业务属性`、`规则类型`、`取值方式`、`来源`、`作用对象`、`实例数据表` 等——这些是**描述本体的元语言/字段名**，被当成了业务对象；而源文件里 `required_fields: ["name","definition","subtype","instance_table","applicableObject"]` 这类清单，正是这些噪声候选的来源。
- **用户可见性**：可见（候选里混入大量非业务概念，需人工剔除）。
- **建议**：识别输入若已是本体格式（JSON-LD / OWL / 自定义本体 schema，可用顶层键特征判定），走**直接转换**路径而非「拆成事实再让模型重组」。此项属架构级方向，**需用户决策**。

## 3. P3：工程与维护性问题（用户不可见）

1. **进度百分比在阶段切换时回退**：`progressPercent = done/total` 取自当前阶段（`BuildProgressPage.vue:223-230`），从 retrieve（done=total=pool）切到 abstract（done=0/total=批数）时百分比回落。
2. **阶段文案两处不同源**：`protocol.py:99-105`（后端「筛选材料片段」等）与 `types.ts:349-353`（前端「检索相关材料」等）对同一阶段键给不同中文；界面取前端，后端文案仅落在 `stage_label`，二者可能同时出现在不同位置。
3. **候选排序键与 `definitionOrder` 不一致**：列表按 `ctype, name, candidate_id`（`storage/ontology_build.py:919-921`），后者的类型顺序一致但排序键不同（按 `definitionKey`，`pipeline.py:956-957`），同一批数据在两处顺序可能不同。
4. **失败即清空该材料既有事实**：`_scan_write_pool_failure` 与超时路径都清空（`pipeline.py:733-752`、`:755-773`）。这是「失败不当空内容继续」的一致口径，但意味着一旦超时，之前成功解析的该材料事实也需重新解析。
5. **限额为「工程保守默认」**：`chunkBytes` 等（`protocol.py:9` 注释）；本工作树实例曾按用户指令临时放宽到 256MB/512MB（`protocol.py:14-16` 注释），**该取值不代表产品默认**。
6. **`checkpoint.generate` 与 `progress` 大量字段无人读**：`checkpoint.generate` 的 `modelFacts`/`relevant`/`related`/`excluded`/`batches.size` 及子字段 `batchId`/`scopeRevision`/`materialRevision` 无前端读取（前端改读顶层 `run.batchId` 与 `baseline`，`BuildProgressPage.vue:82-101`、`:238-243`、`:538-541`）；`progress` 的 `facts`/`candidates`/`relevant`/`related`/`excluded`/`groups`/`duplicates`/`resumed`/`issues` 同样无人读（前端只读 `done/total/waitingPosition/waitingCount`）；`cancelRequested` 由 `run_view` 输出但全仓无人读（`storage/ontology_build.py:615`）；`checkpoint.scan.fallbackFiles/fallbackBytes` 只声明类型不读取（`types.ts:194-195`）。这些字段每次阶段推进仍整体写入 `progress_json`（写点 `pipeline.py:1167-1185`、`:1210`、`:1237`、`:1287`、`:1343`、`:1379-1380`）。属「多写少读」，不影响正确性。
7. **`LLM_CONCURRENCY` 注释自相矛盾**：同段注释先写「默认 4」（`protocol.py:62-64`）再写「默认 3」（`protocol.py:65-67`），实现取 **3**（`protocol.py:69`）。
8. **抽取重试的 docstring 与实现不符**：docstring 称「瞬态错误（连接失败/5xx/429/超时）退避重试 2 次」（`pipeline.py:208-213`），实际是 **不含 5xx**（`_is_transient_llm_error` 刻意排除，`pipeline.py:95-106`）、**429 立即返回不重试**（`pipeline.py:227-228`）、**仅 1 次重试**（`max_attempts = 2`，`:220`）、固定 1 秒退避（`:231`）。
9. **接口文档与实现口径出入**：08 分册 §11 仍称「单材料解析超时未实现（P2）」而 §4 已描述其实现（`文档/接口文档/08-从物料自动构建本体接口.md:488` 对照 `:254-259`）；文档未登记 `progress.waitingPosition`/`waitingCount`（`:90` 仅写 `{done,total}`）；`checkpoint.generate` 的 `log`/`notes`（2026-09-22 新增）未进变更记录（`:469-490`）。

## 5. 修复优先级建议

### 5.1 第一梯队（建议尽快）

| 1 | **P2-8** `aligned_key` 为空 | 小（补一次纯函数调用） | 恢复「人工排除不得复活」保护——会**丢弃用户判断**的正确性缺陷 |

## 6. 本清单未核实的点

> 以下条目来自审计过程，明确标注为**未取得证据**，不得作为结论引用。

1. **HTTP 层服务端超时**：`workbench/server.py` 未逐行核对（请求读超时 / `ThreadingHTTPServer` 重试窗口），「后台作业与 HTTP 请求线程的关系、长轮询是否受影响」未核实。
2. **心跳的线上中间态**：库中该 run 的 `progress_json` 是批次落库时的最终值，未捕获心跳中间态；「心跳是否真的每 15 秒可见」仅从代码路径推断（`pipeline.py:188-196`），无实际轮询快照。
3. **`_finish` 未推进 attempt 时的 lease 影响**：两条轮换路径的交互只在代码层阅读，未做注入式验证。
4. **拆批最深层的真实耗时**：只从代码推导上界（≤2 层、每层 2 次尝试）；本机未出现拆批样本（`log` 无「已自动拆批重试」行）。
5. **`_is_transient_llm_error` 的真实命中率**：库中仅 1 条 generate run，无法统计「连接类 vs 确定性」错误分布。
6. **`waitedSeconds` 是否为前端刻意留白**：未找到需求原文对该字段的验收口径，只确认「前端读、后端不写」。
7. **`scope_revision` 不同源的消费面**：已定位成因（`confirm_scope` 不写该列），但只核对了进度页与任务列表页，未穷举全部页面。
8. **`aligned_key` 为空的业务影响幅度**：库中只有 1 个批次且属失败运行，**没有成功运行样本可比对**；「人工排除继承静默失效」的完整链路未做端到端复现（机制与触发路径已由代码确证）。
9. **扫描期 LLM 兜底的真实预算消耗**：`LLM_FALLBACK_MAX_FILES=200`/`50MB`、每文件 ≤16 片 × 6000 字的线上消耗未取样（该任务 `fallbackFiles=0`）。
10. **前端构建与浏览器实测**：审计为只读，未执行 `npm run build`、未起服务、未做浏览器验收；所有前端结论来自源码阅读。
11. **拆批期间的进度可见性**：拆批在单个 worker 线程内完成、`on_result` 回调前不落库，故拆批过程中前端看不到任何进度——代码路径确证，但无实测样本。
12. **心跳字段抖动**：心跳写完整 payload，两次心跳之间若发生别的 `stage` 调用，`waitingPosition`/`waitingCount` 会消失；实际轮询中的字段抖动未采样。
13. **升挡节奏**：并发 3 时「连续成功 2 次升 1 挡」规则可从代码确定，但本机唯一 run 只有 3 批且无 429，样本不足。
14. **`_leases` 兼容层**：只确认当前版本生产路径不写，未追历史版本或运行时其它入口。
15. **补写 usage 对回归断言的影响**：未查测试对失败运行 `usage_json` 的断言，实施前需核对（P2-7）。
