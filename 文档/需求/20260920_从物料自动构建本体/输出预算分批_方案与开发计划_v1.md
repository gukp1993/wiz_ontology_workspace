## 1. 目标与产品边界

用“语义单元＋输入/输出双预算＋持久化叶任务＋截断后细分”替代新任务的固定20条切批。

**承诺**：不把截断响应当完成；已成功叶任务可保留；重试只补未完成部分；所有目标单元要么有成功处理记录，要么有明确阻塞原因。**不承诺**：首次分批绝不超限、处理覆盖等于语义正确、耗时或token固定降低百分比。

本期面向当前解析器已经产出的事实。100MB原文件能否完整解析、普通JSON数组元素目前仅有摘要、snippet截断等输入覆盖问题必须继续显示，不得借本改动声称已实现100MB全量语义解析。本期不引入向量库、不做通用本体导入器、不换模型、不修改推理档位、不做SSE流式传输。完整叶任务落库后沿既有轮询渐进展示；流式可后续独立增加。

```text
BudgetProfile {
  profileVersion, contextLimit, outputLimit?, requestOutputCap,
  limitsSource: configured|provider_verified,
  estimationMode: tokenizer|utf8_heuristic,
  targetOutputRatio, inputReserveTokens,
  maxJobs, maxAttempts, maxSplitDepth, maxPlanBytes, maxTargetFacts

WorkItem {
  id, kind, subjectKey, primaryRefs[], contextRefs[],
  parentItemId?, partitionDescriptor?, estimatedInput, estimatedOutput
}
Job {
  id, rootOrder, parentId?, childIds[], itemIds[], state,
  requestFingerprint?, attemptSeq, candidateIds[], errorCode?
}
Attempt {
  id, jobId, runAttempt, leaseToken, requestFingerprint,

  promptTokens?, completionTokens?, reasoningTokens?, totalTokens?,
  promptBytes?, completionBytes?, usageSource: provider|unknown

```

primaryRefs是必须处理的目标；contextRefs仅帮助理解，可以重复，不重复算覆盖。引用为factId或`{factId, start, end, unit}`等明确片段引用，不改变原事实。unit明确为字符区间或结构路径，不能混用字节偏移。

所有语义结果仍解码为当前候选协议；不能用默认supported、默认关系基数替代判断。调用内key经现有或核对后的命名空间机制转稳定键，再入库。证据引用必须落在本次允许集合，不能因增量/拆批放松。

## 4. 预算和规划算法

### 4.1 能力与预算配置

适配层按实际provider＋model配置能力，不根据名称包含GLM就假设1M/128K。`requestOutputCap`默认沿用当前32000，但必须受配置的outputLimit约束（如未知则标为本地请求预算，遇供应商拒绝返回明确配置错误）。`contextLimit`须从已核实能力或显式配置取得；缺失时拒绝启用自适应模式并提示配置，不暗中猜1M。

初始工程默认（不是模型能力或质量保证）：targetOutputRatio=0.5、inputReserveTokens=2048、maxJobs=512、maxAttempts=2048、maxSplitDepth=8、maxPlanBytes=512KiB、maxTargetFacts=4096。经测试可调整，必须冻结到plan，不在resume时偷偷变化。调用返回字节/正文字符上限仍受llm_client现有限额约束，不因token预算大就放开。

提供feature flag `WIZ_BUILD_ADAPTIVE_BATCHING`，缺省关闭用于兼容；明确启用的新任务才建v2计划。能力配置实现可采用生成模块专属配置，不改全局其他LLM功能默认参数；T0须冻结配置键及读取优先级并登记capabilities，不把实际密钥加入指纹或日志。

### 4.2 从事实构造单元

按稳定材料顺序和定位顺序组织：JSON-LD以materialId＋nodeId分组；DDL以物料＋表；代码以物料＋限定符号；文档以物料＋章节。普通JSON优先使用现有事实的对象/数组元素路径；只有数组摘要时仅把摘要作为已知证据，不能补造元素。缺语义定位时按文件内连续窗口标为fallback，禁止直接以整文件为无限大单元。

同主体的属性与关系线索先放一起，附必要主体标识和邻域证据。单元过大时按主体定义/属性组/关系组拆；共享的主体信息只作为上下文。拆分前后primary目标守恒、context可重叠。

### 4.3 估算与装箱

输入对**最终序列化请求**估算，包含system、scope、事实、已有定义摘要、JSON格式及消息开销。优先使用与模型匹配的tokenizer；没有时用UTF-8字节数作为保守代理，另外预留消息开销，标为heuristic，不能展示成真实token或数学上界。

冷启动不直接根据文件KB推导输出。默认单根job至多4个小语义单元；每单元可用以下可单测启发式启动：`slots=max(1,叶字段数+显式关系线索数)`，未知数组摘要额外权重4；`visibleEstimate=512+256*slots+ceil(0.25*inputEstimate)`；缺推理统计时`outputEstimate=2*visibleEstimate`。这些系数仅工程种子，不是经验测量，须在代码与界面区分。

加入下个单元必须同时满足：

```text
inputEstimate + requestOutputCap + inputReserveTokens <= contextLimit
outputEstimate <= floor(requestOutputCap * targetOutputRatio)
```

供应商对上下文/推理预算的不同定义通过profile适配；不知道推理分项时直接用总completion做反馈，不能将reasoning再加一次。

无单元能满足时优先细分；不可再分则blocked，不截掉内容凑预算。按稳定顺序装箱，不能为了优先短任务永远饿死大单元。

### 4.4 自适应反馈

每次仅规划最多一个当前并发窗口，尚未派发单元等待反馈。真实usage可用时，同模型/提示词版本/输出协议/推理配置/单元类别维护本计划内高水位成本系数，至少8个完整成功样本后才允许逐步增大后续job；每轮增长不超过25%，下降可立即生效。冷启动与少量样本不宣称稳定P95。首版可只自动缩小、不自动扩大，以降低复杂度，但须在交付中标明。

已派发或已保存job不重分配身份。超限样本是“至少这么多”的下界，不作为低成本成功样本；未知usage不计0、不参与提高批大小。总预算由所有Attempt累计，不只统计最终成功结果。

## 5. 单次调用与超限恢复

将生成专用worker限定为一次供应商调用；原JSON修复、递归拆批和连接重试由协调者显式建Attempt，避免隐藏调用和漏记用量。其他scope/fallback调用的行为不应无关改变，可新增生成专用single-attempt入口。

llm_client应先读取finish_reason与安全usage，再分类结果；兼容旧调用者的返回形式。生成入口使用结构化结果：`ok|output_limit|input_limit|invalid_json|response_limit|rate_limit|transport_error|provider_error`。不要仅用中文字符串包含“截断”驱动调度；供应商异常映射有测试。usage不可得保持null，网络失败不能假称没有消耗。

处理规则：

| 结果 | 动作 |
|---|---|
| 正常结束且schema/证据校验通过 | 原子保存本叶候选、完成状态及Attempt；候选允许是空数组，但表示“该单元已处理”，不证明语义完备 |
| output_limit/input_limit/response_limit | 不把残缺输出作成功结果；父job转split，原子建立子job后再派发；记录本次消耗 |
| invalid_json | 同job至多一次修复尝试；完整记录新Attempt，仍失败则failed；不得默默扩大输出上限 |
| rate_limit/transport_error | 有界重试，同job本轮最多2次；429遵守可用Retry-After/退避；达到上限failed，不能误当材料需拆分 |
| provider参数/鉴权错误 | 明确失败并停止重复调用，不递归拆物料 |

优先按单元边界平衡二分；单单元按可验证子结构拆。长文本只能按段/句或明确字符区间分片并保留原factId＋范围。没有合法分割点，或达到深度/调用数/计划大小上限时标`blocked: unsplittable_budget|plan_limit|attempt_limit`，保留已完成部分及剩余清单。禁止无限“继续”、盲目提高max_tokens或把前N项当全部。

## 6. 持久化、恢复与完成条件

v1采用现有`wb_build_runs.checkpoint_json`内`generate.schemaVersion=2`；计划必须有规模上限，超限显式阻塞，不持续膨胀。大规模jobs单独建表属于后续扩展，不在本次默认引入迁移。

存储：冻结profile、所有目标item及分片关系、稳定job树、Attempt账本、未规划单元列表、计数与有界日志。planFingerprint覆盖材料/范围修订、原fact内容摘要、planner/parser/prompt/codec版本、模型及有效预算/推理配置。候选仍在原表，checkpoint只存ID。写前计算序列化大小；达到512KiB预留阻塞状态所需空间，不先写超限再截断。

状态为`queued/running/split/succeeded/failed/blocked`。一次worker请求前先持久化Attempt=started；结果回到协调者后，通过现有content_tx在同事务内核对取消和lease、保存结果/候选/状态。成功提交后才更新内存计数；普通写错误不能吞掉。当服务在发送请求后崩溃，未收账Attempt记unknown/interrupted；可能发生外部重复调用，明确不承诺供应商侧exactly-once，但本地成功候选必须幂等。

父job不因任一子成功而成功；所有终端叶成功才覆盖父目标。成功叶立即持久化，不等其他叶；最终显示顺序按稳定job顺序，不依赖到达顺序。重复回调、旧lease、重复resume不重复插入。

恢复兼容：旧v1检查点auto沿旧固定计划恢复，不按v2规则解释批号；v2 auto只恢复未完成叶和未派发item。`resumeMode=abstract`是用户明确的全部抽象重跑，可新建plan epoch，沿既有语义处理候选与人工记录；新旧epoch切换原子完成。未知版本拒绝，不能删结果猜测重建。冻结profile变化必须显式重建计划，不继续混用。

生成成功必须同时满足：未规划=0，所有必需终端叶succeeded，无failed/blocked，目标分片集合守恒，最终候选装配/校验完成。runner成功收尾增加v2 guard，不能仅靠pipeline最后一行检查。

本期不得沿旧`MAX_MODEL_FACTS`截前500条后成功：v2处理冻结目标全集，超过maxTargetFacts在调模型前失败并显示范围，用户缩小范围后建新计划。全候选读入/续跑必须分页，不依赖`all_candidates`的500条截断。当前最终候选500上限若保留，超限明确`CANDIDATE_LIMIT`并保留中间结果、停止交付；不能裁前500条报成功，也不能自行宣布扩大产品容量。已持久化候选超过500的恢复和清理要专项测试。

“覆盖”定义为调度处理覆盖，不是概念准确率。未解析片段、被排除材料、原snippet截断必须作为输入覆盖缺口继续显示；不纳入完成分母来掩盖它们。

```text
completion:{processingComplete,blockReason?}
```

Run原usage字节字段保留；新token计数应定义为已知用量小计，unknownUsageCalls>0时页面标“部分用量未知”，不能伪装总消耗。不输出factId全量、原始prompt/response、reasoning文本或密钥。

生成页显示“已处理X个目标单元／共Y个；成功叶N；拆分M；待处理/失败/受阻”，不能把不断增加的叶数当固定总进度。沿已有轮询更新，已持久化候选计数可见，但最终生成完成前不允许交付。v1仍显示旧批次界面，v2不误用旧done数组。

## 9. 必须通过的验证

新增可直接运行的标准库测试脚本：`test_ontology_build_budget.py`、`test_ontology_build_attempt_usage.py`、`test_ontology_build_adaptive_resume.py`；端到端假provider脚本 `test_ontology_build_adaptive_http.py` 需登记HTTP_TESTS，不让unit推导误分组。

| 场景 | 必须观察到的结果 |
|---|---|
| 同样字节数、不同字段/关系密度 | 估算分组不同；固定20条不再是唯一规则 |
| 缺tokenizer/缺usage | 明确估算模式与null；不计0、不擅自扩大批次 |
| 输入预算先超限 | 调用前细分或blocked；无静默clip |
| 正常批、零候选批 | 完整解析和覆盖记录；零候选不伪造对象 |
| length后左右子批一成一败 | 成功子持久化；resume只补失败叶，不重调成功叶 |
| 连续两层拆分、单元不可拆 | 目标集合守恒；不可拆明确阻塞，不无限递归 |
| 非连续失败叶、乱序完成 | 每叶独立保存，最终顺序稳定，无漏回调 |
| 取消/崩溃/重复回调/旧lease | 已提交结果保留；候选不双写；外部未知调用标未知 |
| 解析/预算/profile变化 | 旧plan不可无提示复用；v1/v2兼容行为可复查 |
| 父截断＋子成功＋JSON修复 | 每次Attempt均入账，无漏记父调用、无reasoning重复相加 |
| 501候选与超4096目标 | 不截前N报成功，分页读完整或明确容量阻塞 |
| checkpoint达上限、调用预算用完 | 已完成结果保留，剩余明细/数量可见 |
| 普通JSON只有数组摘要 | 不声称已覆盖数组全部业务条目 |
| 同名异主体、跨批引用 | 新调度不破坏已提交身份规则；新key、owner、端点一致 |
