## 结论速览（TL;DR）

1. **OpenSPG 的自动化构建 = 双链架构**：非结构化文档走 `扫描→解析→切分→LLM抽取→向量化→后处理→落库` 七环节链；结构化数据走无 LLM 的字段映射链。
2. **文件解析只支持 5 种格式**（txt/pdf/docx/md/dict）+ 9 类数据源（目录/URL/CSV/JSON/ODPS/SLS/语雀等）；**PDF 无真实 OCR**（`is_ocr` 参数是未实现的残留）。
3. **LLM 深度参与 8 类环节**：大纲/语义切分、NER、实体标准化归一、OpenIE 三元组抽取、事件抽取、知识单元分解、表格理解、摘要与原子问题生成；每个 chunk 走完整链路约 3-7 次 LLM 调用。mapping/对齐/写入等对齐清洗环节**全部纯规则、零 LLM**。
4. **核心算法是一套组合拳**：SPG 六类本体模型 + schema 注入 prompt 的两模式抽取（自由 OpenIE / schema 约束）+ 三段式实体归一（名称即 ID 精确合并、LLM 唯一官方名、向量相似边）+ KGDSL 规则推理在写库后自动推导归属与因果新知识。
5. **准确性靠七道机制**：schema 白名单注入 prompt → 输出解析强校验（schema 外丢弃/降级 Others）→ 后处理兜底 → 实体归一三件套 → schema 演进强校验 → 属性约束系统 → chunk 级溯源边。哲学是「schema 约束 + 保守对齐 + 规则推理补全」，不是「更强的抽取模型」。

## 0. 总体架构：两个仓库的分工

`OpenSPG/openspg` 仓库是 **Java/Scala 写的 SPG 图引擎**：SPG-Schema 语义建模、SPG-Builder 构建流水线编排框架、SPG-Reasoner（KGDSL 逻辑规则推理）、KNext 可编程框架、CloudExt 云适配层。

LLM 驱动的自动化构建智能在姊妹仓库 **`OpenSPG/KAG`（Python）**。Java 引擎的 pipeline 遇到 LLM 抽取节点时，通过 **Pemja（嵌入式 Python 桥）** 回调 Python 算子（`builder/core/.../physical/operator/PythonOperatorFactory.java:51-65`）——Java 侧只定义协议与策略接口，**抽取算法本体全在 KAG 仓库**。

两仓库的关键对应关系：

| 能力 | openspg（Java） | KAG（Python） |
|---|---|---|
| pipeline 定义 | 17 种节点类型枚举 + 逻辑/物理计划 | `Chain.__rshift__` 编译为 networkx DAG |
| LLM 抽取 | `LLM_NL_EXTRACT`/`LLM_BASED_EXTRACT` 节点（只声明调哪个 Python 类） | `kag/builder/component/extractor/` |
| 实体链接/融合 | `IdEqualsLinking`/`OperatorFusing` 等策略接口（默认平凡实现） | NER std prompt + 向量相似边 + aligner 合并 |
| schema 管理 | `kg_ontology_*` MySQL 表 + alter 流水线同步图库/ES | MarkLang DSL 客户端 + `SchemaClient.load()` |
| 规则推理 | `ReasonProcessor`（belongTo 归纳 + leadTo 因果） | — |

## 1. 构建流程

### 1.1 双链架构

按输入数据类型分流（`kag/builder/default_chain.py`）：

- **非结构化文档链**（注册名 `unstructured`，默认）：
  `Scanner 扫描 → Reader 解析 → Splitter 切分 → Extractor 抽取 → Vectorizer 向量化 → PostProcessor 清洗对齐 → Writer 落库`
- **结构化数据链**（注册名 `structured`）：`mapping → vectorizer → writer`，全程无 LLM，字段映射直接建图。
- 另有 `DomainKnowledgeInjectChain`（注册名 `domain_kg_inject_chain`）：外部知识图谱注入链。

### 1.2 非结构化链各环节

| 环节 | 职责 | 输入 → 输出 | 关键实现 |
|---|---|---|---|
| Scanner | 扫出待处理单元，支持 rank/world_size 分片 | 路径/URL/分区 → 文件路径列表或 dict 列表 | `component/scanner/` |
| Reader | 格式解析 | 路径/dict → `List[Chunk]`（pdf/docx/md 额外产出标题树 SubGraph） | `component/reader/` |
| Splitter | 切分 | `Chunk` → `List[Chunk]` | `component/splitter/` |
| Extractor | LLM 抽实体/关系 | `Chunk` → `SubGraph` | `component/extractor/` |
| Vectorizer | 按 schema 索引声明批量嵌入，向量回填为节点属性 | `SubGraph` → `SubGraph` | `batch_vectorizer.py` |
| PostProcessor | 无效数据过滤、schema 外降级、向量相似链接 | `SubGraph` → `SubGraph` | `kag_postprocessor.py` |
| Writer | 加命名空间前缀后 UPSERT 落库（REST） | `SubGraph` → None | `kg_writer.py` |

默认链的确切组装（`default_chain.py:111-121`）：`reader >> splitter >> extractor >> vectorizer >> post_processor(可选) >> writer`。链间用 `>>` 算子编译为 networkx DAG，按拓扑序执行（`knext/common/base/chain.py:102-169`）；每个 DAG 节点对上游全部输出并行逐条处理（`kag/interface/builder/builder_chain_abc.py:41-70`）。

数据模型：`Chunk`（id/name/content/type，type ∈ TEXT/TABLE，sha256 hash）；抽取产物统一为 `SubGraph`（节点/边 KV + 属性）；组件间数据包在 `BuilderComponentData` 里携带 hash_key。

### 1.3 执行模型：三层 MapReduce + 断点续跑

- **外层（文件级）**：默认入口 `BuilderChainStreamRunner`（`runner.py:294-493`）用 `ProcessPoolExecutor` 真多进程，每个子进程由 chain 配置重建链实例；旁路生成线程流式投喂。
- **内层（chunk 级）**：`DefaultUnstructuredBuilderChain.invoke`（`default_chain.py:123-191`）用 10 线程对每个 chunk 并行执行「抽取→向量化→后处理→写入」小流水。
- **断点续跑**：每个组件 invoke 都有 diskcache 检查点（`kag/interface/builder/base.py:151-163`），chunk 级 `processed_chunk_keys` 去重（`runner.py:339-346`）；命中直接返回缓存，重复执行安全。
- **数据分片**：所有 scanner/组件持 `ShardingInfo(rank, world_size)`，支持横向分布式切分。

### 1.4 Java 引擎侧编排

- 节点类型全集（`builder/model/.../pipeline/enums/NodeTypeEnum.java`）：source（CSV/STRING）→ `PARAGRAPH_SPLIT` → 抽取（`LLM_NL_EXTRACT` / `LLM_BASED_EXTRACT` / `USER_DEFINED_EXTRACT`，全部继承 `BasePythonNodeConfig` 经 Pemja 调 Python）→ `EXTRACT_POST_PROCESSOR` → `VECTORIZER_PROCESSOR` → 映射（`RELATION_MAPPING` / `SPG_TYPE_MAPPING`）→ sink（GRAPH/NEO4J）+ 写库后可选 `REASON`。
- Record 模型（`builder/model/.../record/`）：`ChunkRecord` / `EntityRecord` / `RelationRecord` / `EventRecord` / `ConceptRecord` / `StandardRecord` / `SubGraphRecord`（LLM 抽取原生产物）/ `BuilderRecord`（抽取→映射间传输协议）。
- `SPG_TYPE_MAPPING` 节点内部固化三级策略：**先 linking（实体链接）再 predicting 再 fusing（融合）**（`SPGTypeMappingHelper.java:230-232`）。
- 写库后 `--leadTo` 开启 `ReasonProcessor`：跑 KGDSL 规则推理自动推导新三元组写回（见 §4.5）。

## 2. 支持哪些文件的解析

### 2.1 数据源层（Scanner，9 类）

| 注册名 | 数据源 | 备注 |
|---|---|---|
| `dir` | 本地目录 | `os.walk` + 正则，默认只匹配 `.*txt$` |
| `file` | 单文件 | 支持 http(s) URL 自动下载 |
| `csv` / `csv_structured` | CSV | pandas 读取（dtype=str）；structured 版按 col_map 走结构化链 |
| `json` | JSON 文件/字符串 | 数组或单对象 |
| `odps` | 阿里云 MaxCompute 表 | pyodps，分区读取、区间分片 |
| `sls` / `sls_consumer` | 阿里云 SLS 日志 | 一次性 GetLogs 或消费者组持续消费 |
| `yuque` | 语雀知识库 API | 取 markdown 后走 md 链路 |
| `hotpotqa`/`musique`/`2wiki` | 基准数据集 | 每条 → {id,name,content} |

### 2.2 文件格式层（Reader，按扩展名分发，仅 5 种）

`mix_reader.py:56-62` 分发表：**txt / pdf / docx / md / dict**。未注册后缀直接抛 `NotImplementedError`。

| 格式 | 解析库 | 关键细节 |
|---|---|---|
| **PDF** | pdfminer.six（`extract_pages`）+ PyPDF2（读书签） | **无真实 OCR**：`is_ocr` 参数存在但全仓无任何 OCR 库调用（requirements.txt 无 magic-pdf/tesseract），属未实现残留。有书签：按书签切 Chunk 并建标题树，书签标题用 `SequenceMatcher`（阈值 0.90）在页面文本模糊定位；无书签：按页切 |
| **DOCX** | python-docx | 解析标题层级建树切 Chunk（`docx_reader.py` 近 800 行，最精细的解析器），并调 LLM outline prompt 为无结构文档补目录树 |
| **Markdown** | markdown==3.7 转 HTML + BeautifulSoup | 按 h1-h6 标题树切 Chunk；表格抽出为独立 TABLE 类型 chunk |
| **TXT** | 内置 open | 整文件 1 个 Chunk 不切分 |
| **dict** | — | `{id,name,content}` → 1 个 Chunk |

解析依赖（requirements.txt 实测）：python-docx、pdfminer.six==20231228、PyPDF2、pypdf、markdown==3.7、bs4、pandas、pyodps、aliyun-log-python-sdk。`markdown_to_graph.py` 只是 pyvis 可视化辅助脚本（未注册进链）。

### 2.3 切分策略（Splitter，5 种）

| Splitter | 算法 | LLM？ |
|---|---|---|
| `length`（默认参数 500/100） | 中英句号类分隔符切句 → 滑窗聚合（窗口重叠 100）；超长单句硬切；TABLE chunk 保留表头按行累积 | 否 |
| `pattern` | 正则匹配「数字. 标题」结构抽取 header/name/content | 否 |
| `semantic` | LLM 返回「段落在原文中的起始位置+摘要」列表，代码 `content.find(start)` 定位切片，找不到即丢弃；单片超 1000 递归再切 | **是** |
| `outline` | 最重方案：8000 token 预切 → 10 线程并行 LLM 抽标题（带 current_outline 连续性）→ 正则过滤（篇/章/节/条款 → 1-4 级）→ LLM 分批对齐层级（30% 重叠，失败回退中文规章正则兜底）→ 按标题树切 Chunk | **是**（多次） |
| 表格切分（基类） | markdown 表格定位，每片保留表头+分隔行 | 否 |

## 3. LLM 参与了哪些环节、具体做什么

### 3.1 总表

| 环节 | LLM？ | 每块调用量 |
|---|---|---|
| 大纲抽取/层级对齐/语义切分（切分期） | ✅ | 各 1..N |
| NER 实体识别 | ✅ | 1 |
| 实体标准化（官方名归一） | ✅ | 1 |
| OpenIE 三元组抽取 | ✅ | 1 |
| 事件抽取（仅 schema_constraint 且配置了 event_prompt） | ✅ 可选 | 0-1 |
| 知识单元抽取 | ✅ | 1 |
| 表格理解（表级上下文+行列摘要） | ✅ | 2 |
| Chunk 摘要 | ✅ | 1 |
| 原子问题生成 | ✅ | 1 |
| chunk/outline/naive_rag 节点化（RAG 基线） | ❌ | 0 |
| 结构化映射（spg/relation/spo mapping） | ❌ | 0 |
| 对齐合并（spg/kag aligner） | ❌ | 0 |
| 清洗+实体链接（postprocessor，向量检索） | ❌ | 0 |

即一个 chunk 走完整 schema_free 链路约 **3 次 LLM 调用**（NER → 标准化 → 三元组），配齐表格+摘要+原子问题可达 7 次。所有 LLM 调用带 `@retry(3)` 指数退避。

### 3.2 各环节详解

**① NER（`kag/builder/prompt/default/ner.py:25`）** —— schema 进入 prompt 的关键位置：初始化时把项目 schema 的全部类型名替换进 `$schema` 占位符（只过滤 Index 类型）。指令要点：「提取对知识构建和问答重要的实体，附 type/category/description；description 可基于你自己的知识、不受上下文限制；schema 中不存在该类型则返回空列表；以 JSON 字符串回应」。输出 `{name, type, category, description}`。LLM 结果与 external_graph（外部词典/图）NER 结果按 name 去重合并。

**② 实体标准化 std（`prompt/default/std.py:23`）** —— 消歧归一：「named_entities 里可能有不清楚的缩写、别名、俚语，请基于上下文和你自己的知识给出官方名称。**同一含义的实体只能有一个官方名**」。few-shot 示范 `American → United States of America`。输出 `{name, category, official_name}`；LLM 漏掉的实体由代码兜底补 `official_name = name`。产物落图为 `OfficialName` 边。

**③ OpenIE 三元组抽取（`prompt/default/triple.py:23`）** —— 「你是开放信息抽取专家，抽取所有可能的（主语，谓语，宾语）关系；每个三元组至少包含实体列表中的一个（最好两个）命名实体；**明确把代词解析为具体名称**」。谓词经驼峰转换直接变成边类型。

**④ 知识单元抽取（`prompt/default/knowledge_unit.py`）** —— 把 chunk 拆成原子知识点，输出 7 字段（内容/知识类型/结构化内容/领域本体/核心实体/相关查询/扩展知识点）；知识类型五分类：陈述性/案例类/事实性/过程类/推理类。防过碎规则：「如果再切会丢失上下文和论证过程，就不要再细分」。`Domain Ontology` 字段（`A->B->C`）解析为 SemanticConcept 节点链 + isA 边；`Related Query` 反向拉成 relatedTo 边。LLM 抽出的三元组本身也转成 KnowledgeUnit 节点（`triple_to_knowledge_unit`），与实体、chunk 互连。

**⑤ 表格理解（`table_extractor.py`）** —— 两次 LLM：先总结表名/表描述/关键词（JSON）；再对带 `row_index_N`/`[column_index_N]` 标记的每行每列做摘要。**代码强校验**：行摘要数必须等于行数（或+1 多层表头）、列摘要数等于列数，否则整表结果作废。三种 extract_type：chunk（仅建 Table 节点，不走 LLM）/ row_col（行列摘要切子 chunk）/ row_col_cell_graph（生成 Table/TableRow/TableColumn/TableKeyWord 子图）。schema_free 遇到表格 chunk 自动改走 table_extractor。

**⑥ 切分期 LLM** —— 见 §2.3（semantic 打点 + outline 抽标题/对齐层级）。

**⑦ Chunk 摘要**（`chunk_summary_prompt.py`）—— 「用与给定内容相同的语言生成摘要，不要带前置提示」，结果建 Summary 节点 + childOf/sourceChunk 边。

**⑧ 原子问题**（`atomic_query_extract_prompt.py`）—— 「抽出尽可能多能被该内容回答的问题；问题必须包含必要的实体名、禁止用 it/he/they/该公司 等代词」，逐行输出，每个问题建 AtomicQuery 节点连回 chunk。

### 3.3 工程细节

- **领域定制机制**（`prompt/utils.py:18-26`）：按 `f"{biz_scene}_{prompt_name}"` 找 prompt（如 `medical_ner`），找不到回退 `default_{prompt_name}`——换领域只换 few-shot 示例（medical 版把电影示例换成症状/药品/手术），指令逻辑与 schema 注入机制零改动；可按需精简输出 schema（medical NER 只输出 name/category 两字段）。
- **LLM 输出多级容错解析**（`prompt/default/util.py`）：多级正则 + 补括号 + 去 markdown 围栏修复坏 JSON；knowledge_unit 抽取显式 `with_json_parse=False` 把容错下放到这些解析器。

## 4. 核心算法

### 4.1 SPG Schema 表示框架（本体模型根基）

6 种类型（`knext/schema/model/base.py:24-30`）：**Basic / Standard（标准型，类型名须 `STD.` 前缀）/ Entity / Index（如 Chunk）/ Event / Concept**，根类型 `Thing`。每个类型可携带：

- 继承（父类型，仅 Entity/Event/Index 可继承）
- 属性/关系；属性可挂 **constraint**（NOT_NULL / MULTI_VALUE / ENUM / REGULAR 正则）、**index_type**（Vector/SparseVector/Text 及组合，向量化按此声明生成 `<属性>_vector` 字段）、**logical_rule**（规则属性，KGDSL 文本）
- Concept 类型特有 `hypernym_predicate`（isA/locateAt/mannerOf）与 `taxonomic_type_name`（概念挂载的实体分类类型）；概念类型不允许自定义属性，只接受六组内置语义关系：SYNANT（同义反义）/ CAU（因果）/ SEQ（时序）/ INC（组成）/ USE（用途）/ IND（归属），可 `autoRelate` 自动展开全部语义关系边
- 内置属性：Concept 有 `stdId`/`alias`；Event 有 `eventTime` 与 subject/object/time/loc 属性组

Schema 用自研 **MarkLang DSL** 书写（缩进式；Type→TypeMeta→Predicate→PredicateMeta→SubProperty 五层）。真实示例（`kag/examples/medicine/schema/Medicine.schema` 节选）：

```
namespace Medicine

Chunk(文本块): EntityType
     properties:
        content(内容): Text
          index: TextAndVector

HospitalDepartment(科室): ConceptType
     hypernymPredicate: isA

Disease(疾病): EntityType
     properties:
        complication(并发症): Disease
            constraint: MultiValue
        hospitalDepartment(就诊科室): HospitalDepartment
            constraint: MultiValue
     relations:
        abnormal(异常指征): Indicator
```

### 4.2 抽取算法：两种模式组合

- **schema_free**（自由模式）：NER → 官方名标准化 → OpenIE 三元组。不要求实体类型命中 schema，schema 外一律降级 `Others`。
- **schema_constraint**（约束模式）：NER（含属性抽取）∥ 事件抽取 → 关系抽取 ∥ 标准化。实体/事件类型及属性**自动继承自项目 schema**；属性类型非基础类型时「属性拉边」转成节点+关系。
- 另有 `spg_prompt.py` 五元组模式：LLM 输出 `[主语实体, 主语类型, 谓语, 宾语实体, 宾语类型]`，解析时非 schema 类型强制降级 OTHER_TYPE。

这套组合对应 KAG 论文（arXiv:2409.13731）的 LLMFriSPG 三层表示思想：**KGcs（知识/概念层）+ KGfr（图信息层/扁平文本层）+ RC（原始 chunk 层）互索引**——三元组同时扁平化为文本知识单元，保证检索可回溯原文。

### 4.3 实体链接与归一算法（三段式，从强到弱）

1. **名称即 ID 的精确合并**：节点 id 就是清洗后的实体名（`processing_phrases` 清洗），同 id 节点属性 dict 合并（`sub_graph.py:185-194`）；批内按 `类型#名称` 键合并（`spg_aligner.py:59`），跨批靠图库 UPSERT。
2. **LLM 官方名归一**：std prompt 产出唯一 official_name；`official_name ≠ name` 时建 official_name 节点并连 `OfficialName` 边。
3. **向量相似链接**：后处理把节点 name 向量在图中检索 topk=1，score ≥ 0.9（默认阈值）且非自身时加 `similar` 边（`kag_postprocessor.py:107-159`）——**建相似边而非硬合并节点**，消歧保守。

无编辑距离/字符串相似度归一；结构化数据可挂自定义 `link_func`。问答期另有实体链接：向量召回（阈值 0.8）+ 文本检索兜底 + 语义类型重排（`kag/common/tools/algorithm_tool/graph_retriever/entity_linking.py:205-271`）。

概念层归一：概念实例 id 约定为 `-` 连接的层级路径，按 `-` 拆分逐级建节点连 isA 边（`spg_type_mapping.py:176-196`）；解析/推理期概念词在 SemanticConcept 标签上向量检索 topk=1，score < 0.9 回退通用 `Entity`（`kag/common/parser/schema_std.py:82-103`）。

### 4.4 融合（Fusing）策略

- 批内：MultiValue 约束或对象属性 → 新旧值拼接 + set 去重；**单值基本类型属性 → 新值直接覆盖旧值**（`spg_aligner.py:73-89`）；多子图按节点/边对象相等性去重。
- 跨批：图库 UPSERT。Java 侧 `OperatorFusing`（调 Python 算子）/`OverwriteFusing`（恒等，靠存储 upsert 覆盖）。
- **没有 LLM 级的属性冲突仲裁**。

### 4.5 KGDSL 规则推理（构建期自动产新知识）

规则以 KGDSL 文本挂在 schema 语义上（`belongTo` 动态分类学 / `leadTo` 因果语义，`LogicalRule.content` 即 DSL 文本）。构建写库后由 `ReasonProcessor`（`builder/core/.../reason/`）执行两条推导链：

- **归纳推理**（belongTo）：规则 DSL 判定实体（如「缺血肌酐数据的患者状态」）→ 自动生成 `belongTo 概念` 归属三元组。
- **因果推理**（leadTo）：实体归属的概念命中某 leadTo 规则起点时执行规则，推出的新事件**递归**再做归属/因果推导，新记录写回图存储。

即规则能把抽取出的知识按本体逻辑**再推导一层**，补全图谱而不靠 LLM 幻觉。推理执行栈：LocalReasonerRunner → lube 逻辑/物理计划 → 经 cloudext 读图存储。

### 4.6 互索引结构

每个实体/知识单元挂 `source` 边指向来源 Chunk；三元组扁平化为文本 KnowledgeUnit（id=sha256）；Chunk/KU/实体三向互连——图结构与原文双通道，是检索可验证性的结构基础。

## 5. 本体建模准确性的保障机制（七道）

按「防在前、兜底在后」：

1. **Schema 白名单注入 prompt**——NER/关系抽取指令明确「主语和宾语实体类型必须是 schema 定义的类型，否则无效」（`spg_prompt.py:507`），从生成源头约束。
2. **输出解析强校验**——解析 LLM 返回时 `category not in schema` 直接丢弃（`spg_prompt.py:190-191`）；五元组两端类型不在 schema 里降级 OTHER_TYPE（`spg_prompt.py:596-600`）；表格行列摘要数量不符整表作废。
3. **后处理兜底降级**——`filter_invalid_data` 删无 id/label 节点，schema 外 label 强制归 `namespace.Others`（`kag_postprocessor.py:93-101`）。**不报错、不丢弃、也绝不自动扩 schema**——schema 变更只能走 MarkLang `diff_and_sync` 显式提交。
4. **实体归一三件套**——LLM 唯一官方名 + 名称即 ID 精确匹配 + 向量 similar 边（0.9 阈值），缓解 OpenIE 噪音与歧义（README 原文：「用概念语义对齐的知识对齐来缓解 OpenIE 引入的噪音问题」）。
5. **Schema 演进强校验**（`schema_ml.py:1192-1437`）——已发布 schema 禁止改类型类别/父类型（须先删再建）；被其他类型继承的类型禁止增删改属性；概念 hypernym_predicate 与 StandardType spreadable 禁改；事件 subject 属性禁删——防止建模演化弄断下游构建。
6. **约束系统**——属性级 ENUM/REGEX/MultiValue/NotNull 在 schema 层声明，构建与推理都受其约束；对齐合并按约束决定拼接去重还是覆盖。
7. **溯源与互索引**——实体/KU 挂 `source` 边指向来源 Chunk（chunk 级粒度），三元组扁平化为文本 KU，图上结论可回溯原文验证。

## 6. 局限性（诚实清单）

- **PDF 无真实 OCR**：`is_ocr` 参数是残留；扫描件 PDF 解析不了（只有文本层）。
- **溯源只有 chunk 级**：无字符级 offset/句子级 provenance。
- **单值属性冲突是「新值覆盖」**而非仲裁，跨批后写赢。
- **schema 外知识全部降级 Others**：开环，抽取结果不会反馈改进 schema。
- **无 LLM 级冲突仲裁、无别名表精确匹配**；实体归一靠「LLM 官方名 + 精确匹配 + 向量边」，向量阈值固定（0.9/0.8）。
- **MySQL/图存储适配**：cloudext 有 tugraph/neo4j/elasticsearch driver 抽象，但 KAG 侧 MySQL 运行时同样标注未实测（与本项目 MySQL 预留处境类似）。

其准确性哲学可总结为：**schema 约束 + 保守对齐 + 规则推理补全**，而不是「更强的抽取模型」。

## 7. 对本工作台「从物料自动构建本体」的启示

以下为调研者基于本需求线的参考性判断，非实施决定：

1. **schema 注入 prompt 是第一道质量闸**：把已有本体（对象类型/属性/约束）编译进抽取指令 + 强校验 JSON 输出，比先自由抽取再对齐便宜且准；「schema 外降级 Others 不丢数据」是值得抄的兜底。
2. **每 chunk 多轮小 LLM 调用**（NER→归一→关系，各自带 few-shot）优于一次大调用；领域适配只换 few-shot 不改指令（biz_scene 命名覆盖 + default 兜底）。
3. **LLM 输出必须配多级容错解析器**（正则修复坏 JSON），所有调用带 retry。
4. **解析环节诚实面对格式**：docx/markdown 靠结构（标题树），pdf 靠书签+文本层；对工程物料（如 chuangzhiyuan2.zip）这类带章节层级的内容，outline 先行切分最对症。
5. **实体归一保守策略**：LLM 官方名 + 精确匹配合并 + 向量只建 similar 边不硬合并——宁可欠合并不可错合并。
6. **断点续跑（per-chunk diskcache）+ 多进程×多线程两层并行**是万条目级物料能跑完的前提。
7. **溯源边 + 三元组扁平化为文本知识单元**双通道，是人工复核自动化产物的基础设施——与本项目讨论中的滞留留痕/确认记录机制同构。
