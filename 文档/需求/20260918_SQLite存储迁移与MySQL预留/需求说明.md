# 工作台数据库化方案：SQLite 落地，预留 MySQL

版本 v1 · 2026-09-18 · 架构设计，未实施、未迁移真实数据。

配套：[架构与流程交互图](交互原型_v1.html) · [开发计划](开发计划.md) · [执行指令](执行指令.md)。原型用于解释存储架构，不要求新增数据库管理页面。

## 1. 推荐结论

保留 Vue3、Python HTTP 服务和现有本体/项目/函数编排业务逻辑。增加薄的存储层，使用 **SQLAlchemy 2.x Core + Alembic + SQLite**；后续通过同一存储接口和数据库方言接入 **MySQL/InnoDB**。

采用“**关系表管理资产、版本、引用与配置；完整文档保存模型快照；可重建索引支持查询**”的混合模型。

不把对象属性全部拆成固定关系列，也不只建一张 `files(path, content)` 表。对象、属性、链接、动作、业务规则等定义变化频繁，需要完整保留 JSON 扩展；资产列表、版本引用、名称检索、反向引用则由数据库索引支持。

切换的是**工作台自己的配置库**，不是储能业务数据库。`m_storage_cluster_phase`、Redis实时值、历史采样表、ES等外部业务数据仍通过项目连接读取，不复制进工作台SQLite。用户填写的SQL模板仍查询项目业务源，不访问工作台内部存储库。

SQLite 物理上仍是文件，但应用不再直接读写几十个 JSON/YAML 文件，而是通过数据库事务与接口读写记录。

### 2.1 需要特别清除的文件耦合

只替换 `write_draft()` 不够：`model_routes.initial/current/restore/get_releases/get_source_reference`、`workflow.defaults()`、`project_routes.get_project_config()`、`versions.ensure_base_release()`、演示加载器等仍可能直接读旧目录。切换后的在线服务必须无此回退；否则会出现页面列表来自库、详情来自文件的双重事实。

## 3. 架构分层

```text
Vue 页面
  ↓ app/http + 本体/项目/编排 API 模块
Python 路由（已有URL、白名单、Origin、大小限制）
  ↓ 业务命令/查询服务（校验、发布分类、项目升级、权限边界）
存储接口（Repository） + 事务边界（Unit of Work）
  ↓ 一套 SQLAlchemy Core 查询与表定义
SQLite adapter                 MySQL adapter
本机文件库/WAL                 InnoDB/连接池

外部业务源/LLM调用 ← 独立执行器；不得占用内部库写事务
导入/导出适配器  ← 文档快照与附件；不是第二套在线存储
```

### 3.1 每层职责

| 层 | 做什么 | 不做什么 |
|---|---|---|
| 路由 | HTTP参数、错误映射、响应兼容 | 拼SQL、遍历草稿目录、重复业务校验 |
| 业务服务 | 保存/发布/升级/恢复用例；组织事务 | 暴露数据库连接给前端 |
| Repository | 资产、快照、版本、设置、凭据、缓存的读写 | 决定业务是否可发布 |
| Unit of Work | 一次业务操作共用一连接与一事务；提交/回滚 | 自动执行外部请求 |
| SQLAlchemy/方言 | 参数绑定、类型、引擎、SQLite PRAGMA/MySQL连接差异 | 把数据库差异散落进业务代码 |
| 格式适配 | API schema ↔ JSON-LD；旧文件格式导入；导出打包 | 保存时丢失未知字段或换稳定ID |

使用SQLAlchemy Core即可，不引入ORM实体树、微服务、任务队列、Redis缓存、事件总线或复杂DDD框架。现有业务函数可逐步改成调用Repository，不要求整体挪进新的 services/ 大目录。Core支持显式连接与事务以及多种数据库方言，适合此处的轻量数据层。[SQLAlchemy文档](https://docs.sqlalchemy.org/en/20/core/connections.html)

### 3.2 为什么不直接到处使用 sqlite3

Python标准库sqlite3足以实现本地数据库，但若业务函数依赖PRAGMA、SQLite专用UPSERT、JSON函数和问号占位符，未来MySQL仍需重写。让SQLAlchemy编译语句，数据库差异收口到engine/types模块；默认SQLite仍使用标准库驱动。新增依赖有明确收益：SQLAlchemy处理方言，Alembic管理表结构变更，cryptography处理凭据加密；PyMySQL只在内部库选MySQL时需要。

版本由实施时锁文件固定并在目标Python运行时验证，不在本方案中承诺“永远兼容最新版本”。

## 4. 数据模型：完整快照 + 查询索引

### 4.1 三个不变原则

1. 稳定ID不变：本体ID、项目ID、flowId以及对象/属性/规则/动作ID原样保留。
2. 一次草稿保存是一个整体：项目五份文件不能拆成五次事务。
3. 发布不可变：项目引用确定的本体发布版本，不跟随本体当前草稿自动改变。

### 4.2 建议表清单

以下为首期逻辑表；字段名/类型经双数据库契约测试后冻结。不是一张对象类型对应一张数据库表。

| 表 | 核心字段 | 主键、约束与用途 |
|---|---|---|
| wb_assets | asset_uid, kind, external_id, name, name_key, summary_json, created_at, updated_at, deleted_at | PK asset_uid；UNIQUE(kind,external_id)；kind=model/project/flow；登记资产，已有外部ID不改 |
| wb_asset_heads | asset_uid, snapshot_id, revision_token, generation, snapshot_seq, release_seq | PK/FK asset_uid；当前草稿指针和单调代际；snapshot可空仅用于资产创建事务内部 |
| wb_snapshots | snapshot_id, asset_uid, seq, purpose, payload_format, payload_json, content_hash, legacy_revision, created_at | PK snapshot_id；UNIQUE(asset_uid,seq)及(asset_uid,snapshot_id)；完整不可变文档，purpose=draft/release/imported-base |
| wb_releases | release_id, asset_uid, version_label, release_order, snapshot_id, source_draft_id, manifest_json, created_at | UNIQUE(asset_uid,version_label)、(asset_uid,release_order)；指向所属资产快照；保留原版本标号、发布说明/分类 |
| wb_project_refs | project_snapshot_id, target_ontology_id, target_version, target_release_id, resolution | 每个项目快照最多一条；已解析引用FK到发布记录；缺失历史引用保留原字符串并标missing |
| wb_definition_index | row_id, asset_uid, snapshot_id, definition_kind, stable_id, stable_id_hash, owner_id, owner_hash, name, name_key, ordinal, document_locator | 当前本体草稿/已发布版本的定义查询索引；名称不是ID；包含对象/属性/共享属性/链接/规则/动作等 |
| wb_reference_index | row_id, snapshot_id, source_kind, source_id, target_kind, target_id, target_id_hash, relation_kind, document_locator | 共享属性引用、对象动作关联等反查；允许草稿中存在失效引用，由业务校验提示 |

| wb_model_configs | provider_id, name, endpoint, model, timeout_seconds, temperature, secret_id, metadata_revision, updated_at | PK provider_id保持原值；不含明文API Key；默认项由设置表统一记录 |
| wb_credentials | secret_id, namespace, owner_key, resource_id, display_name, key_id, nonce, ciphertext, secret_revision, updated_at | UNIQUE(namespace,owner_key,resource_id)；namespace区分connection/api/model；owner_key使用项目UID或固定global |
| wb_settings | setting_key, value_json, revision, updated_at | PK setting_key；首期存models.default_provider_id等实际设置，不预造账户数据 |
| wb_artifacts | artifact_id, owner_asset_uid, snapshot_id, release_id, purpose, legacy_name, media_type, content_hash, bytes_data, created_at | 历史ZIP、被引用导入材料、发布原始字节附件；允许owner为空的部署材料；不存密钥原文 |
| wb_import_items | item_id, batch_id, source_key, source_key_hash, source_hash, entity_kind, target_id, status, summary_json | UNIQUE(batch_id,source_key_hash)，命中后核对完整source_key；记录迁移映射、失败与可重入状态；summary不得包含秘密 |
| wb_requests | request_key, operation, owner_key, request_hash, response_json, created_at | 复合唯一(operation,owner_key,request_key)；发布等写入的幂等回执，不记录请求密钥/正文 |
| wb_write_guards | guard_key, generation | PK guard_key；初始化预建asset-name:model/project/flow与model-default等少量锁行，处理跨资产命名与第一条默认配置的竞态 |

summary_json只保留可派生列表摘要（如节点数、定义数），与head同步更新。需要运行配置校验才能得到的旧configStatus/errorCount，不能用过期摘要冒充实时结果；可按候选分页做校验，或标明摘要待重检。迁库不承诺所有旧列表接口完全不解析文档。

不是所有信息重复拆表：连接、对象绑定、函数规则的权威内容仍在**项目快照**；凭据/缓存/部署级设置有独立生命周期才单独建表。首期不单独建立object_types/properties/actions的第二套可写权威表。

### 4.3 字段和约束细节

- 内部主键用应用生成的UUID字符串；外部ID保持原格式（storage、UUID、项目/编排短ID）。不强行转换所有旧ID为自增数字。
- snapshot/head/release关系通过复合FK保证属于同一asset，不能让项目指向另一资产的草稿。asset_heads独立出来避免assets与snapshots建表环。删除默认RESTRICT；不为清理方便串联CASCADE删发布版本。
- 资产名称唯一按现行业务规则处理。当前项目名称检查还与引用本体范围有关，不能直接增加UNIQUE(kind,name_key)改变旧行为。创建/重命名在事务内先条件更新对应wb_write_guards行，再按原业务范围查询重复；同类名称写入在数据库内短暂串行，而非依靠进程LOCK。统一 `strip().casefold()` 生成name_key，再精确比较；MySQL用明确的二进制排序规则保存name_key/ID，不依赖默认大小写/重音等价规则。检查历史重名后才建立必要的唯一约束，不自动合并资产。软删除后的名称是否复用沿用原规则，不能顺带改变。
- stable_id可能是长IRI，完整值存TEXT，检索使用SHA-256定长hash；唯一键用(snapshot_id,definition_kind,stable_id_hash,owner_hash)，遇hash匹配还需比原字符串，不截断稳定ID以满足索引长度。definition_kind/owner为空用约定空串，避免NULL唯一语义差异。
- payload_json建议应用序列化为UTF-8 JSON文本；SQLite TEXT/MySQL LONGTEXT（方言类型映射）。业务查询不依赖原生JSON路径语法。数值/日期编码沿用现有API协议，禁止迁移器偷偷改单位、百分比或时间格式。
- 日期统一由应用写UTC；存储为约定精度的时间字段并使用类型适配，不依赖数据库当前时区。布尔统一应用bool，状态用受约束字符串，不使用MySQL ENUM。
- artifacts字节字段SQLite BLOB/MySQL LONGBLOB，大附件按批次导入；不把所有历史ZIP一次载入内存。API原2MB请求限制不为历史迁移放开，迁移走本机CLI。
- indexes/统计属于派生数据，可删除重建。快照、发布记录及其原始内容不可被重建过程修改。

### 4.4 快照格式与查询一致性

新保存使用现有API schema形态存入payload_json（包含ontology/workflow/layout等完整组件），前端JSON-LD编辑适配仍由model_format负责。definitionOrder和extensions全部保留。

迁移旧修订时保留其原始组件形态，标明payload_format（如legacy-files-v3），不先经可能丢字段的转换再写库。读取时用版本化适配器生成现有API结果；新保存才产生新格式快照。旧快照不被原地升级。已发布目录的原始文件字节归档到artifact（只打包该发布目录白名单，不包含vault），维持历史导出与完整性核对。同一资产/purpose/legacy_name重复附件须核对内容，禁止静默覆盖。

定义/引用索引只为**当前草稿与发布快照**生成，避免每次自动保存都永久复制一整套历史查询索引。新草稿快照、索引和head在同一事务中切换；过往草稿索引可后续清理，快照不删。历史草稿查询直接读取该快照并解析，或按需重建索引；不能误查当前索引。

每个查询都先固定snapshot_id，再读索引或文档。响应带snapshot/revision；分页游标绑定该快照。翻页过程中已保存新草稿时，继续旧快照或返回明确的游标失效，不能跨版本拼结果。发布查询固定release_id。索引不存在时回源完整文档或显式重建，不能返回假空列表。

## 5. 接口设计

### 5.1 HTTP：兼容优先，不把数据库暴露给浏览器

| 现有接口组 | 新实现 |
|---|---|
| GET/POST /api/ontologies，GET /api/state，POST /api/save | 本体资产与快照服务 |
| GET /api/versions、/api/version-state，POST /api/publish | 发布服务；原本体语义版本规则保留 |
| /api/projects、/api/project-state、/api/project-save、/api/project-publish | 项目资产服务；原v1/v2编号保留 |
| /api/project-upgrade-check | 读取两个固定本体发布快照 + 当前项目快照；仅预检不写入 |
| /api/flows、/api/flow-state、/api/flow-save、copy/delete | 编排资产服务；运行仍由现有executor负责 |
| /api/connection-catalog、catalog-refresh | 外部读取后短事务写catalog_cache |
| /api/connection-secret、api-credential、llm-provider-* | 凭据/模型配置服务；浏览器只读安全元数据 |
| /api/export、restore、releases、source-reference | DB读快照/附件，边界处生成或解析文件；历史名称解析仍兼容 |

首期保持URL、state字段和状态码兼容，不强迫所有Vue页重写。写入接口仍接受revision，409仍带currentRevision。新增内部库健康/迁移状态接口只返回就绪/迁移版本/后端类型，绝不返回含口令DSN或主密钥。

可补充只读查询接口：`GET /api/model-definitions?ontology=...&version=...&kind=property&owner=...&q=...&cursor=...&limit=...` 和 `GET /api/model-references?...`。version省略表示读取一次固定当前快照；搜索按明确规则匹配，limit上限100。只有页面确需分页/引用查询时接入；现有整state读取仍可继续。

本期不新增每个字段的PATCH接口。后续若拆细粒度保存，必须复用同一整资产事务和版本控制，不能绕过快照规则。

### 5.2 Python存储接口（示意）

```python
class AssetRepository(Protocol):
    def list_assets(self, kind, cursor=None, limit=50): ...
    def get_head(self, kind, external_id): ...
    def read_snapshot(self, snapshot_id): ...
    def append_snapshot(self, asset_uid, payload, format, purpose): ...
    def compare_and_swap_head(self, asset_uid, expected_token,
                              expected_generation, next_snapshot_id): ...
    def list_releases(self, asset_uid): ...
    def get_release(self, asset_uid, version_label): ...
    def append_release(self, asset_uid, snapshot_id, version, manifest): ...

# 只有业务服务决定事务边界；仓储方法不自行commit。
with unit_of_work.write() as tx:
    tx.assets.compare_and_swap_head(...)
    # 快照、索引、引用及必要回执由同一tx写入
# 任一异常：全部回滚。
```

另有ConfigRepository（模型配置、凭据、目录缓存、设置）和ArtifactRepository。接口只返回值对象/dict，不向上层暴露SQLAlchemy Connection、Path或行对象。禁止万能execute_sql接口给页面自由拼内部查询。

## 6. 并发、事务与revision

### 6.1 revision与内容哈希分离

现在多个存储模块把内容SHA当revision。新架构区分：

- `content_hash`：按已标记格式的确定序列化计算，判断内容完整性/同内容，不作为修订主键；同内容可以出现于多次修订。
- `revision_token`：不透明且不复用的保存版本，例如`r:<snapshot_uuid>`，用于客户端并发控制。
- `generation`：数据库CAS计数，每次资产写事务单调增加。防止A→B→A后旧客户端误以为没发生修改。

迁移时当前旧revision可作为初始token保留以便兼容，第一次成功写后返回新token，不再生成内容哈希形式token。切换期间旧页面一旦过期返回409并提示刷新，不接受仅按内容相同放行。前端须核对没有解析revision前缀的逻辑；界面显示短hash只能用于展示。

API字段名revision与现有409契约不变；路由必须改为取Repository的token，不能继续现场调用`revision(state)`替代数据库版本。旧legacy_revision单独保留用于审计/导出兼容。

### 6.2 草稿保存事务

1. 事务外解码/结构校验/生成候选文档与索引，保留本次依赖的当前revision、generation及配置指纹。
2. 开启短写事务：读取/检查head，执行条件UPDATE提升generation（或等价行锁+CAS）；expected_token或generation不一致则回滚返回409。
3. 在同一连接上插入快照，分配该资产seq，更新定义/引用索引、项目版本引用，指向新head并生成新revision_token。
4. 记录幂等回执（适用时），提交后才返回成功。
5. 插索引/写快照/更新head任一失败全部回滚。不能先commit快照再换head。

SQL示意（具体编译交给SQLAlchemy）：

```sql
UPDATE wb_asset_heads
SET generation = generation + 1
WHERE asset_uid = :asset AND revision_token = :expected
  AND generation = :read_generation;
-- rowcount必须等于1，否则回滚。
```

SQLite采用明确短写事务（实现层配置BEGIN IMMEDIATE）；MySQL采用InnoDB事务及同一条件更新。碰到SQLITE_BUSY/死锁仅有限次重试整个未提交事务；过期revision不自动覆盖保存。CAS失败先回滚，再在新读事务获取currentRevision，避免MySQL旧快照返回已经过期的token。数据库不可用/锁超时返回可重试存储错误，不报成业务字段错误，也不回退写文件。

现有进程LOCK可在过渡期保留，但不能作为最终正确性保证：多进程靠DB CAS/唯一约束。目标读/外部调用不占全局锁，后端不能因一次LLM请求阻止保存。

### 6.3 发布与恢复

- 发布基于固定候选快照完成业务校验/变更分类；事务中再核对head/上个release及影响校验的依赖代际。变了则409或要求重新校验，不发布旧校验结论。
- 版本分配、发布快照、manifest、引用、release索引以及当前接口原本会保存的项目草稿必须一个事务成功。发布快照按现有约定去掉空metrics/rules，与草稿内容有差异时另存release-purpose快照。
- 同资产并发发布用head generation或行锁串行分配版本，版本号唯一约束兜底。新版本严格递增，不根据字符串排序计算2.0.0与10.0.0。
- 发布成功但HTTP回包丢失：客户端复用同一个requestId查询/重试，返回相同回执。相同requestId不同请求hash返回409；不能生成两个发布版本。旧客户端无requestId时不承诺幂等，可先兼容后由发布按钮补传。
- 发布与普通保存都不自动升级任何其他项目的本体引用。升级通过现有预检与显式保存完成。
- 恢复历史内容创建**新草稿快照**，保留恢复前snapshot供撤销/备份引用。绝不修改已发布快照或恢复项目部分进本体草稿。
- 资产删除优先保留现有语义且检查发布引用；禁止物理级联删除被项目版本引用的本体发布。首期不自动清理历史草稿/ZIP/附件。

## 7. SQLite部署规则

建议默认文件：`<DATA_ROOT>/data/workbench.sqlite3`，路径明确与真实/测试根隔离；旧ontology目录切换后成为只读迁移备份，不再在线写入。数据库路径用受保护启动配置，不能被项目“数据连接”页面覆盖。

- WAL用于读写并行，但仍是同一数据库同一时刻一个writer；不把WAL文件放NFS/网盘同步目录供多主机共享。多人/多进程并发量明显上升时迁移MySQL，而不是用应用线程数量证明容量。[SQLite WAL](https://sqlite.org/wal.html)
- 每个连接启用`foreign_keys=ON`，`busy_timeout=5000`作为初始建议；初始化验证journal_mode实际为WAL。持久化建议`synchronous=FULL`优先数据可靠，性能经实测再调整。
- 每次请求/事务使用独立连接上下文，不在线程间共享正在使用的连接；正确关闭结果集，避免长读事务阻塞checkpoint。Python sqlite驱动的事务行为必须显式配置并回归测试，不依赖默认legacy模式。[SQLAlchemy SQLite方言](https://docs.sqlalchemy.org/en/20/dialects/sqlite.html)
- 库目录0700、库及临时/备份文件按最小权限创建；SQLite本身不是内置账户权限系统。本期仍绑定127.0.0.1，不顺带开放远程管理。
- `integrity_check`、`foreign_key_check`作为迁移与恢复验证；外键需逐连接启用。[SQLite外键文档](https://sqlite.org/foreignkeys.html)

外部业务SQL、Redis、HTTP、LLM执行之前读取需要的不可变配置/凭据，释放内部事务再调用。结果/缓存若需保存，另开短事务，并比较原配置指纹；配置变更导致的迟到目录结果应丢弃，不能写到新连接名下。

## 8. MySQL预留：不只是替换连接地址

数据库方言层解决语句和驱动差异，业务接口不变；但真正上线MySQL仍需要建库、迁移数据、配置证书/权限、跑同一套测试并切换。

| 差异 | 本期预留约束 |
|---|---|
| 驱动 | SQLite sqlite3；MySQL mysql+pymysql；一套Repository实现，方言差异限于engine/types |
| 事务 | InnoDB必选；CAS/唯一约束，不依赖进程LOCK；重试处理死锁；不假设数据库隔离级别恰好一致 |
| 类型 | TEXT/LONGTEXT、BLOB/LONGBLOB显式映射；统一UUID/UTC/布尔；不依赖SQLite宽松类型 |
| JSON | API保留JSON；首期库内按文本处理，不用某一家JSON函数作核心查询 |
| 名称/ID | 明确大小写策略和utf8mb4；用于相等比较的ID/哈希/name_key用确定的二进制排序规则 |
| 长索引 | IRI等长值不直接创建超长复合索引；定长hash索引+完整值核对 |
| NULL/唯一 | 固定非空作用域键，不靠多NULL达到唯一约束；不依赖SQLite partial index实现关键业务唯一性 |
| UPSERT/RETURNING | 不在业务写SQLite专用语句；优先通用insert/update+事务；方言特性仅适配层封装 |
| DDL | Alembic版本化迁移；SQLite batch迁表与MySQL DDL提交行为分别验证，不混在业务事务中 |
| 查询分页 | 显式排序、稳定游标、limit；不依赖隐含插入顺序；搜索语义由应用约定 |
| 连接与健康 | MySQL连接池+健康检查+受保护DSN；SQLite参数不能直接套MySQL；库不可用不建空库伪装正常 |

MySQL使用InnoDB事务与锁机制，不能通过启用一个驱动就保证业务并发正确。[MySQL事务文档](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-model.html)；SQLite表结构变更按Alembic batch策略实现并验证。[Alembic迁移文档](https://alembic.sqlalchemy.org/en/latest/batch.html)

首期必须对MySQL跑**存储契约测试**（创建/保存/并发/发布/回滚/名字/类型），但不要求把当前生产数据切到MySQL。没有测试库时明确标未验证，不能宣称已支持。

## 9. 凭据与配置

既然日常用户配置迁入数据库，连接密码、API凭据、模型API Key也迁到wb_credentials，但采用应用层认证加密，避免一份SQL导出直接带走明文。

- 使用成熟库提供的AES-GCM等认证加密；每条/每次加密生成新nonce，保存key_id；AAD绑定namespace+owner_key+resource_id，防跨行调换。禁止自研加密或重复nonce。[cryptography AEAD文档](https://cryptography.io/en/latest/hazmat/primitives/aead/)
- 根密钥从操作系统密钥存储或受保护启动环境加载；本地交付可使用库外0700目录下0600的key文件。**解密根密钥不能放在同一数据库明文表中**。这是启动秘密，不属于可通过业务API维护的数据。
- 数据库连接DSN、加密根密钥不能依赖数据库本身才能读取。后续部署MySQL仍通过环境/部署secret配置，日志全部脱敏。
- 模型元数据与其加密密钥一次事务写入；编辑留空保留旧密钥。数据连接密钥、API凭据使用原作用域与稳定ID，不误合并。
- 默认模型记录`models.default_provider_id`；服务读取时仍返回isDefault兼容字段。创建第一条、设默认、删默认的兜底行为保持现状，在同一事务先更新预建的model-default guard再修改设置行，覆盖第一条配置时设置行尚不存在的情况，防止并发出现多个默认。
- 公共查询接口只返回keyConfigured等安全状态，内部执行器经SecretStore解密；不提供读取明文的HTTP接口。
- 普通导出白名单不包括credentials/settings秘密；运维备份包含密文，但密钥另行备份并做恢复演练。根密钥丢失时应明确报错，不能自动生成新key覆盖旧key导致无法解密。
- 无需在本轮新增密钥管理后台、权限中心或账户系统。

## 10. 文件迁移方案

### 10.1 迁移方式

**受控停写迁移，一次切换，一个权威写库。** 不做长期文件/数据库双写，不在读取失败时自动退回文件，也不启动时静默扫描写入真实库。

迁移工具使用已有格式适配与显式文件清单，但不得直接调用会初始化/发布基础版本的线上读取函数。原目录只读；迁移报告只统计ID、数量、哈希、错误路径，不输出密钥或原始配置正文。

### 10.2 步骤

1. `inspect`：扫描登记、current指针、修订目录、发布索引、实际发布目录、历史ZIP、catalogs、三类vault、引用资源。记录来源版本、未知扩展、重复/损坏/孤儿文件；不写目标库。
2. `plan`：确定资产/发布/快照映射；本体发布先于项目引用；没有草稿的基础数据显式生成imported-base，保留旧读取结果。核对旧ZIP不等于语义发布registry，两者不能混成同一版本表。
3. 停止文件后端写服务或明确维护窗口；等待在途请求结束，生成**完整源备份**与稳定manifest。迁移过程中源清单变化立即停止，不“边写边搬”。
4. 在新路径创建staging数据库并应用schema；先资产，再历史快照/发布、当前head、项目引用、编排、缓存、模型配置、加密凭据、附件。外部模型/业务数据库不连接、不测试。
5. 按对象/阶段批次事务导入；wb_import_items记录源hash与目标ID，重复运行同一备份可继续且不重复插入；已有源同key内容改变则失败，不能无提示覆盖。
6. 验证：记录数、全部当前草稿语义哈希、历史发布内容/原始附件哈希、固定引用、原API输出对比、目录与密钥元数据数量一致；在工具进程内解密比对密钥但报告不输出值；integrity_check及外键检查通过。
7. 用隔离端口启动staging，运行只读接口验收及仅写入副本的回归测试；测试结束重新从已验收staging或源备份形成干净候选库，不能将测试数据随迁移切到生产。
8. 停机后切换受保护启动配置，启动数据库后端，检查只读/保存/发布闭环。明确记录切换点与新的schema/token策略。
9. 原文件备份保留只读，本轮**不删除**。观察与备份恢复验收后是否清理由用户另行决定。

### 10.3 不完整/特殊历史数据

- current指针缺失目标或当前文件损坏：阻断该资产切换，不自动选择“最新目录”掩盖问题。
- 孤儿完整revision、未登记的release目录：列入报告，保留为历史/附件或由用户决定，不静默丢弃、不擅自设为当前。
- 已有项目引用不存在版本：保留target_ontology_id/target_version并标missing；旧配置能展示，发布继续受校验阻止。不能创造空本体版本补FK。
- 发布hash不一致：阻断并定位；不用新编码重算后覆盖原hash。
- 扩展字段/新kind：原文保留，索引可标unknown；无法证明无损时停止，不“清理无用字段”。
- 历史同内容多修订：保持独立seq和snapshot，不按content_hash合并到一个记录。
- 旧ZIP恢复仍按原语义解析，不能因包含项目材料就顺便覆盖项目草稿。

## 11. 回滚、备份、恢复

- **切换前失败**：staging可重建；原文件未改，原服务可恢复。
- **切换后尚无新写入**：停库服务，恢复原后端与配置即可，但先确认没有新提交。
- **切换后已有新数据**：不能直接启动旧文件库。先停写，导出数据库中的全部新草稿/版本/设置/凭据，通过已验证的反向导出生成新的兼容目录并核对，再切旧后端；或者回滚程序到仍兼容当前schema的版本。反向导出涉及明文vault，目录需严格权限，不能放公开下载区。
- 回滚流程需在测试环境演练；schema降级不保证无损，优先修复前进或恢复受验证备份，不靠自动alembic downgrade碰碰运气。
- SQLite热备使用备份API或受支持的快照方式，不运行中只拷贝.sqlite主文件忽略WAL。[SQLite备份API](https://sqlite.org/backup.html)
- 备份包含数据库、schema版本、应用版本、根密钥key_id引用与校验清单；根密钥独立保管。恢复到新路径验证后再切换，禁止直接覆盖正在使用的库。
- MySQL采用该部署规范的事务一致备份/恢复；逻辑导出用于跨引擎迁移。SQLite→MySQL按表顺序导出/导入，保留所有稳定ID、token、发布号及语义哈希，重建派生索引，不把SQLite二进制文件当MySQL导入文件。

## 13. 分期与验收总标准

第一期完成：SQLite全部在线权威读写、事务/CAS、不可变发布、凭据与缓存迁移、导入/导出/备份、旧接口兼容、MySQL契约测试。前端不重做页面，只适配revision不透明化和必要requestId。

第二期需要MySQL部署时：真实目标库数据迁移、连接池容量配置、生产备份恢复、切换演练。不是重写本体/项目/编排模块。
