# SQLite存储迁移与MySQL预留：开发计划

版本v1 · 设计交付，未实施。

依据：[完整架构方案](需求说明.md) · [架构交互图](交互原型_v1.html) · [执行指令](执行指令.md)。

## 1. 实施策略

先完成可验证的存储层，再逐个替换业务存储入口，最后迁移、验收和切换。开发阶段在隔离数据上进行；真实迁移单独安排停写窗口，不能在某个页面第一次打开时自动执行。

保持现有HTTP接口。新增Repository、事务和迁移工具，不把全项目重写成ORM实体，不换前端框架或HTTP框架。完整快照为事实，定义/引用索引可重建。配置库与项目业务数据库使用不同引擎实例、不同命名与授权边界，禁止共享一个“任意SQL连接”入口。

P6是独立部署动作。当前用户只要求方案，**本方案交付不授权现在操作真实数据迁移或停服务**；实施代码和临时数据测试完成后，再提供具体迁移清单/备份位置/停写步骤供安排。

## 4. 需要冻结的技术合同

在开始P2前将最终决定追加本文件：

1. schema表字段/索引/FK以及SQLite/MySQL类型映射；name_key、项目名称范围、wb_write_guards及legacy重复名处理。
2. payload_format枚举与旧格式只读适配；公开DTO保持既有schema；未知字段/unknown kind不丢。
3. new revision_token格式、旧current hash接受一次的过渡、409 currentRevision读取新事务策略。
4. UoW事务启动（SQLite明确BEGIN IMMEDIATE、MySQL普通事务+CAS），异常类型与重试上限/退避。
5. wb_requests生命周期与发布requestId接入：同key同payload返回既有回执，不同payload409；提交状态不确定时只用同key重试。
6. secret命名空间、AAD、密钥来源、key_id与轮换/备份流程；不得把数据密钥放入日志。
7. migrate inspect/import/verify/export的精确CLI、目标校验、防误写生产库开关、停写策略。
8. 迁移清单包含所有修订/发布/附件/凭据；不完整条目处理报告，导入不得静默漏掉。

## 5. 并发与迁移测试重点

### 5.1 存储契约套件（两数据库同套运行）

- 各类型创建/列举/读取、同名规则、超长Unicode名字、大小写ID，空/布尔/日期/JSON结构保真。
- 两独立连接/进程持相同revision同时保存，一胜一409；回滚后用新读事务取currentRevision，不能用MySQL旧事务快照返回过期值。
- A→B→A后旧token被拒；相同content_hash的历史修订仍有不同snapshot/seq。
- 在插快照、写索引、切head、插release等步骤注入异常，事务结束后没有半保存/半发布。
- 并发发布编号不重复，requestId回包丢失重试只生成一版本；请求超时不自动判失败重发不同key。
- 发布快照不可通过任何Repository更新/删除；固定项目引用不随当前本体修改。
- 普通资产列表使用关系字段和派生摘要；需要实时校验的旧接口按候选集合读取文档，不扫描全部历史；定义索引回源/重建一致，分页token固定快照；索引清理不删版本。
- 默认模型创建/设置/删除事务一致；三种secret命名空间同名不冲突；密文不同nonce；错误key能识别失败。
- 外部请求人为延迟时另一资产保存正常完成；catalog配置指纹不匹配的迟到结果不落库。

### 5.2 导入与回滚

构造有旧draft.json、基础目录、V3多修订、发布目录/索引、旧ZIP、未知扩展、坏指针、孤儿修订、缺引用及三类虚构凭据的临时树。验证扫描/导入/重跑/源变更中止/导出对比。迁移数据的原文件hash保持不变。

历史发布原字节附件/manifest、所有当前API返回、语义hash与引用目标逐项比对，不能只比较文件/行数量。非法数据场景必须报告和阻断该切换，不能通过清空缺失项过关。

用迁移后的副本新增草稿/发布/模型配置，再走反向导出与旧兼容读取对比；证明回滚不会丢迁移后的新写入。热备恢复验证sqlite主库/WAL一致性，根密钥从独立备份恢复。真实钥匙不进入测试fixture。

### 5.3 现有功能回归与范围控制

本体类型转换、时间序列、属性来源、发布版本、项目引用升级、编排、保存队列、路径隔离、金样校验的现有套件按改动覆盖运行；修改project_validation规则才更新金样，不能仅为迁库顺手重写规则/文案。

改前端时必须`npm run build`；无前端改动也应在最终集成验证类型/接口消费者。浏览器自动化用临时WIZ_WORKBENCH_ROOT+专用端口；MySQL用独立测试库（非业务源连接），所有模型与业务外连用替身。

## 6. 性能验收

先用相同脱敏数据样本测文件版：列表、完整state读取、连续自动保存、发布、属性名称查找，记录记录数/快照大小/时间/峰值内存。再对数据库版重复，核对执行计划。

不先拍脑袋写“快10倍”。初始目标是结果正确、列表不遍历整个历史库、一次保存不阻塞外部请求、内存不随全部历史线性增长。大目录/大附件批量导入需分批；慢操作给出原因与优化前后证据。

SQLite容量拐点由锁等待、并发写量、数据库大小、备份时间实测决定，不能用“支持50agent”推导存储吞吐量。

## 7. 生产切换核对单

- 已备份原数据根，备份路径和key备份位置清晰，权限正确。
- 已停写且无另一进程仍写旧目录；来源manifest稳定。
- staging完整通过D01–D14适用项；未通过项目不隐瞒。
- 目标库与根密钥可读，schema版本匹配；目标配置不会连接业务数据库。
- 干净候选库不含验收产生的临时资产；切换后只读/写闭环用明确的测试资产并受控清理，不改用户已有资产。
- 数据库错误不会落回文件；旧目录保持备份只读。
- 回滚路径区分有无新写入，未把反向导出与业务公开下载混用。
