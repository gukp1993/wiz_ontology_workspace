## 2. 推荐实现：浏览器解析，复用现有草稿保存

本期不新增上传服务、解析后台任务、导入数据库或后端 Excel 依赖。

1. 将已确认模板复制到 `frontend/public/templates/ontology-import-v1.xlsx`。这里是运行资产，不是用户数据。开发/生产均通过静态路径下载，用 Vite BASE_URL 生成地址，不用硬编码文件系统路径。
2. 新增一个浏览器端 XLSX 读取依赖，懒加载。实施者核验正式上游分发渠道、安全状态和许可，锁定明确版本，提交锁文件；不要随手使用过时 CDN 或在页面运行时从外网加载脚本。
3. 解析只取业务列的原始值、公式标记、Excel行号；识别隐藏列和合并区域，不计算公式。格式、下拉验证不视为数据。单独封装解析模块，不能让 UI 到处感知库的数据结构。
4. 纯函数处理标准化、字段校验、同名决策与导入计划。计划在浏览器内存中，不写 localStorage、用户草稿或临时用户文件。
5. 确认后复用 `formSave.submitForm('ontology', mutate)`，批量追加全部新增定义。保存请求仍走既有编码与 `/api/save`。

该方案控制改动面；不需要更改本体持久化协议、项目映射、后端写入路径。若所选 XLSX 库无法可靠识别本模板的隐藏列/公式等必要信息，应在解析模块内换合适依赖，不能悄悄降低验收标准。

## 4. 内部数据契约（不新增本体字段）

建议结构，用于导入面板内部：

```ts
type ImportPolicy = 'skip' | 'rename';
type ImportKind = 'object' | 'sharedProperty' | 'businessRule' | 'action';
type ImportIssue = { sheet: string; row: number; column: string; message: string };
type ImportDecision = {
  kind: ImportKind; sheet: string; row: number;
  originalName: string; finalName: string;
  disposition: 'create' | 'skip' | 'rename' | 'error';
  reason: string;
  definition?: unknown; // 待追加的完整节点/工作流定义，含预先生成的稳定 ID
};
type ImportPlan = {
  ontologyId: string;
  baseRevision: string;
  baseContentFingerprint: string;
  fileFingerprint: string;
  policy: ImportPolicy;
  decisions: ImportDecision[];
  issues: ImportIssue[];
};
```

- fingerprint 仅用于判定预览过期，不是服务端授权凭证。结构可用现有编辑代数或稳定快照摘要实现，不引入跨后端认证协议。
- ID 使用已有生成方式（对象/属性 mg 稳定 ID、规则/动作按现有库构造器）。随机后缀和 ID 是两回事，Excel 不要求用户填写它们。
- 对象追加 `owl:Class`；属性用共享类型构造器，再设数据类型和自然语言格式。规则追加 `workflow.businessRules`；动作追加 `workflow.actions` 的 V2 结构。
- 不修改 `actionAssociations/businessRuleAssociations`，不生成属性引用、不生成链接。
- 已有数据用既有状态深拷贝/快照方式保护，不能只根据四表重建本体、丢失其它内容。

## 5. 保存与并发的实施要点

1. 打开面板前按现有导航/表单保护处理未保存修改，确保本体区保存队列进入可提交状态。
2. 检查完成记录本体ID、基线和计划；面板打开期间发生草稿变化则失效。切换本体经守卫，不把旧面板挂在新本体下。
3. 确认前再次检查基线和最终编码请求大小；进入 `submitForm` 后，在同步 mutate 入口再确认本体与状态未变，避免 flush 期间的变化被遗漏。不要在 mutate 中执行异步读取。
4. 若需要让 mutate 可以有理由地中止，局部扩展既有表单提交机制并补该分支测试，不能让异常逃逸破坏工作区状态。优先通过现有组件状态锁与基线检查实现。
5. 409必须重新读取和预览，不能通过「换 revision 强制重提交」掩盖过期的重名判断。无需修改所有普通表单的冲突策略。
6. 网络结果不明时，面板保留本次计划及 ID；禁用再次确认，先只读加载最新本体并逐项核对。所有计划新增 ID及字段一致则同步最新状态并显示成功；全不存在则使旧计划失效并重检；部分匹配或被随后修改则要求核对。
7. 核对时不能靠名称或成功数量猜测，不能因为观察到其他用户新增同名项就认定本次成功。后缀绝不因网络重试反复生成。
8. 不承诺跨浏览器重启的批次幂等。关闭浏览器后重新上传是新操作，会重新遵守用户选择的重名策略；本期不新增批次持久化。

## 7. 验证计划

- **模板检查**：四表名称、准确表头、1000行下拉、观测值 IF 联动、隐藏辅助列；下载文件哈希与原件相同。
- **解析测试**：空模板，单Sheet有数据，隐藏H列，打乱业务列顺序，缺表/缺表头/重复表头，业务公式及缓存，损坏文件，合并数据单元格，空格行，超行数，额外有数据列。枚举验证不等于业务单元格公式。
- **计划测试**：现有/批内同名，跨类同名，不同本体独立，trim/大小写，跳过缺其他字段的重复行，新行缺字段阻断；注入确定性随机函数测试碰撞、名称占位和超限，不依赖偶然随机结果。
- **序列化测试**：普通/时间序列/数组/结构体、显示格式自然语言、规则/动作与现有结构一致，decode/encode 往返，definitionOrder 无遗漏。
- **保存集成**：单批一次保存、刷新读回、取消和预览零修订、错误整批零写入；旧字段与旧关联保留；两客户端409；模拟服务端已写但响应丢失，不重复导入。
- **前端验收**：运行 `cd frontend && npm run build`；用真实页面选择文件操作，不用只有 mock 的单元测试冒充端到端。
- 自动化后端/浏览器写入均用 `WIZ_WORKBENCH_ROOT=<临时目录>`、`WIZ_WORKBENCH_PORT=<隔离端口>`，不要向18765真实草稿写测试数据。
- 若修改 `saveCoordinator.ts`，遵守AGENTS要求先补保存队列用例；否则不为了本功能重写或全量扩展其测试。
