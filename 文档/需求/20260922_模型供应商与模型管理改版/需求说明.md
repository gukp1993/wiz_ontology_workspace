# 需求说明 — 模型供应商与模型管理改版（参照 ZCode 开源配置模型）

- 版本：v1（2026-09-22，zcode 交付）
- 关联：`交互原型_v1.html`、`开发计划.md`、`执行指令.md`（同目录）
- 状态：**方案与原型交付，未实施**。不得据此声称工作台已实现。

## 1. 背景与现状局限

当前「设置中心 → 基础设置 → 模型设置」（`frontend/src/tools/LlmProviders.vue`）是一条**扁平配置**：一行 = 名称 + 完整 chat/completions URL + 单个模型名 + 密钥（`wb_model_configs` 表，`(owner_user_id, provider_id)` 主键）。经只读调研核实，存在以下局限：

1. 无供应商预设：必须手填完整 `chat/completions` URL，仅靠 placeholder 提示。
2. 模型名纯手填：不能从 `/v1/models` 拉取，也没有内置模型目录，写错只能在调用时失败。
3. 无模型元数据：上下文窗口、最大输出、思考档位（reasoning levels）均无概念；`max_tokens` 在 `llm_client.py` 硬编码 4000。
4. 无启用/禁用：不想用的配置只能删除。
5. 一条配置只绑一个模型：同一供应商下多模型要重复建多条、重复填同一个 Key。
6. 默认项只到「配置」粒度：无法表达「默认用某供应商的某个模型」。
7. 节点级绑定只有 `providerId`：编排节点不能选该供应商下的具体模型。

密钥安全（AES-256-GCM + AAD 绑定 + 库外根密钥 + 只写不读回）与按账号隔离是既有正确设计，本改版**完整沿用，不改加密体系**。

## 2. 参照物：ZCode 开源配置模型（已核实）

用户指定直接参照 ZCode（智谱开源 coding agent）。核实来源：

- 本机实际配置 `~/.zcode/v2/provider_config.json`（与 ZCode Desktop 共用同一格式）；
- 开源仓库 [kingsword09/zcode-cli](https://github.com/kingsword09/zcode-cli)（从 ZCode Desktop 提取官方 agent runtime）的 `provider.example.json` 与 `docs/PROVIDER_CONFIG.zh-CN.md`；
- 应用内置目录 `/Applications/ZCode.app/Contents/Resources/config/provider/zcode-builtin.json`（revision 30，182KB）。

### 2.1 三层配置模型（ZCode 的核心思想）

```
第 1 层  内置目录（随应用分发，只读，版本号 revision）
         ├─ templateRules：20 个供应商模板（api.type + baseUrl 预填）
         ├─ modelRules / modelApiRules：按模型名正则匹配的默认能力规则（84/72 条）
         ├─ templateModelRules：每个模板默认启用的模型清单（244 条）
         └─ builtinProviderModelRules：内置账号型供应商的模型清单
第 2 层  用户供应商规则 providerRules[]（provider_config.json）
         ├─ templateId：继承某个内置模板（预填协议 + baseUrl + 模型目录）
         └─ 覆盖：access（鉴权）、api（协议/baseUrl/自定义 headers）、enabled、顺序
第 3 层  用户模型规则（对第 1 层做增量覆盖）
         ├─ providerModelRules[]：智能配置 = 部分覆盖，缺省字段继承目录
         └─ manualProviderModelRules[]：手动配置 = 全量字段（目录没有的模型）
默认模型  defaultModelSelection = {providerId, modelId, options:{reasoningLevel}}
```

继承语义：**缺字段 = 继承目录默认；显式写入 = 固定覆盖**。上游目录升级不回写用户文件，用户覆盖始终优先。

### 2.2 关键字段（ZCode 原文，已核实）

**供应商规则**：`providerId`（唯一稳定 id）、`templateId`（继承模板）、`providerName`、`enabled`、`config.access{type: api-key | zhipu-coding-plan-api-key, apiKey, apiKeyManagementUrl}`、`config.api{type: openai-chat-completions | anthropic-messages | openai-responses, baseUrl, headers}`、`config.personalModelIds[]`（追加模型）、`config.modelOrder[]`、`config.visibility`、`config.logo`。

**模型规则**：`enabled`、`properties.contextWindow`、`properties.inputFormat{supportsText/Image/Video/Audio/Pdf}`、`properties.supportsToolCall / supportsJsonSchemaOutput / supportsNativeWebSearch / …`、`optionSpecs.maxOutputTokens{max, map}`、`optionSpecs.reasoningLevel{values, map}`。`map` 是把内部选项映射到各家 API 参数的表达式字符串（如 `{"max_tokens": maxOutputTokens}`、`{"reasoning_effort": reasoningLevel}`）。

**内置模板实例**（zcode-builtin.json 实测）：`zai-api`/`bigmodel-api`（anthropic-messages）、`zai-standard-api`/`bigmodel-standard-api`（openai-chat-completions）、`deepseek`、`minimax`、`moonshot-kimi`、`qwen-alibaba-model-studio-cn/intl`、`xiaomi-mimo`、`openai`、`anthropic`、`openrouter`、`opencode-*` 等 20 个。

### 2.3 抄什么、不抄什么

**直接抄（本需求范围）**：三层配置模型与继承语义、供应商模板预设、两级结构（供应商 ×多模型）、模型规则（目录继承式覆盖 + 手动全量）、`enabled` 启用禁用、`defaultModelSelection` 三元组默认模型、`apiKeyManagementUrl`、密钥只写不读回（我们已有）。

**明确不抄（非目标）**：`zhipu-account` OAuth 账号体系（我们是账号内自管 Key）、`openai-responses` 协议（消费方用不到）、`map` 表达式引擎（改为按 `api.type` 的**内置固定映射枚举**，见开发计划 §2.4）、多模态能力标记（`supportsImage` 等）只存目录元数据不做交互、logo/visibility/group 装饰性字段（保留 `logo` 思路的文字商标位，不建资源体系）、上游目录在线同步（目录随仓库版本更新）。

## 3. 需求（R 系列）

- **R1 两级结构**：模型配置改为「供应商 → 模型」两级。供应商持有鉴权与接入点（协议类型 + baseUrl + 可选自定义 headers + API Key + 超时 + 温度）；模型挂在供应商下，可多条。
- **R2 供应商模板**：新增供应商时先选内置模板（智谱 BigModel / DeepSeek / MiniMax / Kimi / 通义 / OpenAI 兼容自定义 / Anthropic 兼容自定义等），模板预填协议类型、baseUrl、密钥管理页 URL 与默认模型目录；也允许「自定义」从空白填写。baseUrl 允许在模板基础上覆盖。
- **R3 模型目录与继承**：内置目录随仓库分发（JSON 数据文件），提供各模板的已知模型清单及默认元数据：上下文窗口、最大输出、思考档位（reasoningLevel values，如 `disabled/low/medium/high`）。用户对目录模型的配置是**增量覆盖**（只改想改的字段），目录升级不丢用户配置。
- **R4 手动模型**：目录之外的模型可手动添加（全量必填：模型 id、上下文窗口、最大输出、思考档位）。手动条目与目录覆盖条目分开管理，同一 `(供应商, 模型)` 不得同时存在。
- **R5 启用/禁用**：供应商级与模型级均有 `enabled` 开关，禁用保留配置、不出现在选择列表，被消费方引用时按校验规则报错提示。
- **R6 默认模型三元组**：默认项从「默认配置」升级为 `{providerId, modelId, reasoningLevel?}`；删除供应商/禁用模型后的兜底规则明确（见开发计划 §2.5）。
- **R7 节点级模型选择**：函数编排的 Python（LLM 求值）与 LLM 计算节点、本体构建范围页，均可选到具体模型（供应商 → 模型级联 + 可选思考档位）；留空 = 跟随默认模型。旧节点只存 `providerId` 的绑定保持兼容（回退到该供应商默认模型）。
- **R8 连通测试**：沿用现有「已存配置 / 临时配置不落盘」两形态真实探测，粒度细化到（供应商 × 模型）。
- **R9 密钥安全**：沿用 AES-256-GCM + AAD（`namespace|owner|resource`）+ 库外根密钥 + 只写不读回（`keyConfigured` 标志）；迁移保持 `providerId` 不变使密钥**零重加密**。
- **R10 存量迁移**：现有 `wb_model_configs` 每行自动迁为「1 个供应商 + 1 个目录模式模型」（baseUrl 去掉 `/chat/completions` 尾缀推断），默认项、密钥、编排节点引用全部无损保留。

## 4. 数据与兼容约束

- 接口变更遵守《接口文档与前后端契约》：**先改 `文档/接口文档/04-编排与LLM接口.md` 与 `05` 速查表并登记变更记录，再改代码**；新端点进 `server.py` 白名单表。
- 存储变更走 Alembic 迁移（`workbench/migrations/`），程序化迁移，服务启动绝不隐式 DDL；真实库迁移用 CLI 演练后执行。
- 按 `owner_user_id` 完全隔离；跨账号按不存在处理。
- `wb_model_configs` 迁移后保留只读兼容读取一个过渡版本（或确认无旧实例后直接删除，以开发计划冻结为准）；`flows` 节点里的 `providerId` 引用校验错误码沿用 `LLM_PROVIDER_NOT_FOUND` / `LLM_PROVIDER_NOT_CONFIGURED`，新增模型级 `LLM_MODEL_NOT_FOUND`。
- `llm_client.py` 的 MiniMax 特判（温度下限 + reasoning_split）在 `openai-chat-completions` 协议下原样保留，避免存量行为变化。

## 5. 验收标准

1. 新增供应商：选「智谱 BigModel」模板 → 填 Key → 保存，供应商出现在列表且带目录模型清单，密钥不回传、库内密文。
2. 同一供应商下启用第二个模型不需要再填 Key；禁用某模型后节点选择列表不再出现，重新启用配置无损。
3. 手动添加目录外模型成功；与目录覆盖条目互斥（后端 400）。
4. 默认模型可精确到「供应商 × 模型 × 思考档位」；删除默认供应商后兜底规则符合开发计划 §2.5 并有明确 UI 提示。
5. 编排节点选具体模型执行成功；旧流程（仅 `providerId`）不改动仍可执行（回退供应商默认模型）。
6. 存量迁移演练：备份→迁移→校验，密钥可解密、节点引用不悬空、默认项等价。
7. 回归：`python3 tests/run.py`（quick/http/unit）全过；新增模型配置接口测试与迁移演练测试。
8. 前端 `npm run build` + `npm run typecheck` 通过；设置页、节点面板、构建范围页浏览器验收通过。
