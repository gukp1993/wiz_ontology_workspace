## 3. 技术设计约束（实施时按现有架构落实）

### 3.1 接口契约先行

新增能力语义应明确：
- 本体列表状态与元数据修订、名称修改、归档/恢复使用、受限删除。
- 指定版本只读读取（优先复用已有接口）。
- 两个比较端点标识（发布版本/草稿修订/恢复检查点），及完整差异响应。
- 恢复预检绑定sourceSnapshotId与targetDraftRevision，恢复提交带requestId，操作结果查询、检查点列表/读取。
- 发布变更审核依据与恢复来源，必须绑定当次草稿和比较基线。

端点名称不在本计划硬编码；T0按HTTP契约、GET/POST白名单约定确定。**不得在既有`/api/restore`里把release的ZIP字符串偷偷改为版本号**。兼容路径和新版本恢复路径职责分明。只读比较/查看不得隐式保存草稿。

预检响应不是可任意信任的客户端指令，提交仍由服务器重新验证归属、版本、修订和依赖。恢复目标引用稳定快照，不通过名称解析。

### 3.2 存储

新增元数据、归档状态和检查点记录采用现有SQLAlchemy Core/Alembic，禁止在线DDL、手写真实SQLite。字段与索引在T0/T3设计并登记，不要求另建一套仓库。

检查点与恢复草稿必须原子；不可先改head再尝试备份。requestId限定owner、asset、操作类型及请求内容，重复请求返回原结果，不接受不同目标复用。发布快照不UPDATE；恢复只追加草稿和操作记录。MySQL仍是预留，不因本改版声称已实测支持。

归档/改名也需并发令牌。可按现有资产修订能力选择独立元数据revision或受控统一revision，但必须保障旧编辑页在归档后不能写入。对归档本体读取旧版本不报不存在；跨账号访问仍按不存在处理。

### 3.3 前端

复用标准表格、抽屉、确认框、错误展示、表单守卫及唯一HTTP层。确认的缓存键应包含比较基线和内容指纹，不是全局boolean。CAS冲突不自动确认新的影响；结果未知保留requestId查询，不盲目重做。

历史只读展示不能复用当前草稿引用解析；可复用呈现组件，传入完整历史state。图谱改版不重新迁移编辑器或改视觉引擎，仅统一领域操作边界。已有视图坐标、搜索、布局等能力保持。

## 4. 验证矩阵

| 验证组 | 必须证明什么 |
|---|---|
| 领域操作 | 列表/图谱删除同一私有属性，在被旧契约引用时同样拒绝；共享定义被接口引用不能绕过；规则/动作有引用阻断；引用边移除和转私有不同且稳定ID正确 |
| 差异分类 | 仅名称、业务定义、类型、关联、未知扩展各一例；结构破坏不能人工降级；相同版本无差异；旧草稿确认失效 |

| 恢复存储 | SQLite发布→恢复，不依赖ZIP；原子故障注入；A→B→A旧revision拒绝；同requestId幂等；重复恢复检查点不覆盖 |
| 资产管理 | 归档后所有写入口拒绝，历史引用仍可读；改名不改稳定ID和旧发布；归档重名不释放；空本体删除并发新增引用/未知内容阻断 |
| UI闭环 | 未保存表单保存/放弃/取消；恢复前后比较；检查点查看/恢复；失败重试、409重预检、结果未知查询；1024/768焦点、滚动、按钮可达 |
