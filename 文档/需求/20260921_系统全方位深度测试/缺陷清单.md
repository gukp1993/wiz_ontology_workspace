## 按严重性排序

### 1. D-Q02-01 ｜P1｜新发现｜发布/恢复链路整体失效
在线发布不生成可恢复快照：`/api/publish` 只写 release 行不写 release-zip 附件，`GET /api/releases` 对新资产恒为 `[]`，前端「恢复快照」无可选项、`POST /api/restore` 成功路径不可达；接口文档 02 §2.3/§3.3 与 05 速查表仍把该能力标为可用。
复现：新建本体→save→publish 三个版本→GET /api/releases 恒空（证据 q02/o3o4o5-rules-publish.jsonl 行27）；错误路径 400/409 正常。修复建议：发布事务内生成 release-zip 或 restore 直读 release 快照；否则文档与前端同步降级。
注（Q03 语义澄清）：`/api/releases` 本义是 release-ZIP **工件**列表而非版本历史（版本历史是 `/api/versions`），publish 后为空"符合该端点自身语义"；缺陷定性不变——在线发布永不写工件 ⇒ 前端「恢复快照」恒空、`/api/restore` 成功路径对新资产不可达，而文档 02/05 把恢复能力标为可用。

### 2. A01 ｜P1｜基线已知（本轮证据升级）｜非法规则/动作选填字段进入不可变发布
规则 `content={"x":1}`、动作 v2 `effect=["a"]` 经真实 HTTP `validate(零错误)→save(200)→publish(200)` 全链路发布成功，非法值原样存入发布快照（版本 2.0.0 读回）。较基线验收（进程内函数级）证据更强。同族信号：validate 外层 catch 把内部构造异常压成泛化文案并丢弃具体错误。
证据：q02/o3o4o5-rules-publish.jsonl 行20/22。代码位置：`workbench/workflow.py`（str() 判型）等。
