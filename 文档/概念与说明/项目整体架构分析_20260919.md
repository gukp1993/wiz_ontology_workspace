# 项目整体架构分析 —— 本体建设与项目映射

日期：2026-09-19。本文基于当前代码与接口文档整理（commit 基线：`f6ef9f9` 之后的账号体系版本），字段描述以 `workbench/model_format.py`、`workbench/projects.py`、`frontend/src/project/bindingModel.ts` 与 `文档/接口文档/01-通用约定与数据模型.md` 为准。

## 1. 整体架构总览

### 1.1 技术底座

| 层 | 技术 | 说明 |
| --- | --- | --- |
| 前端 | Vue 3 + TypeScript + Vite，cytoscape（关系画布） | 无路由库，`view` ref + hash 导航；无状态库 |
| 后端 | Python 3 标准库 HTTP 服务 | 仅绑定 127.0.0.1:18765；HTTP 层只做安全边界 + 路由分派（`GET_ROUTES`/`POST_ROUTES` 白名单） |
| 存储 | SQLite（SQLAlchemy Core + Alembic） | 在线权威存储 `data/workbench.sqlite3`；MySQL 预留未实测 |
| 密钥 | AES-GCM（根密钥在库外 `keys/`） | 连接密码 / API 凭据 / LLM Key 只写不读回 |
| 鉴权 | Cookie 会话（`wiz_session`）+ PBKDF2 口令 | 数据按账号完全隔离（`owner_user_id`） |

### 1.2 三条独立数据线

系统核心设计是**双工作区、三条互不携带对方数据的状态线**，各自有独立的草稿、发布与并发令牌（revision）：

| 数据线 | 状态结构 | 保存接口 | 发布接口 | 发布形态 |
| --- | --- | --- | --- | --- |
| **本体区** | `OntologyState` | `/api/save` | `/api/publish` | 语义化版本（1.2.0）+ 变更分类 |
| **项目区** | `ProjectState` | `/api/project-save` | `/api/project-publish` | 递增版本（v1、v2…） |
| **编排区** | `FlowState` | `/api/flow-save` | 一期无发布 | 仅草稿 + 软删除 |

三者关系一句话：**本体定义"业务上有什么"（对象/属性/链接/规则/动作），项目映射回答"这些数据从哪来"（哪张表、哪个 Redis Key、哪个编排），编排是可复用的取值函数图。** 项目固定引用已发布本体版本，本体改草稿不影响项目，升级由项目主动发起。

### 1.3 存储与版本机制

- 编辑只写草稿（`wb_snapshots` 的 `purpose=draft` 行），发布产生不可变快照（`purpose=release`）；服务启动与请求路径绝不隐式建表/迁移/回退文件。
- revision 是不透明 token（`r-<uuid>`），与内容 hash 分离；保存走 CAS + generation 并发控制，旧 token 拒绝并返回 409 + `currentRevision`。
- 旧 `ontology/` 文件目录只作迁移输入与备份，**在线服务无文件回退**。

## 2. 本体是怎么建设的

### 2.1 建设流程（页面动线）

本体区按 6 个页面组织（左侧导航）：

```
工作概览 ──► 对象建模 ──► 共享属性库 ──► 业务规则 ──► 动作定义 ──► 本体校验与发布
   │            │
   │            ├─ 对象列表 / 关系画布（cytoscape，可建节点与连线）
   │            ├─ 对象详情：属性页签（从属性库添加 / 新增私有属性）、链接、动作、规则页签
   │            └─ 搜索 / 分页 / 收藏 / 排序
   ├─ 下载 Excel 模板 / 导入 Excel（批量填充）
   └─ 下一步建议（校验项按稳定 ID 结构化跳转「去处理」）
```

典型的建设顺序：

1. **新建本体**（空白开始，不复制任何已有内容）。
2. **建对象**：在「对象建模」中创建对象类型，填名称 + 业务定义；切换「关系画布」可以拖拽建节点、连对象间链接。
3. **建属性**：优先在「共享属性库」定义跨对象复用的属性（一处修改所有引用同步），再到对象详情里「从属性库添加」形成引用；也可以直接在对象下建私有属性（仅该对象可用）。
4. **建链接**：在对象或画布上建链接类型，指定起点/终点对象、显示名、基数（one-to-many 等）。
5. **建规则与动作**：业务规则（自然语言描述计算规则）进规则库；动作（做什么、什么效果）进动作定义库；都在对象详情页签里与对象挂接（仅挂接，不复制定义）。
6. **校验与发布**：发布前强制校验；`contracts.classify` 自动把变更分为 initial / compatible / breaking / pending——破坏性变更强制升大版本，引用失效禁止人工标为兼容。发布产生不可变版本快照，供项目引用。

配套机制：

- **保存直通**：前端 `saveCoordinator.ts` 每区一个串行保存队列，编辑即自动保存（900ms touch 合并），409 冲突自动换基线重试；重要表单走 `commit-now` 立即持久化。顶栏没有保存按钮，只有五态状态条。
- **Excel 批量导入**（20260917 需求）：工作概览下载四表模板（对象/属性/规则/动作），填业务内容即可，不要求填编号、ID 或关系；上传后检查 → 预览（新增/跳过/自动重命名/问题）→ 一次合入草稿。同名策略可选「跳过」或「保留并自动重命名（随机六位后缀）」。**不自动建立对象—属性、对象—规则、对象—动作关系，也不生成对象间链接**——模板没有关系信息，不能靠同名推断。
- **计算契约不在主流程**：`workflow.functions`（guide_version=3 契约）已移出本体基础建设流程，只在「更多工具」维护；不得要求业务专家先建计算契约。

### 2.2 本体的数据模型（双形态）

接口边界上本体是 **JSON schema 形态**（自有格式，非 Foundry 导入格式）；后端 `model_format.decode_state` 解码为内部 **JSON-LD（`@graph`）** 处理，`encode_state` 再编码回 schema 形态。前端有镜像的协议层 `frontend/src/ontology/modelFormat.ts`（**两处必须同步改**）。

```jsonc
{
  "workspaceId": "storage",
  "ontology": {
    "schemaVersion": 1,
    "namespaces": { "mg": "https://example.com/microgrid/", "owl": "...", "rdfs": "...", "xsd": "..." },
    "objectTypes": [],        // 对象类型      → owl:Class
    "linkTypes": [],          // 链接类型      → owl:ObjectProperty
    "properties": [],         // 对象属性      → owl:DatatypeProperty
    "sharedProperties": [],   // 共享属性      → mg:SharedProperty
    "valueTypes": [],         // 值类型        → mg:ValueType（历史保留，常为空）
    "metadata": [],           // 其他资源（带 resourceType）
    "definitionOrder": ["<稳定 id>", "..."],  // 必须完整列出每个定义 id，顺序即定义顺序
    "extensions": {}          // 未识别字段一律放这里，零丢失
  },
  "workflow": { "objective", "functions", "actions", "interfaces", "release",
                "businessRules", "actionAssociations", "businessRuleAssociations" },
  "metrics": { "metrics": [] },
  "rules":   { "rules": [] },      // 旧格式兼容文件，允许为空
  "layout":  { "positions": {}, "zoom": 1, "pan": { "x": 0, "y": 0 } }
}
```

关键约束：

- 所有引用（契约签名、属性来源、关联）一律用**稳定 id**（如 `mg:object_xxx`、`mg:p_xxx`），改显示名不断链；手写数据勿自造 id。
- 直接改 schema 形态 JSON 必须同步维护 `definitionOrder`，否则保存报错。
- 空 `metrics`/`rules` 不写入发布快照。

### 2.3 稳定 ID 体系

| 定义 | id 形态 | 示例 |
| --- | --- | --- |
| 对象类型 | `mg:object_<32hex>` | `mg:object_06e387145e154b3a876bc050ba70be13` |
| 共享/对象属性 | `mg:p_<32hex>` | `mg:p_e04bf9aa560c4cc1a81dbe9c6c2113d0` |
| 链接类型 | `mg:link_<32hex>` | `mg:link_23f7280b9b044793a60980a32be20d49` |
| 业务规则 | `rule_<32hex>` | `rule_36a8a327...` |
| 动作 | `action_<32hex>` | `action_62df7a2c...` |

## 3. 本体描述字段（逐组）

以下字段名是 **schema 形态**（接口边界/存储）的字段；括号内是 JSON-LD 内部对应（`model_format.py` 的 FIELDS/REFS/JSON_FIELDS 映射）。

### 3.1 objectTypes（对象类型）

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id`（@id） | ✓ | 稳定 id，`mg:object_*` |
| `displayName`（rdfs:label） | ✓ | 显示名，如「储能设备」 |
| `description`（rdfs:comment） | ✓ | 业务定义 |
| `aliases`（mg:aliases） | — | 别名数组；**只适用于对象类型** |
| `extensions` | — | 未建模字段的兜底存放处 |

### 3.2 linkTypes（链接类型）

| 字段 | 说明 |
| --- | --- |
| `id` | 稳定 id，`mg:link_*` |
| `displayName` | 链接显示名（正向），如「所属于」 |
| `reverseDisplayName`（mg:reverseLabel） | 反向显示名，如「拥有充放电计划」 |
| `description` | 业务定义 |
| `cardinality`（mg:cardinality） | 基数：`one-to-one` / `one-to-many` / `many-to-one` / `many-to-many` |
| `sourceObjectTypeId` | 起点对象稳定 id（rdfs:domain） |
| `targetObjectTypeId` | 终点对象稳定 id（rdfs:range） |

### 3.3 sharedProperties（共享属性，共享属性库）

| 字段 | 说明 |
| --- | --- |
| `id` | 稳定 id，`mg:p_*` |
| `displayName` | 属性名，如「额定功率」 |
| `description` | 业务定义 |
| `dataType` | 数据类型描述，见 3.5 |
| `valueSuffix`（mg:valueSuffix） | 单位后缀，如 `kWh` |
| `visibility`（mg:visibility） | `normal`（其他取值历史兼容） |
| `formatting`（mg:formatting） | 显示格式：`{mode:"natural", instruction:"单位是kW", maxDecimals?...}`；自然语言原文保存，不调用 LLM |

### 3.4 properties（对象属性）

对象属性是「对象 ↔ 属性定义」的挂接记录，两种形态：

- **引用共享属性**（推荐）：`{ id, objectTypeId, sharedPropertyId }`——名称/类型/单位随共享定义统一维护。
- **对象私有属性**：完整定义内联在记录上——`{ id, objectTypeId, displayName, description, dataType, apiName, valueSuffix, visibility, formatting }`。

| 字段 | 说明 |
| --- | --- |
| `id` | 稳定 id，`mg:p_*`（与共享属性同一命名空间） |
| `objectTypeId` | 所属对象（rdfs:domain） |
| `sharedPropertyId`（mg:sharedProperty） | 引用的共享属性 id（REFS 映射） |
| `apiName`（mg:apiName） | 属性 API 名；缺省取 id 去前缀；项目映射用 apiName 定位属性 |
| `isDisplayName`（mg:isDisplayName） | 标记该属性是对象的「实例显示名称」；项目层 `derive_display_names` 按此自动推导 `title_key` |
| 其余 | 同共享属性（displayName/description/dataType/valueSuffix/visibility/formatting） |

### 3.5 dataType（数据类型描述）

属性统一按数据类型描述，普通值与时间序列共用一个 `dataType` 对象：

| 形态 | dataType | 说明 |
| --- | --- | --- |
| 普通 | `{"type": "string\|double\|boolean\|dateTime\|array\|struct"}` | 文本/数值/是与否/时间/数组/结构体 |
| 时间序列 | `{"type": "timeSeries", "valueType": "string\|double\|decimal\|integer\|boolean\|date\|dateTime"}` | 观测值类型必填；**只适用于属性组** |

旧 `valueShape` 字段仅兼容读取（`scalar`/`timeSeries`），新写入一律用 `dataType`；普通值↔序列的类型变化按破坏性变更处理。共享属性改数据类型会沿引用传播。

### 3.6 workflow（工作流区）

| 子结构 | 字段 | 说明 |
| --- | --- | --- |
| `objective` | `name / scope / question / acceptance` | 本体目标（name 即本体名，顶栏面包屑同源） |
| `businessRules[]` | `id / name / description / content / output` | 业务规则：名称、业务定义、规则内容（自然语言）、输出结果 |
| `actions[]`（V2） | `id / name / description / effect / definitionVersion:2 / status` | 动作：名称、业务定义、业务效果；`status` 如 `experimental`。旧 V1 历史动作只读展示，可转新格式编辑 |
| `functions[]`（契约，guide_version=3） | `id / name / description / guide_version / status / no_inputs / conventions / applicable_objects / inputs[] / outputs[]` | 计算契约：输入/输出为结构化签名 `{id, name, description, ref:{kind:"object"\|"property"\|"base", id}}`；由 `contracts.signature_errors` 校验 |
| `actionAssociations[]` | `{actionId, objectTypeId}` | 动作 ↔ 对象挂接 |
| `businessRuleAssociations[]` | `{ruleId, objectTypeId}` | 规则 ↔ 对象挂接 |
| `release` | `note / reviewer` | 发布备注 |
| `interfaces[]` | — | 接口声明（当前常为空） |

## 4. 项目映射是怎么做的

### 4.1 项目与本体的引用关系

每个项目在 `project` 块记录引用的本体与版本：

```jsonc
{ "project_id": "9803ea198cbc", "name": "创智园二期",
  "ontology": "0d12b233-...", "ontology_version": "3.2.0" }
```

- 项目**只引用已发布本体版本**，不跟本体草稿走；`ReferenceNotice` 只读比较「项目引用版本 / 本体已保存草稿 / 最新发布版本」三者差异，不自动升级。
- 本体发新版本后，项目发起升级时出 `UpgradeReport`（影响面 + 阻断项）；破坏性变更到映射层会被阻断。

### 4.2 映射流程（项目区 5 个页面）

```
项目概览 ──► 数据连接 ──► 对象映射 ──► 计算实现（属性取值规则） ──► 项目校验与发布
                │              │
                │              ├─ 对象 → 实例身份（连接+表+主键，或项目登记实例）
                │              ├─ 属性 → 取值来源（身份表字段/数据库直选/Redis/编排/规则/聚合…）
                │              └─ 链接 → 两端字段关联 或 成员规则
                └─ 连接探测（真实网络探测，永不持全局写锁；密码进 vault 永不回传）
```

1. **数据连接**：登记 MySQL / Redis 连接（ConnectionConfig）；密码单独走 `/api/connection-secret` 写受保护 vault，永不进配置/快照/日志。连接可刷新**表结构目录**（catalogs，服务端缓存，可达数 MB，前端出站请求必须剥除）。
2. **对象映射**：为每个要落地的本体对象建一条 object_binding——先定实例身份（对象实例从哪来），再逐属性配取值来源，再配链接。
3. **计算实现**：维护命名取值规则（queryRule）与计算函数实现，供属性来源引用。
4. **校验与发布**：服务端全量校验出 `ValidationReport`（errors/warnings + 结构化 items，页面「去处理」按 kind/id 跳转）；发布形成项目版本快照。

### 4.3 对象实例身份（两种模式）

| 模式 | 存储 | 说明 |
| --- | --- | --- |
| **数据库身份**（默认/旧） | binding 顶层 `connection` + `table` + `primary_key` | 对象实例 = 身份表的行；普通属性直接写字段名字符串即可 |
| **项目登记身份**（registered） | `identity: {kind:"registered", instances:[{id,label}]}` | 无表对象：实例在项目里手工登记（id + 显示名称）；校验/执行按登记实例走。切回数据库身份前会检查登记属性/聚合/membership 的依赖 |

### 4.4 属性取值来源（`properties[apiName]`，kind 全集）

每个已映射属性挂一个来源对象，以 `kind` 区分。**字符串是身份表字段直接映射**（演示引擎只认它）：

| kind | 结构要点 | 典型用途 |
| --- | --- | --- |
| （字符串） | `"capacity"` | 身份表本行字段直取 |
| `field` | `{source, field, selection?, timeField?, tieBreaker?, missing?}` | 补充来源表的字段（多表 JOIN 语义：来源表按 matchLeft=matchRight 与身份表匹配）；selection 支持 latest/sum/average |
| `database` | `{connection, table, lookup:{match[], timeRange?}, result:{valueField, timestampField?…}}` | **数据库直选表**：任意表 + 多条件 AND（至少一条绑定当前实例）+ 可选时间范围；时间序列目标必配时间字段与时间戳编码。等价于身份表直取的极简配置会**压缩回字符串** |
| `redis` | `{command:GET\|HGET, key, params:{token→{from:primary\|property\|identityField}}, hashField?, conversion, missing}` | Redis 直连；key 模板占位符 `{token}` 逐个绑参；`connection`（直连）与 `source`（登记来源）互斥 |
| `computed` | 三种子形态：规则引用 `{implementation, output}`；内联 SQL `{mode:"inlineSql", inlineSql:{version,connection,sql,params}}`；计算函数 `{mode:"calcFunction", implementation, output, inputs}` | 引用计算实现；时间序列目标要求实现声明 `output='series'` |
| `flow` | `{flow, output, inputs:{编排输入id→{from:property\|constant\|instanceId}}}` | **函数编排取值**（2026-09-18 新增，新建统一走它）：只存编排 id + 输出 + 输入绑定，不复制编排；类型相容表前后端镜像校验；循环依赖阻断 |
| `registered` | `{field:"id"\|"label"}` | 登记信息：实例编号 / 显示名称 |
| `aggregate` | `{relation, property, operator:"sum", empty:"null", missing:"incomplete", inputUnitConfirmed}` | 关联聚合：对某链接成员集合的属性求和（本期仅 SUM）；成员由 membership 规则定位 |
| `unknown` | — | 未识别结构原样保留（零丢失），绝不当 computed 重存 |

旧格式（`related_sources`、`{kind:'related'}`、纯 `column` 链接）由 `bindingModel.ts` / `projects._sources_of` 内存适配，**保存即迁移出旧格式**。

### 4.5 链接映射（`relations[]`，三种形态）

| 形态 | 结构 | 说明 |
| --- | --- | --- |
| 表字段关联（新） | `{relation, target_type, sourceId, field, targetSourceId, targetField}` | 用两端来源表的字段对（sourceId 空串 = 身份表）实现链接 |
| 旧 column 关联 | `{relation, target_type, column}` | legacy 标记，保存时整体写新格式 |
| membership 成员规则 | `{kind:"membership", relation, target_type, rules:[{sourceInstance, scope:"filtered"\|"all", conditions:[{field, operator:eq/ne/in/isnull/notnull, value?}]}]}` | 无表对象按条件选成员；配合 aggregate 做关联求和；条件值支持属性/常量/参数 |

### 4.6 表单状态机与并发

- 技术字段（连接/表/主键）变更即失效旧表单响应：靠 **generation 计数**防旧响应覆盖新表单（仅改名不失效）。
- 保存走项目区独立 Saver（串行队列 + revision CAS）；`catalogs` 由 `project/api.ts` 的 `stripCatalogs`（全前端唯一实现点）出站剥除，避免污染草稿哈希。

## 5. 项目映射描述字段（逐组）

### 5.1 ProjectState 顶层

```jsonc
{
  "project": { "project_id", "name", "ontology", "ontology_version" },
  "connections": { "connections": [ /* ConnectionConfig */ ] },
  "bindings": {
    "notice": "",                  // 引用提示（ReferenceNotice）
    "object_bindings": [],         // 对象映射（核心）
    "observation_binding": {},     // 观测绑定（历史结构，保留）
    "source_candidates": [],       // 来源候选（历史结构，保留）
    "actionBindings": [],          // 动作绑定（保留结构）
    "catalogs": {}                 // 【服务端派生】表结构目录缓存，请求必须剥除
  },
  "implementations": { "implementations": [] },  // 计算实现清单
  "parameters": {}                               // 项目参数（供来源引用）
}
```

### 5.2 ConnectionConfig（数据连接）

| 字段 | 说明 |
| --- | --- |
| `id` / `name` | `conn-*` 稳定 id / 显示名 |
| `engine` | `mysql` / `redis` |
| `host` / `port` / `username` | 地址三元组 |
| `database` | MySQL 库名（必填）；Redis 用 `dbIndex` |
| `tls` / `caPath` | `none` / `encrypted` / `verify` |
| `password` | **永不在配置中出现**——只经 `/api/connection-secret` 写 vault，永不回传 |

### 5.3 object_bindings[]（对象映射，核心）

以真实项目「创智园二期」的绑定为例：

```jsonc
{
  "object_type": "object_06e387145e154b3a876bc050ba70be13",  // 本体对象稳定 id（去 mg: 前缀）
  "connection": "conn-6e4bedfe447e",   // 身份连接（数据库身份模式）
  "table": "m_storage_phase",          // 身份表
  "primary_key": "id",                 // 实例主键字段
  "title_key": "name",                 // 实例显示名称字段（由本体 isDisplayName 自动推导）
  "properties": {                      // 属性来源表，键 = 本体属性 apiName
    "p_b8f26c60...": "rated_power",                                   // 字符串 = 身份表字段
    "p_5f38b7d7...": { "kind": "redis", "command": "GET",
                       "key": "m_storage_phase-{id}-ptotal", ... },   // 对象 = 结构化来源
    "p_2607cb5b...": { "implementation": "cf-4a39...", "inputs": {...} }  // 规则/函数引用
  },
  "relations": [],                     // 链接映射（见 4.5）
  "sources": [],                       // 补充数据来源（DbSource/RedisSource）
  "identity": { "kind": "registered", "instances": [{"id","label"}] }  // 可选：登记身份
}
```

补充来源 `sources[]`：

| kind | 字段 | 说明 |
| --- | --- | --- |
| `db` | `{id, name, connection, table, matchLeft, matchRight, cardinality:"one"\|"many"}` | 补充表，按 matchLeft（来源表字段）= matchRight（身份表字段）关联；cardinality=many 的来源不能给链接端点供字段 |
| `redis` | `{id, name, connection}` | 登记的 Redis 来源（供属性 redis 来源引用） |

### 5.4 implementations[]（计算实现）

| kind | 版本 | 关键字段 | 说明 |
| --- | --- | --- | --- |
| `calculationFunction` | — | `id / inputs / output / outputDeclarations / contract 引用` | 计算函数实现；输入/输出按契约稳定 id 对齐；`outputDeclarations[].valueShape` 旧声明兼容读取 |
| `queryRule` | `schemaVersion:1` | `contractId` + 适用对象 | 旧版：绑定计算契约的取值规则（兼容保留） |
| `queryRule` | `schemaVersion:2` | `inputs.model_name / attr_name / model_id:"{id}"` + `connection` + 流程 | 通用规则：无适用对象，按对象表名/属性名/实例主键定位；`model_id` 必须是 `{id}` |
| `queryRule` | `schemaVersion:3` | `mode:"sqlTemplate"` 或步骤结构 | SQL 模板/步骤代 |
| `queryRule` | `schemaVersion:4` | `steps[]` + `result` | SQL 步骤：多步动态表/字段定位，前序输出引用必须指向已执行的唯一记录步骤；仅配置/校验，不执行真实 SQL |

规则校验在 `workbench/query_rules.py`；参数引用统一用 `{{inputs.xxx}}` / `{{steps.<id>.<out>}}` 模板语法。

### 5.5 校验报告与版本

```jsonc
// ValidationReport（/api/project-validate / publish）
{ "errors": ["阻断发布"], "warnings": ["提示"],
  "items": [ { "kind": "connection|objectBinding|propertySource|implementation|linkMapping|reference",
               "id": "<稳定id>", "name": "<显示名>", "status": "...", "issues": ["..."] } ] }
```

关键校验语义：已启用对象缺身份来源（connection/table/primary_key）**阻止发布但允许保存草稿**；校验失败不得假成功（不写 200 空数据）；409 冲突带 `currentRevision`。项目发布引用本体已发布版本，升级需显式走升级流程（`UpgradeReport` 出影响面）。

## 7. 一页总结

- **本体区**回答"业务模型是什么"：对象（`objectTypes`）挂属性（引用 `sharedProperties` 或私有 `properties`）、对象间连链接（`linkTypes`）、配业务规则与动作（`workflow.businessRules/actions`）。字段围绕「稳定 id + 显示名 + 业务定义 + 数据类型」；发布按语义化版本且不可变。
- **项目区**回答"数据从哪来"：项目固定引用本体已发布版本，为每个对象配实例身份（数据库表或登记实例），逐属性配来源（字段/直选表/Redis/编排/规则/聚合），逐链接配字段对或成员规则。字段围绕「连接 + 表 + 字段 + 来源 kind」；发布为递增版本。
- **两区之间只有引用**：对象用 `object_type` 稳定 id、属性用 `apiName`/稳定 id、链接用 `relation` 稳定 id——本体改显示名不断链，改结构按变更分类管控升级。
