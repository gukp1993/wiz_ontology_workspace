## 1. 业务规则的定义

业务规则描述在特定业务情境下，使用哪些信息、遵循哪些条件与逻辑，形成什么计算结果、判定或建议。允许以自然语言承载复杂知识，不限定为公式或程序。规则定义不等于可执行函数，也不等于动作执行授权。

这是本工作台拟新增的业务知识定义，并非 Palantir 官方同名资源类型。通用规则不包含连接地址、表字段、Redis Key、现场固定设备数量；这些放项目绑定。

## 2. 建议填写字段

| 字段 | 是否必填 | 填写指导 |
|---|---|---|
| 名称 | 必填 | 用业务名称表达，例如“储能运行异常判定”。 |
| 业务定义 | 必填 | 一两句话说明解决什么问题及边界。 |
| 规则内容 | 必填 | 自然语言写步骤、条件、公式、例外、缺失处理；不强制拆成代码或决策表。 |
| 输出结果 | 必填 | 说明最后提供哪些值、结论、解释或建议；首版可用文本，不要求编程类型。 |
| 适用对象 | 按需 | 选择一个或多个对象类型；通用取数/匹配规则可不绑定特定对象。 |
| 所需信息 | 按需；有输入时填写 | 列出所需属性、时间、指令、事件或外部数据；已有属性优先引用，没有的先写业务说明，不必为每个中间量建属性。 |
| 依赖规则 | 按需 | 引用已有规则并说明用途；区分参考口径、读取结果、前置核验、反馈，不等同执行编排。 |
| 可配置参数 | 按需 | 阈值、时间窗口等；建议记录参数名、含义、单位、默认值和是否允许项目覆盖。没有确认默认值则留空标待确认。 |

维护职责：业务专家负责定义与口径，开发/实施负责项目数据来源、参数绑定和实现。稳定ID、版本、修订记录由系统管理。分类仅作为可选标签，不新增多个规则编辑器；案例、来源依据可后续补充。

交互建议：必填字段直接展示；适用对象、所需信息、依赖和参数放“补充配置”折叠区。允许保存未完成草稿；正式发布时检查必填与已登记引用，不将自然语言中的每句话假定为机器可执行条件。
