## 一、我们的方向与现状

**定位**：单用户本地本体工作台。自动化构建是"从物料（DDL/数据字典/业务说明/代码）生成可编辑本体草稿"的能力，交付物是三件套（本体草稿 + 证据链 + 未决问题清单），后两者是草稿的随行说明，作用域限于生成任务内。不自动追加既有本体、不碰项目映射、不自动发布。

**方案叙事（已收敛，建议置于收尾文档开头）**：能力已建、治理待补、以试点物料组合验证后放量。

**能力基线（main 已合并实现，源码核实）**：

| 能力 | 状态 | 证据 |
|---|---|---|
| 物料解析 | 全物料线已实现：DDL/代码/Markdown/文本/PDF/Word/Excel | `workbench/ontology_build/parsers/`（code.py、ddl.py 等 8 个） |
| 候选生成 | 五类候选（对象/属性/链接/规则/动作）+ LLM 参与生成 | `protocol.py:69`、`llm.py` |
| 审核与晋升 | 候选带任务内 id、人工决定（纳入/暂缓/排除）、证据分组、原子交付 | `review.py`、`alignment.py`、`delivery.py` |
| 交付安全 | 幂等（requestId+内容指纹）、一任务一交付、同名不覆盖、只建新草稿、事务原子 | `delivery.py:232-307`、`ontology_build_routes.py:702-713` |
| 未实现（治理层） | 物料哈希口径机制、确认失效机制、业务方确认留痕、缺口标注、来源枚举、按物料语义路由 | 全模块 grep 无对应实现 |

## 五、下一轮讨论方向（建议议程）

**总判断：方案讨论阶段应结束，重心转向"一个裁决 + 一套试点"。** 四轮会议的边际产出已递减（46→47 已在讨论"怎么核对"的元问题），建议下一轮以本文档为唯一输入，拍完 A/B/C 三类即产出收尾文档（D1/D2 本侧执行），关闭本条讨论线，转入试点执行。

**议题 1（唯一业务裁决）：哈希口径与确认失效（A1+A2）**
讨论输入已齐：判据把技术问题翻译成了业务二选一——"业务方确认的到底是表结构（语义）还是这份文件（原文）"；回放方案给出上下界，拍板后跑回放拿量级佐证，白名单细则留给实现。需要拍：绑定口径 + 是否接受一期整文件回退折中。

**议题 2：试点验证设计（B1+B2+B3）**
需要拍：物料组合清单与业务方确认方式、指标矩阵与滞留窗口定义、放量触发条件（验证域句式）。提示：试点是"验证已建成能力在真实物料上的表现"，不是开发前置——不要让它膨胀成新一轮方案设计。

**议题 3：增量需求排序（C1–C5）**
建议顺序：留痕 → 哈希机制 → 确认失效 → 路由。核心理由：留痕是所有二期触发信号的数据地基，晚一天上线就少一天数据；路由在 LLM 自然分布下不紧迫，等试点矩阵数据说话。需要拍：是否按此顺序立项（立项后按需求归档规则建 `文档/需求/` 条目、走 worktree 开发）。

**议题 4：收尾与固化（D 类）**
无需讨论，确认执行方式即可：收尾文档与两条补记由本侧产出；断言挂测试集走 worktree 授权。
