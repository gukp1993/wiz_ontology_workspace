## 一、整体判断

**这份记录适合作为讨论素材，不建议直接作为开发依据。**

“候选生成、证据追溯、人工确认”的主线正确，但后续讨论出现了目标偏移、概念混淆和不必要的流程扩张。其中一些已经达成“AI 共识”的内容，实际需要纠正。

建议保留我们现有“从物料自动构建本体”需求作为主线，吸收本次讨论的证据追溯和审核细节，不直接替换成数据库导入、口径回填和审批治理方案。

## 二、主要偏差：逐渐偏离自动化构建目标

用户希望从代码、文档、数据库结构等资料中理解业务，辅助生成本体定义。

讨论最后收敛成：首期读取数据库结构，暂不使用 LLM，生成对象、属性、链接候选，再让业务专家补定义。

这更接近**数据库结构导入与人工审核工具**。它能够验证入库流程，却难以验证自动化建模的核心价值：理解业务、减少填写、识别数据库中没有直接表达的概念。

| 储能场景 | 仅依赖数据库结构的不足 |
|---|---|
| capacity 字段 | 未必能判断是额定容量、可用容量还是剩余电量 |
| 无对应表的储能系统 | 容易遗漏具有独立业务含义的虚拟聚合对象 |
| 设备 SOC 加权计算 | 通常需要代码或业务说明才能还原计算口径 |
| 停止充放电 | 需要业务操作依据，不能直接从表结构推导 |

可以缩小首期范围，但建议按业务场景缩小，而不是把业务理解能力全部推迟。数据库结构导入可以作为一个技术验证切片，不能替代最终产品闭环。

## 三、值得保留的建议

| 建议 | 保留理由 |
|---|---|
| 物料解析与业务抽象分开 | 解析出表、字段、方法，不等于识别出了业务对象和动作 |
| 先生成候选，再由用户确认 | 避免模型结果直接污染正式本体 |
| 一条候选关联多处证据 | 同一个概念可能需要文档、代码和表结构共同解释 |
| 相似度只推荐，不自动合并 | 同名或相近名称不代表业务口径相同 |
| 保存物料版本及人工修改记录 | 重新生成时可以识别变化，并保护人工成果 |
| 正式保存复用现有协议、校验和并发控制 | 避免出现第二套本体数据规则 |

这些方向与现有需求基本一致，可以补强细节。

## 四、形成正式方案前必须纠正的问题

| 编号 | 讨论中的建议 | 问题 | 建议调整 |
|---|---|---|---|
| R01 | 数据类型不进入审核判断 | 数值 SOC 与时间序列 SOC 不应忽略类型后合并 | 数据库类型不能单独决定业务类型，但候选业务类型必须参与兼容检查和审核 |
| R02 | 候选不能包含任何 ID | 链接引用、合并、撤销、再生成、日志均需定位候选；记录后面又提出“按候选 ID 查日志” | 区分任务内 candidateId 与正式本体 ID，保存时建立映射 |
| R03 | 缺少业务定义时填“待确认”字符串 | 内容与状态混杂，容易形成看似满足必填的假定义 | 候选定义可以暂空，另设材料不足／待确认状态；正式保存前处理必填缺口 |
| R04 | AI 生成定义不能以“已确认”状态出现 | 用户审核接受后，应允许成为已确认定义 | 分开记录生成来源与审核状态，AI 生成不等于永远不能确认 |
| R05 | 建模证据与项目数据来源“是同一件事” | 文档支持属性含义，不代表它能提供某台设备的属性值 | 证据说明“为什么这样建模”；映射说明“这个项目如何取值”，可以关联但不能合并职责 |
| R06 | 对齐后的属性优先成为共享属性 | 多份材料提到同一属性，只能说明证据可以合并，不代表应该跨对象共享 | 默认保留对象归属，语义、类型、口径一致时再建议共享 |
| R07 | 把口径回填建成 Action Type | 把工作台编辑操作混入用户的领域本体 | 使用普通审核、编辑操作并记录操作者，不必向储能本体增加动作 |
| R08 | 所有候选都必须有原文证据 | 用户可能补充材料未表达、但明确成立的业务知识 | 接受原文依据或明确的人工补充说明，区分来源，不伪造原文 |
| R09 | 同源同名默认关联已有对象 | 简单 Excel 模板没有来源标识；同名不能证明是同一概念 | 不改既有同名策略；未来辅助合并需单独设计并由用户确认 |
| R10 | 前端保存队列和错峰操作保证批次安全 | 单个页面的队列无法协调其他页面或后台任务 | 依靠服务端版本检查、事务和幂等；错峰只能作为辅助安排 |

优先修正 R01、R02、R03、R05，即类型参与审核、候选标识、内容与状态分离、证据与映射分离。

### 4.1 数据类型参与审核的正确边界

“不让物理类型决定业务含义”是合理原则，“审核过程不看类型”不是。

例如数据库 tinyint 字段不能未经判断就映射为布尔属性，但在候选已提出数值、布尔两种解释时，审核必须看见并解决该分歧。正式写入时也必须检查类型是否合法、与被共享定义是否兼容。

### 4.2 候选身份与正式定义身份分开

候选在任务内部需要稳定身份，否则名称修改、候选合并或重新生成后，无法可靠关联证据、链接端点和用户决定。

正式本体 ID 由受控保存机制分配，不由模型随意创造。两者不冲突，不能用“正式 ID 在保存时分配”推导出“候选不允许有 ID”。

### 4.3 审核状态与保存状态分开

保存失败不应撤销用户已经完成的审核决定。候选是否被接受，与选定集合是否成功创建本体，是不同状态。

同样，明确失败后的重新提交与结果不明时的网络重试需要区别处理。幂等请求身份不能在每次重试时随意改变，否则可能重复创建资产。

## 五、建议简化或暂缓的设计

讨论不断增加授权业务方及角色、定期推送、超期降权和归档、口径回填 Action、元素级 draft→active、数据画像和值交集率、各种占位字段。

这些并非全无价值，但当前本地建模工作台尚未明确需要多人审批运营体系。首期更需要让用户拿到一份可编辑、有依据的本体初稿。

| 内容 | 建议 |
|---|---|
| 审核记录 | 保留，记录实际操作者与决定，不等于新增角色审批体系 |
| 定期推送、超期治理 | 暂缓，不作为首期建模闭环前提 |
| 元素级 draft→active | 优先复用现有本体草稿与发布机制，不再增加一套生效流程 |
| 业务数据库抽样画像 | 不作为默认前置；首期读取 DDL、数据字典文件即可，真实数据接入另定范围 |
| 注释缺失阻止生成 | 不建议，允许其他材料补充依据并显示覆盖缺口 |
| 过程元数据全部放 extensions | 不建议，证据和任务状态主要由生成任务管理，不把 extensions 当杂项容器 |
| 将数据不完整表排除在建模之外 | 不应机械处理；数据质量差不代表相关业务概念没有建模价值 |

候选缺信息可以暂缓，但不能因为某个输入来源较弱，就忽略其他来源能提供的业务依据。

## 六、建议采用的首期闭环

### 6.1 选择小而完整的储能场景

覆盖储能设备与储能簇，包括额定容量、SOC、所属关系、SOC 计算规则和停止充放电动作。

首批物料可以限定为：

- 一份业务说明；
- 一份 DDL 或数据字典；
- 一小段相关代码。

不需要首期支持所有文档格式和整个代码仓库，但应保留跨材料理解能力。

### 6.2 用户流程

```text
添加物料
  → 确认本次建模范围
  → 解析并定位证据
  → LLM 生成五类定义及关联候选
  → 检查类型、引用、冲突和证据支持情况
  → 用户编辑、纳入或暂缓
  → 原子保存为新本体草稿
```

五类定义指对象、属性、链接、业务规则、动作。按材料实际支持情况生成，没有动作依据就不生成动作，不为凑齐类型补造内容。

该建议沿用现有“只创建新本体草稿”的边界，不扩展为自动追加已有本体、修改项目映射或自动发布。

### 6.3 用户最终获得什么

**一份可继续编辑的本体草稿，以及对应的来源依据和未决问题。**

候选池、证据库、日志是支撑这个交付的内部机制。讨论中“本体本身不是交付物”的表述不适合我们的产品目标，应调整。

### 6.4 怎样判断真正有价值

“有证据”不等于“生成正确”。候选引用了一段源码，仍可能误读其含义。

评审不能只检查证据字段非空或状态流转测试通过，还应使用人工核对样本检查：

- 关键业务概念是否遗漏，例如没有对应表的储能系统。
- 属性含义、数据类型、链接端点和数量关系是否正确。
- 引用片段是否真正支持生成结论。
- 同名不同义是否错误合并。
- 规则是否丢失单位、过滤条件、缺失值或时间口径。
- 用户完成一份可用初稿的修改量和耗时是否下降。

不预设未经样本验证的准确率，也不以生成节点数量代替质量。

## 七、讨论记录本身的可信度问题

记录多次出现“没有分歧”“完整闭环”“只需加一条断言”，但缺少真实业务样例的反向检验。

| 观察 | 对评审的影响 |
|---|---|
| 一方面禁止候选 ID，另一方面按候选 ID 查日志 | 说明形成共识并未消除内部矛盾 |
| 要求业务定义，却把定义文本排除在审核判断外 | 窄接口设计没有覆盖真实业务判定条件 |
| 从“规则内容、预期效果选填”推导“业务定义可待确认占位” | 混淆了不同字段的填写要求 |
| 摘要称全程无截断，末尾标注 orchestrator · truncated | 纪要完整性说明不可靠，应以实际导出记录为准 |
| 名为 palantir 的模型角色发表意见 | 不能据此认定为 Palantir 官方方法或产品事实 |
| 依赖核实用 skip 占位 | 可以记录未验证项，但不能把跳过测试作为闭环通过证据 |
| 反复声称增加字段和断言成本可忽略 | 没有覆盖存储、状态迁移、交互、权限与异常处理的实际成本 |

## 八、与现有需求的主要差异

| 维度 | 现有从物料构建需求 | 讨论记录倾向 | 评审建议 |
|---|---|---|---|
| 核心能力 | 多物料理解与本体候选生成 | 数据库结构导入先行、LLM 延期 | 按业务场景缩小，保留语义生成 |
| 输入边界 | 文件物料，不直连业务库 | information_schema 及抽样画像 | 沿用文件输入，直连另议 |
| 产出范围 | 五类定义及关联 | 首期对象、属性、链接 | 能力覆盖五类，有证据才生成 |
| 正式写入 | 用户确认后创建新本体草稿 | 候选直接写草稿，讨论与 Excel 同库合入 | 明确新建边界，不自动改既有本体 |
| 共享属性 | 默认私有，确认后共享 | 对齐属性优先晋升共享库 | 沿用现有需求 |
| 证据管理 | 字段级证据及任务附件 | 大量过程信息放 extensions | 任务侧管理，正式定义与候选显式关联 |
| 审核方式 | 内容、证据、结构与人工决定分别管理 | 窄接口、阈值及口径回填 Action | 分离状态，不增加领域动作 |
| 配套治理 | 先完成单用户生成闭环 | 推送、角色、超期运营 | 暂缓复杂治理 |

## 九、结论与待确认选择

建议保留现有需求作为主线，吸收接入解耦、多证据、来源版本和审核记录等合理设计；修正类型、候选身份和职责边界问题，暂缓审批运营体系。

下一步最值得确认的是首期验证范围：

- **推荐**：小规模储能场景，少量业务说明、DDL、代码联合生成，验证业务抽象价值。
- **备选**：只做数据库结构导入，但明确它是技术验证切片，不称为完整自动化本体构建。

本轮仅评审并归档意见，未修改既有需求、代码或用户数据。
