## 1. 现在你只需区分三个位置

| 位置 | 用途 | 后续怎么处理 |
| --- | --- | --- |
| 项目根目录 | 持续开发：源码、测试、当前规范、真实数据 | 继续在这里开发 |
| 发布包/ | 只包含当前运行所需程序和已构建页面 | 交付该目录，并单独配置数据与运行环境 |
| 待删除_非运行资料/ | 历史资料、原型、一次性脚本与旧回退备份 | 确认不再需要历史资料后，可整目录删除 |

**不要把整个开发项目直接拷贝到生产。发布时按运行清单生成包。** 前端源码和测试不进入运行包，但保留在开发工程，供下次修改和验收。

## 2. 精简运行包

```text
发布包/
├── workbench/                 后端全部运行源码，含 demo/ 与 formatter_runtime.cjs
├── frontend/dist/             构建后的 HTML、JS、CSS
├── resources/imports/
│   └── storage_20260814/source.jsonId  “来源参考”接口仍读取的原始资料
├── requirements.txt           Python 运行依赖
├── 运行说明.md                 安装、启动、数据位置说明
└── 文件清单.json               本次交付文件与内容摘要
```

运行时会在数据根下生成 ontology/。此包是程序交付包，不附带当前项目的真实本体、项目映射或连接密码。迁移现有数据须单独安排，不能把空程序包当成数据备份。

### 必须保留的内容

| 内容 | 原因 |
| --- | --- |
| workbench/*.py | Python服务直接执行这些代码 |

## 5. 真实数据与凭据

整个根目录 ontology/ 原位保留，不进入待删除目录。

- drafts 是草稿及修订历史；releases 是发布版本，两者不是构建缓存。
- workspaces 和 projects 是登记/初始化相关资料，也不能仅因“看起来旧”删除。
- vault 是连接密码，不随通用程序包分发；部署时通过工作台重新配置，或单独安排受控迁移。
- 大模型设置位于当前用户配置目录或环境变量，不包含在程序包内。运行环境需另行配置，文档和清单不记录密钥。

默认启动时，数据在运行包根目录的 ontology/ 下。也可通过 WIZ_WORKBENCH_ROOT 指定独立数据根；该路径下应包含 ontology/。源码中原始来源参考读取的是数据根下 resources/，独立数据根若需该功能，也需放入运行包提供的 source.jsonId（不需要其他历史导入文件）。

## 6. 启动与后续重新交付

进入运行包根目录，在目标环境安装Python依赖后启动：

```bash
python3 -m pip install -r requirements.txt
python3 -m workbench.server
```

地址仍是 http://127.0.0.1:8765/。Node需支持代码使用的 --permission 参数。自然语言显示格式需配置 FORMAT_LLM_URL、FORMAT_LLM_MODEL、FORMAT_LLM_API_KEY 或当前用户下的模型设置文件。

后续代码修改后，重新生成一个新运行包：复制workbench源码（排除缓存）、requirements.txt与原始source.jsonId，再将npm run build的结果输出到新包的frontend/dist。不要向已投入运行且存有ontology数据的目录直接执行整目录清空/覆盖。

本次“生产包”是当前本地工作台的精简运行交付目录。监听地址仍限本机，不包含公网/多人访问部署改造；文件整理也不代表已有业务验收问题自动解决。
