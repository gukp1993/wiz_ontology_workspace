## 3. 剩余修订项与最小反例

以下均针对测试代码，不表示真实业务接口发生了这些故障。

### G01 · 高：report容器再次把不同诊断拼接成一条

位置：`tests/deep_verdicts.py:144–213`，尤其from_envelope的非list分支直接item_text递归展平。

```python
response = {'status':422, 'json':{
    'report': {'errors':['activePower', '输出未绑定']}
}}
expect = {'diagnostic_term_groups':[['activePower'], ['输出未绑定']]}
classify_guard_attempt(True, response, expect)['result']
# 实际 product_pass；期望 test_error
```

把errors放顶层会正确拒绝，但多套一层指令明确要求支持的report就失效。因此“同一条诊断”约束没有贯穿嵌套结构。

修订：区分report/check等容器与单个诊断条目；递归进入容器时保留errors/diagnostics列表元素边界。同一errors条目中的name+message仍应可联合，不得把合法对照改坏。追加嵌套不同诊断/同条目两个字段两组对照。

### G02 · 高：warning可替无关error证明阻断正确

位置：`tests/deep_verdicts.py:445–508`。has_error取errors，但随后_diag_hit扫描整个响应，包含warnings。

```python
response = {'status':200, 'json':{
    'errors':['名称重复'],
    'warnings':['activePower 输出未绑定']
}}
classify_validate_observation(True, response, {
    'diagnostic_term_groups':[['activePower'], ['输出未绑定']]
})['result']
# 实际 product_pass；期望 test_error
```

存在的是无关阻断错误，目标内容仅为警告，不能证明目标依赖已经被阻断。守卫判定也不应仅凭warning替代拒绝原因。

修订：用于“正确阻断”的证据只从阻断错误提取；warning可供展示，不参与阻断通过判定。保留error/diagnostics中真实定位与原因的支持，补errors无关但warnings匹配的反例。

### G03 · 中：info不能覆盖业务的规则只在原编号路径生效

位置：`tests/deep_results_index.py:324–359`。valid_cases先加入所有编号；同编号检查会排除info，但CASE_ID_SPLITS和CASE_ID_ALTERNATIVES直接使用该集合。

复现：被替代批次含业务O4-07；有效批次同时含O4-07a、O4-07b，但两行均 `result='info', kind='info'`。`validate_superseded_coverage`返回uncovered=[]。同理旧别名映射到a/b，只有a说明行也通过。

本轮独立例子的case均用正常业务kind，排除工具错误豁免影响。实际历史数据没有据此被判丢失，但机器保证仍可被错误配置绕过。

修订：同编号、拆分、任选其一三条路径共用同一“有效业务证据”过滤，再判断集合；info不得混入。至少补拆分双info、一真一info、别名仅info和真实对照。
