# 业务规则管理一期需求

日期：2026-09-17。状态：按用户确认的简版范围实施。

唯一交互依据：[业务规则管理交互原型](../prototypes/业务规则管理交互原型_v1.html)。原型最新内容优先于前期复杂方案；本文约束优先于原型中的示例数据和演示限制。

## 1. 目标与范围

在本体建模中维护通用业务规则；规则只有四个业务填写字段。对象通过“规则”页签引用规则，规则列表可以反向查看引用对象。

一期只有：规则列表、按名称搜索、新建、查看、弹窗编辑；对象添加/移除规则引用；既有本体保存、校验、发布链路接入。不引入规则之间的依赖，不配置项目，不执行规则。

## 2. 四个字段

| 字段 | 数据键 | 形式 | 要求 |
|---|---|---|---|
| 名称 | name | 单行文本 | 必填，去除首尾空白 |
| 业务定义 | description | 多行文本 | 必填，简述规则用途 |
| 规则内容 | content | 多行文本 | 必填，保留换行、公式和自然语言原文 |
| 输出结果 | output | 多行文本 | 必填，用文本描述输出内容，不要求程序类型 |

系统生成稳定 id，不在业务表单展示。引用对象属于独立关联数据，不是第五个规则字段。无分类、标签、状态、参数表、输入表、适用对象字段、规则依赖、审核字段。

四项必填在点击保存时提示，提示紧邻缺失字段并聚焦首个问题；没有独立“检查填写”按钮。沿用系统允许保存不完整草稿的后台边界，正式发布禁止不完整规则；不能把业务内容不完整等同存储失败。表单正常保存应先通过必填检查。

## 3. 规则管理

菜单名称“业务规则”，置于本体区，不放项目区。保留现有其他菜单，按原型放在对象建模、共享属性库之后、动作定义之前；不要重做全站导航。

列表仅三列：名称、引用对象、操作。不得显示业务定义摘要、分类、状态或技术ID。

- 名称搜索：输入即筛选，仅按名称；保留搜索条件，中文与空结果正常展示。
- 点击名称或“查看”：打开只读详情弹窗，完整展示四个字段，保留正文换行；提供关闭和编辑。
- 点击“编辑”：打开编辑弹窗，四个字段，底部仅取消和保存；无额外页签或折叠配置。
- 点击“新建规则”：同样使用四字段弹窗，初始为空。
- 取消、关闭、Esc：有修改时询问是否放弃，不直接修改已保存内容；无修改直接关闭。
- 保存：经现有本体保存协调器即时持久化，成功后关闭并更新列表；失败保留填写内容并显示错误，不假成功。
- 引用对象：显示“X 个对象类型”或“暂无引用”；点击查看对象类型名称列表。每项可跳到对象建模对应对象的规则页签。
- 本期不提供删除规则、复制规则、分类筛选、审核和执行。

只读详情仍可显示业务定义；“列表不要业务定义”不代表删除该填写字段。

## 4. 对象建模的规则页签

在现有对象详情页增加“规则”页签，与属性、链接、动作并列。不得替换现有对象建模布局或删除其他页签。

- 展示当前对象引用的规则，仅名称与操作。
- “添加规则”：弹窗搜索已有规则名称，支持多选；已关联项不重复添加。
- 搜索变化不丢失已勾选项；无可选项有空态提示。
- “添加所选规则”：保存对象—规则引用，刷新两处引用展示。
- 查看：展示规则的只读四字段详情。
- 移除引用：仅删除当前对象的关联，不删除规则，也不改变其他对象引用。
- 同一规则允许被多个对象类型引用。
- 规则重命名后引用保持；引用必须使用稳定ID。

维护引用唯一入口是对象的规则页签，不在规则编辑弹窗提供“适用对象”或依赖编辑。

## 5. 数据归属与协议

规则属于本体，通过已有本体草稿/发布链路保存；项目 implementations 中的取值规则与本功能无关。

为减少格式迁移，建议并固定本期存储在已有 workflow 中：

```json
{
  "businessRules": [
    {
      "id": "系统生成的稳定ID",
      "name": "储能运行异常判定",
      "description": "识别无法由正常业务原因解释的运行异常。",
      "content": "先核验数据质量和有效边界，再判断实际响应。",
      "output": "判定结果、异常类型、依据与原因。"
    }
  ],
  "businessRuleAssociations": [
    {
      "objectTypeId": "对象现有的完整稳定ID",
      "ruleId": "规则的稳定ID"
    }
  ]
}
```

- 这不是新增独立数据文件，不使用历史 `rules.yaml`，不与项目 `queryRule` 混用。
- 老本体缺少两数组时按空数组读取；禁止初始化时覆写已有 workflow。
- 保留 workflow 中 actions/functions/interfaces 等其他数据和未知字段。
- 对象ID规范沿用现有完整 `@id`；旧格式若需兼容应在读取边界规范化，不靠显示名称连接。
- 关联对 `(objectTypeId, ruleId)` 唯一；引用对象或规则不存在时发布校验应准确提示。
- 对象删除沿用引用保护，存在规则引用时提示先移除；不得静默留下失效引用或顺带删除规则。
- 不变更 JSON-LD 对象/属性 schema；如果实际实施涉及格式协议，按 AGENTS 同步维护镜像。

## 6. 保存、版本与发布

复用 /api/save、本体 Saver、revision 和既有不可变发布机制，不增加一套规则专用草稿或发布按钮。

新建规则/新增关联按兼容新增纳入现有变更比较；删除已发布规则或关联按破坏性处理（即使一期UI不提供规则删除，比较器仍不能漏检）；规则内容、业务定义或输出变化标为待确认，不自动认定语义兼容；仅改名称按兼容处理。

必填及引用问题复用现有校验页面，定位到业务规则或对象规则页签。此处是发布校验结果，不是新增业务状态字段。

发布后读取该本体版本应包含规则及关联；不得改写历史版本或自动升级项目引用。

## 7. 原型与正式产品区别

原型仅供交互参考：19条示例与初始对象关联不等于真实用户数据，不自动导入。其他两条原始材料不适合直接作为本体业务规则，因此不作为本期预置内容。

正式产品不得保留“保存到原型”“刷新恢复示例”等演示文案，应真实持久化。示例只用于临时隔离测试，不得写入真实 ontology/。

## 8. 明确不做

分类/标签、规则状态、规则依赖图、规则之间的关联、输入输出签名、参数编辑、补充配置、原始材料审阅、项目衔接说明、SQL或Python编辑、LLM推理、测试执行、额外审核流程、恢复计算契约菜单、批量导入和规则删除。

不得为了“通用性”自行添加字段、页签、概念或开发平台。规则正文可以自然语言提到其他规则，但一期不解析、不存依赖关系。
