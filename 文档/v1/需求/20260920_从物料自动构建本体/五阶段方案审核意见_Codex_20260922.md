# 五阶段自动构建方案审核意见

日期：2026-09-22。审核对象：[生成五阶段完整方案](生成五阶段完整方案_20260922.md)。代码基线：`codex/auto_build`，`578acd7d47e2e457757e088110f2582ae261cbb0`。原方案为工作树内未提交文件，本轮未修改或代为提交。

## 1. 结论与边界

**五阶段职责划分可以保留，但当前方案不能作为“可靠完成自动构建”的验收依据。建议修改后复审。** 当前能力定位应是“根据物料辅助生成本体定义候选并交人工评审”，不是已经完成业务实例抽取、实体消歧、实例图入库的自动知识图谱系统。

优点是明确了任务侧候选与正式本体的边界，保留证据来源、人工评审、未发布草稿、CAS、交付事务和执行权隔离。主要缺口是：证据覆盖不足、跨批引用不稳定、冲突默认决定失效、部分失败恢复不完整。补等待秒数、提高并发或延长超时不能解决这些正确性问题。

本轮是方案审核与源码核对，不是完整产品验收。主审负责调度恢复和文档论证，两条独立只读审查负责语义链路及评审门禁；仅使用内存合成数据与替身调用，未访问真实数据库、调用外部模型、启动或重启服务。下列建议尚未实施，也不构成开发、集成或合并授权。

以下代码位置均相对于本工作树。P1 表示建议在宣称可靠生成前解决的正确性问题；“设计风险”与已复现行为分别标注。

## 2. 必须优先处理的问题

### R1 · P1：跨批临时键冲突会让属性归属错误

- 方案位置：§4.3 第10步（原文第276行）。
- 代码事实：`llm.py:82` 只要求单次输出内 key 唯一；`pipeline.py:1325/1368` 把所有调用结果直接累加、全局对齐；`alignment.py:138-155` 遇重复 key 时取首个对象。最终 `pipeline.py:326-338/1388` 才改重复 key，且未同步重写宿主和链接端点。
- 合成复现：第一批输出 `obj=电池,p=额定功率`，第二批输出 `obj=逆变器,p=额定功率`；全局对齐后只剩一项属性，键为 `property:额定功率#number@电池`。不同对象的属性被误合并。
- 建议：每次模型调用（包括拆分子批）结果进入累积集合前，先给 key 加稳定命名空间，并同步转换 `ownerKey/sourceRef/targetRef`；之后才进行语义上的跨批合并。解析不到的宿主不能全部归入 `@unknown` 自动合并。
- 验收：跨批复用 `obj/p`、跨子批重名、乱序完成、失败续跑，都保持两项属性及正确宿主；链接端点同测。

### R2 · P1：跨批发现冲突后仍可能默认纳入

- 方案位置：§5.2“其余默认 defer”（第410行）及 §8.1“非 supported 纳入必须理由”（第637行）。
- 代码事实：逐批 `verify_candidates` 先给 supported 候选 `include`；`alignment.py:91/124-131/195` 合并后保留首项决定并降级为 conflict；二次 `pipeline.py:906-907` 优先保留旧 decision。`delivery.py:48-52/99-134` 按 include 选定且未补充冲突审核与理由门禁；人工接口 `review.decide` 的理由校验无法覆盖此自动路径。
- 合成复现：两个同名对象，定义冲突但各有合法证据，依次执行 `verify → align → verify → adapt`，结果为 `conflict + include + conflicts=1`，没有 reviewed 或 reason。
- 建议：区分系统默认决定和人工决定；证据或冲突状态变化后重新计算默认决定。交付端再次检查非 supported 纳入的人工确认及理由，不能只依赖前端或决定接口。
- 验收：未经人工确认的冲突项不进入默认交付集合；直接请求交付同样不能绕过。已有人工决定遇新冲突时应显式失效或要求复核。

### R3 · P1：去重把不同主体的相同取值当成同一事实

- 方案位置：§3.3 第2步（第193行）。
- 代码事实：`retrieval.py:344-346` 哈希只含 snippet，`pipeline.py:1191-1197` 全池去重忽略定位和 data；却用组内去重统计 `grouped.stats.duplicates` 对外报告（第1198行）。
- 合成复现：`a.json $.battery.voltage=220`、`b.json $.motor.power=220`，全池只保留一项，但分组报告重复数为0。
- 建议：把“重复文件副本”和“不同字段同值”分开。事实身份至少包含主体、字段及语义定位；去重后保留所有来源映射，统计与实际删除集合一致。原文建议按布尔、短标量直接过滤也应收紧：`enabled=true`、额定值、枚举、主键可能有关键业务意义，应连同字段路径判断。
- 验收：同值异字段/异对象均保留；同一文件副本只降低独立佐证计数而不破坏来源追溯。

### R4 · P1：拆批部分失败被标成整批成功

- 方案位置：§4.3 第8/11步（第274、277行）、§4.5。
- 代码事实：`pipeline.py:238-249` 只有左右子批都失败才返回失败，一半成功就返回 `ok=True`；第1314行据此把父批记入 done。失败半批没有独立检查点，auto 会跳过整个父批。
- 影响：可能缺失半批事实对应候选，却继续进入后续阶段并报告成功。这是明确的控制流缺陷，不是模型质量推测。
- 建议：保存子批状态和事实集合。父批完成条件必须是所有必需子批完成；成功部分保留，失败部分可补跑。正式“部分成功”状态需同步接口契约和交付覆盖确认。
- 验收：左成功右失败、左失败右成功、嵌套拆分失败均可恢复，最终事实覆盖与不中断运行一致。

### R5 · P1：非连续失败批续跑会漏掉已返回结果

- 方案位置：§4.5 与 §7.6 的“只补失败批”承诺。
- 代码事实：`pipeline.py:144/168-176` 以整数逐一推进 next_flush，不跳过历史已完成的批号。调用方第1345-1347行也未消费返回的剩余 results。
- 主审复现：从当前源码提取调度函数，用立即完成的 Future 替身运行，`done={2},pending=[1,3]`，两次模型替身调用均成功，实际 `flushed=[1],unflushed=[3]`。第3批结果未触发落库回调。
- 相关缺口：按连续前缀刷写还会让第1批长等待时，第2/3批虽已返回但仍在内存；这不能等价表述为“任何已完成批次都立即持久化”。
- 建议：持久化按批次身份独立完成，最终展示和装配时再确定顺序；至少按实际 pending 序列推进游标。回调持久化异常（第174-175行当前吞掉）必须显式失败，且内存 done 不能先于事务成功成为权威状态。
- 验收：完成集合有空洞、首批慢后批快、写事务失败、取消及进程中断时，逐批核对调用记录、候选和检查点。

## 3. 方案层面的三处不足

### D1：500条预算没有转化为可追踪的覆盖目标

`pipeline.py:1177-1178/1200-1205` 把 relevant 与 related 拼接后取前500条，重试复用同一清单；末端第1388行再截断到500候选。前面的模块可能用尽预算，其他模块没有进入模型，却仍可能完成五阶段。原文虽披露截断，但“缩小范围重跑”不等于补齐。

建议：建立材料→主体→事实→模型批次→候选的覆盖记录，分别统计已解析、入选、已抽取、失败、预算排除；生成完成与覆盖完整分开表达。采用按模块/主体分配预算或持续分批覆盖，候选不能简单裁掉关系所依赖的对象。交付摘要明确遗漏范围与用户确认，不把 groups 数当覆盖率。

### D2：证据分组目前没有真正驱动抽取

`pipeline.py:1190` 计算 groups 后主要消费计数，第1235-1236行仍直接每20条切批；`llm.py:438-444` 只给当前批事实与 scope。没有全局对象表或跨批关系补充抽取；末尾精确同名合并不能恢复从未生成的关系。

建议保留五阶段名称，但把“align”产物变成可供下一阶段消费的主体组、候选身份和关系邻域。按主体与关系编批、按输入和预期输出预算拆分；必要时先抽对象/属性，再基于稳定对象表抽链接/规则/动作。跨批语义漏检属于待金样验证的风险，不在本轮声称实测漏检率。

### D3：证据引用存在不等于业务陈述有证据支持

`verify_candidates` 检查引用集合、枚举及结构，不能证明引用文本支持候选定义；模型原报 supported 若未触发降级，就可能进入默认 include。因此阶段名“检查冲突与引用”应说明其语义验证能力边界。

建议区分“引用有效”“字段有依据”“人工已确认”。按原需求 G16 建人工金样，分别衡量关键对象/关系漏检、字段证据支持率、错误合并率、接受率和人工修改耗时；固定材料版本、范围、模型标识及输出，以可复查样本为依据，不先承诺准确率。可增加语义复核，但另一次模型投票也不能替代事实依据。

## 4. 原文需要修正的论证

1. **“输出才是唯一瓶颈、生成速度基本固定”证据不足。** §4.4 用 `5352/89=60.2` 算出速度，再反推 `5352/60.2≈89`，是同一数据的回算，不能排除模型排队、首响应等待和网络耗时。单样本也不能证明110条事实必然线性产生29436 token，或并发3就稳定3分钟完成。保留样本观测，线性估算改为条件性假设，增加多样本分布及耗时分解后再定批大小。
2. **“429交调度器降挡重排”与代码不符。** 第273、558行的表述应改正：第182-185行只减并发并冷却，没有把失败批放回 queued。主审替身复现单批429只调用一次并回调失败；恢复仍依赖人工 resume。
3. **“390秒”不是所有失败路径的硬上限。** 它对应示例的260+130连接类尝试，JSON修复（`llm.py:447-466`）和递归拆批还可追加调用。应列调用层级和总截止时间，不把示例预算当全局承诺。
4. **现状、历史实测和提案应分栏。** 原文第138行及§9.2继续引用27.6万事实约40分钟，同时描述已优化的索引实现；应补各次实测SHA、输入摘要和证据文件，不能直接用旧耗时评价新实现。本轮未重跑性能测试，也未核验文档所列真实模型原始测量。
5. **候选密度口径混用。** 110条→55候选为0.5/条，20条→25–30为1.25–1.5/条；可能分别是去重前/后或不同样本，但需明确，不能直接作为统一外推系数。
6. **“直接发布”不应列为当前待选改进。** §9.4该项超出现有“只创建未发布草稿”的已确认边界；若要讨论应归未来范围，不影响本轮五阶段完善。

## 5. 推荐修改顺序与复审标准

先解决 R1–R5 的引用身份、冲突门禁、无损去重和完整恢复；再补 D1–D3 的覆盖记录、按主体编批及金样质量评价；最后基于真实耗时分布调整并发、超时和进度呈现。等待秒数与直达任务列表可以独立改进，但不能作为生成正确性验收的替代。

修订版应给每阶段写清输入输出契约、稳定身份、失败与部分完成状态、持久化条件及验收样本。至少覆盖：不同对象同值、不同批次同key、跨批关系、冲突需人工确认、拆分半失败、非连续续跑、超过500条的多模块材料。复审要同时看结构可保存、关键语义正确、遗漏可见及失败可恢复。

本报告仅交付审核结论；未改业务代码，未合并main，未更新主服务。纯文档交付不需要前端构建；本轮合成复现不等于浏览器或全套回归通过。
