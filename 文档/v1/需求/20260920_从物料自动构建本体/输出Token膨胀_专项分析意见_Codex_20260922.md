# 输出 Token 膨胀：专项分析意见

日期：2026-09-22。依据：[待分析文档](输出Token膨胀分析_20260922.md)与 `codex/auto_build @ 805e1d9` 源码。原文快照SHA-256：`1e6ae7cd9be9c6d7cc57e325d98e74db43f4cc9040fa1528fab1125fb543eb2c`。仅讨论本次 Token 膨胀问题，不展开此前五阶段审核整改。原文真实样本数字作为作者报告引用，本轮未访问业务库、原始物料或模型凭据，未调用付费模型，未修改业务代码及原文。

## 判断

这个问题可拆解，难点在于区分必要的业务信息和可以避免的生成工作。现有文档找到了推理开销、格式开销和元数据三个方向，但“输入侧完全没问题”“总输出与批大小无关”“整体发送不可行”“压缩协议必须改前后端”等结论过强。

针对本文样本，优先验证的根因假设是：**材料已经带有本体结构，却被转成通用叶子/数组摘要，再交给模型重新判断并书写完整候选；模型承担了可由程序保留、复制和转换的工作。** 加上未显式控制的推理强度、长引用与重复字段，才形成高输出。输出超过输入本身不是错误，目标应是降低“每个正确、唯一、可追溯候选的总成本”，不能通过漏对象、漏关系或删证据来做低数字。

## 1. 首先修正测量和归因

原文把3万更正为约1.2万–1.6万，是修正了参与计算的事实数。但后者仍是单批样本乘3，并非整轮各次调用 usage 的总和。不同批的实体密度、重复定义、推理量和重试都影响结果。

应分四层测量：

| 层 | 应记录的数 | 当前材料的限制 |
|---|---|---|
| 输入 | provider prompt_tokens、请求字节、实际入模事实数/主体数 | 110条解析事实的31%元数据比例不能套用到入模60条 |
| 输出 | provider completion_tokens；有明确明细时记录reasoning_tokens | 英文思考字符数和中文JSON字符数不能按同一比例换算；50%只能按原文暂视为估算 |
| 最终结果 | 去重后正确候选数、证据和关系覆盖 | 55个最终候选的重建JSON不是每次原始模型输出；其中骨架字符占比不是token占比 |
| 时间与重试 | 总耗时、每次调用/失败/修复/拆分尝试、可测时记录首响应延迟 | completion_tokens÷总耗时是吞吐观测，不是纯解码速度；不能再用该商证明时间全花在解码 |

源码核实：`workbench/llm_client.py:61-83` 没有返回 provider 的 usage 或推理用量；`ontology_build/llm.py:163-165/445-457` 统计 calls、正文字节、耗时。**现有工作台用量不能完整解释推理token或整轮计费。** 建议仅补安全数值、模型标识、请求关联标识、finish_reason及有效推理配置，不保存或展示推理原文；未返回的usage标为未知而不是0，失败尝试也纳入可观测账本。

本轮未重新核验原文“两次输入差异完全不影响输出”的说法；相近token数不等于相同内容和相同任务。骨架48%→15%、总输出降30%、关思考减半均需对照实验，不能作为收益承诺。不同措施的收益也不能直接相加。

## 2. 推理强度是一个具体、可独立验证的调整点

当前 `workbench/llm_client.py:43` 请求只有 model、temperature、max_tokens、messages，没有 reasoning_effort。

截至本次查询，Z.ai官方明确：GLM-5.3与GLM-5.3-FLASH强制思考，不接受 `thinking.type=disabled`；API支持 `reasoning_effort=low/high/max`，默认max。参见[官方Deep Thinking参数说明](https://docs.z.ai/guides/capabilities/thinking)。因此应测试受支持的low档，而不是用“不要思考”的提示词替代API控制。若实际接入第三方网关或其他服务面，仍需验证参数是否接受并生效；本轮未读取实际endpoint，未证明生产实例已采用官方默认档。

推理不进入最终本体，但可能帮助概念消歧、关系判断和证据核对，不能等价为无效工作。建议先在同模型、同输入、同输出格式下比较默认档与low档，再决定是否保留。降低max_tokens是限额保护，不是降低推理开销的等价手段；过低可能使JSON截断并增加重试。

## 3. 对这份材料，保留结构比缩短字段名更值得优先验证

原文描述输入包含classes、object_properties、data_properties、required_fields等。当前 `parsers/json_parser.py:78-104` 的专门节点处理主要针对JSON-LD，其他内容进入通用walk_tree；`parsers/structwalk.py:7-9/159-195` 将标量作事实，普通数组作类型、长度和首元素键摘要。

这会增加两类负担：模型重新拼上下文；模型判断“规则、属性、字段说明”究竟是业务概念还是描述格式的元信息。数组摘要还可能不足以支持完整的语义转换。因此“输入token不大”并不说明输入表示合适；解析耗时0.04秒也不能证明解析后的表示没有增加下游模型负担。

建议分为三条路径，都是建议而非已实现：

| 输入情况 | 程序负责 | 模型负责 |
|---|---|---|
| 已支持、可验证的本体格式 | 按明确映射保留名称、原始定义、类型和关系，附来源路径，生成标准候选 | 只处理映射歧义或缺项 |
| 未支持但有清晰语义结构的JSON | 保留完整类/属性/关系节点及邻域，而非只给离散标量 | 判断节点语义、目标类型与不确定映射 |
| 普通文档、代码、杂项材料 | 提取有上下文的证据块并保留定位 | 从业务证据抽取候选 |

不能仅凭 `.ontology.json` 后缀或出现classes键就直接导入。继承关系、对象链接、属性类型、规则类别必须有目标协议映射；无法表达的语义显式列出。确定性转换也只进入现有候选评审，不绕过草稿和人工确认边界。

一个值得实验的目标是：源文件已经有name/definition时，让模型输出“源节点标识 + 目标类型 + 必要修改/不确定项”，后端按来源映射复制原文；只有确需抽象的定义才让模型新写。这样减少的是完整候选的重复生成，而不只是几个标点。现阶段不承诺具体节省比例。

## 4. 紧凑协议可以限制在模型接口内部

`ontology_build/llm.py:434-476` 已有“模型响应→清洗→标准候选”的边界。可以在该边界增加有版本的紧凑编解码，继续对存储和前端返回原有候选结构。**单纯压缩模型线协议不必修改前后端HTTP契约或本体字段镜像**；内部协议仍应文档化。若新增对外用量字段或配置入口，才同步其实际涉及的接口。

优先顺序：

1. 请求内证据别名：用F1/F2替代长factId，服务端持有一一对应表，响应先反解再校验；不要直接截哈希后缀。子调用独立绑定映射，越界或未知别名不能猜。
2. 省略真正无语义的空容器：无冲突时省略空conflicts，无字段时省略空fields，后端补空值。缺失不等于“已验证无冲突”；不能默认补supported、关系基数、属性宿主等业务判断。
3. 分类输出或短对象键：在objects/properties/links等分组下避免逐项重复type，保留可校验字段。先做短对象键比位置数组稳妥；数组错位、修复重试可能抵消节省。
4. 来源复制：已存在的定义、标签通过来源映射复用；模型只返回新增判断或变更。字段级证据不能为了缩短输出退化成一条不明来源的总引用。

不建议压缩后立刻提高每批事实数：先固定批大小验证质量与净token，再调整批次，才能分辨收益来自哪项变化。

## 5. 不能据现有数据排除整份输入或较大语义批次

“同一组事实分几批，总输出都相同”并不成立。每批都重新收到系统提示与范围、重新推理，可能重复生成同一对象；大批又可能增加复杂推理或重复。因此输出量、质量和批大小有关，但方向需要实验，不能线性断言。

小型结构化材料保留整体或按完整主体分组值得对照。它可能减少重复对象和重复推理，也可能增加尾延迟、截断和单次失败损失。37%–50%的估计输出预算占用只能说明一种假设，不能证明不可行。大规模资料仍需要按主体、关系邻域与token预算编批，不能推广成所有文件一口气输入。

并发主要改变墙钟时间，不会自动减少总token；流式主要增加可见性，若仍生成相同内容也不省token。两者都应与减少生成工作区分衡量。

## 6. 最小验证顺序

以下只是建议实验，未运行、未形成开发排期或模型调用授权。

| 顺序 | 对照 | 目的 |
|---|---|---|
| 0 | 固定材料/范围/请求，记录安全usage与最终候选 | 建立整轮基线，含重试开销；先统计真实入模60条的构成 |
| 1 | 原格式默认推理 vs 原格式low | 单独判断推理档位的净收益与质量损失 |
| 2 | 相同推理档下完整协议 vs 紧凑协议 | 判断格式节省，不把推理变化混入结论 |
| 3 | 叶子事实 vs 完整语义节点/经验证的映射 | 判断重复推理、噪声候选和语义遗漏是否改善 |
| 4 | 最佳表示下主体分组 vs 小文件整体输入 | 再决定批大小与并发，不先固定40条或无限大批 |

同一输入每组重复若干次并交错运行，避免把服务负载差异当优化效果；初筛少量重复只能看中位数和范围，不能声称稳定P95。至少使用已结构化本体、普通业务JSON、非结构化文档三类脱敏样本。

通过条件同时看：关键对象/属性/关系不漏、证据可追溯、无新增元信息误建模；JSON成功率与人工修改量不恶化；全轮token、耗时和重试成本下降。最终比较“总token÷正确且唯一的候选数”，并同时看覆盖，防止靠少生成候选让成本显得更低。

**推荐方向：先测量并验证low档，再让结构化输入走保留结构或确定性转换路径，让模型只输出必要的语义判断，后端补全标准格式。** 单独压缩JSON只能解决部分开销，结构和职责分配决定长期成本。
