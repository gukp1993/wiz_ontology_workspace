## 3. P1-1 实验 commit_failure 重复回调必须幂等返回 False

- **位置**：`experiments/ontology_token_pilot/state.py` `commit_failure`（约 432–465 行，449 行 `attempt 非 started` 检查先于一切幂等判断）。
- **现象**（验收反例 E-bool3）：同一 job 首次 `commit_failure` 返回 True 后，重复回调抛 `ValueError("尝试 … 状态 failed，非 started（晚结果拒绝）")`；在线侧 `OnlinePersistence.commit_failure`（`batch_persistence.py:387-388`）返回 False。违反冻结语义（True=新提交/False=幂等跳过，`2ee24cd` 声称统一但只改了在线侧）。
- **冻结要求**：
  1. 重复失败回调（job 已 failed / attempt 已 failed）→ 返回 **False**，不抛异常、不改写任何状态、不重复写入；
  2. 与在线侧行为一致；执行器拿到 False 走既有 `PersistenceRejected` 路径，不得被当成存储故障重试。
- **建议实现**：进入在途检查前加早退分支——job 状态为 `failed`（终态）且 attempt 状态为 `failed` → `return False`（镜像在线侧"job 终态即跳过"的次序）。
- **测试**（必加）：`tests/test_ontology_token_pilot_state.py` 增"commit_failure 首次 True/重复 False 且库内无重复写入"；**D17 脚本B**（`tests/test_ontology_token_pilot_acceptance.py`）契约 3 扩展为覆盖 `commit_success` **与** `commit_failure` 双适配器幂等（这是本次漏网原因，防止复发）。
- 可选加固（不强制）：跨终态回调（如 job 已 succeeded 又收到 failure）实验侧目前抛 ValueError、在线侧返回 False——若顺手对齐则一并处理并在契约注释写明；不处理则在 `state.py` docstring 如实记录该差异点。

## 4. P1-2 容量在途口径不一致 + 容量触发受阻未按契约落库

- **位置**：`workbench/ontology_build/batch_execution.py:208`（`_plan_guard` 用 `checkpoint_fits(doc, 0)`）与 `:339`（claim 无捕获）；`workbench/ontology_build/batch_persistence.py:139-147`（`_ensure_fits` 按新文档 started 数计在途，claim 后=1）；`experiments/ontology_token_pilot/state.py` `_persist_doc`（claim 时在途恒 0）。
- **现象**（验收反例 O-cap3/O-cap4）：计划合法落库在 soft(0)−512B（soft(n)=1MiB−16KiB−8KiB×(n+1)）→ 守卫放行 → claim 按在途=1 抛 `CheckpointCapacityError` → 执行器无捕获上抛 → run 按通用异常 **failed** 收尾。违反冻结契约"不足 → 停止派发并**记 CHECKPOINT_BUDGET_EXCEEDED**（受阻、可读原因、成功叶保留）"；且 resume 会重复同样失败不可自愈；实验侧 claim 在途口径与在线不一致。1MiB 级 checkpoint 在 4096 目标上限下可达，非纯理论。
- **冻结要求**（四条，缺一不可）：
  1. **守卫与 claim 口径一致**：派发守卫放行后，claim 不得因容量抛异常（守卫余量必须覆盖单次 claim 的文档增量）；
  2. **容量触发的受阻必须能落库**：最终态为 blocked + `checkpoint.generate.blocking.code == CHECKPOINT_BUDGET_EXCEEDED`、文案可读、成功叶与已记账 usage 保留；`CHECKPOINT_TERMINAL_RESERVE_BYTES`（16KiB 终态写入预留区，`batch_contracts.py:76`）的设计意图必须落地——终态/受阻写入允许用该预留（仍不得超 1MiB 硬上限）；
  3. **双适配器一致**：OnlinePersistence 与 ExperimentState 的在途计数与终态宽限同一口径；
  4. **硬上限不放松**：> 1MiB 序列化仍整体拒绝且库内不变（既有行为不得回归）。
- **建议实现**（可按现状落实的技术路线，允许等价替代）：
  - 守卫收紧：`_plan_guard` 改按"拟派发一个调用"计——`checkpoint_fits(doc, 当前 started 数 + 1)`（同步执行器恒为 soft(1)），余量 8KiB 覆盖 claim 的 ~400B 增量；
  - `_ensure_fits` 增终态宽限：写入后文档**无 started 在途尝试**时，上限放宽至 `checkpoint_soft_limit_bytes(0) + CHECKPOINT_TERMINAL_RESERVE_BYTES`（= 1MiB−8KiB，仍 < 1MiB），使 `_block_run` 的 blocking amend 永远可持久化；
  - 保险丝：`_drive_job` 对 claim 抛出的 `CheckpointCapacityError` 兜底转 `_block_run(CHECKPOINT_BUDGET_EXCEEDED)`（正常路径不应触发，防未来口径再漂移）；
  - 实验侧 `claim_job` 的 `_persist_doc` 传入新文档 started 数，与在线统一；
  - `batch_contracts.py` 容量闭环注释块同步改为与实现一致的冻结口径（先改契约注释再改实现，保持"唯一口径"纪律）。
- **测试**（必加，双适配器同场景）：
  1. 计划 ≈ soft(1)−ε：step → claim 正常、调用执行、commit 成功（不再崩）；
  2. 计划 ∈ (soft(1), soft(0)] 或略超（终态宽限内）：step → **blocked**，库内 `blocking.code==CHECKPOINT_BUDGET_EXCEEDED`，成功叶保留，run 不因未捕获异常 failed；
  3. > 1MiB：save/claim 仍拒且库内不变（回归既有断言）；
  4. resume 前述受阻计划：不进入"重复崩溃"循环（受阻态给出可读处置，与既有"受阻需新建计划"语义一致）。
  放置建议：`tests/test_ontology_build_budget_storage.py`（在线）+ `tests/test_ontology_build_batch_execution.py`（执行器边界）+ 脚本B 容量契约扩展（实验侧）。
