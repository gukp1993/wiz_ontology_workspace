## 问题与整改

### A1 · P1 · R1：拆分子批复用键仍会把属性挂到错误对象

定位：`workbench/ontology_build/pipeline.py:239–248` 子批直接拼接、`:1395` 仅父批命名空间、`:350–362` 最后只改重复 key；真实交付在 `ontology_adapter.py:160` 按 ownerKey 解析。

复现：一次父调用截断后拆成电池、逆变器两个子调用；各自返回合法 `obj/prop`。真实执行 split → verify → namespace → align → verify → adapt → dedupe → assemble，最终：

```text
电池额定功率 → 电池
逆变器额定功率 → 电池  # 应为逆变器
```

alignedKey 显示正确宿主不能代表最终图正确。实施方原复现检查属性数和 alignedKey，没有验证最终 domain，因而漏报。原 R1 验收明确包含拆分子批，复验指令中的“已知未修复”不能自行豁免。

整改：每个实际模型调用，包括递归拆分叶，在拼接前获得稳定身份和命名空间；统一重写 key/ownerKey/sourceRef/targetRef。不能以最终临时改 key 代替身份隔离。同名同义候选是否合并是后续独立语义决策。验收必须装配最终图检查每条 domain/range，覆盖嵌套拆分、对象顺序变化、跨父批和恢复路径。

### A2 · P2 · R2：门禁后的依赖集合不一致，预检通过但实际交付失败

定位：`delivery.py:48–60` 新门禁过滤候选；`:117–152` 依赖检查仍使用全候选；`review.py:373` 的 deliver_blockers 按 include 判断依赖，不识别门禁排除；`delivery.py:214` 实际装配使用过滤后的集合。

在真实临时 SQLite 中播种“冲突且未确认的电池对象 include + supported 功率属性 include（ownerKey 指向电池）”，实际返回：

```text
precheck True [] excluded 1 counts {'property': 1}
prepare blocked: 交付前检查未通过
```

对象被门禁移除，属性仍通过预检；直到装配才失败。没有证据说明错误图已被创建，问题是预检误报、交付流程阻断。

整改：服务端定义唯一最终选定集合，预检、依赖解析、别名解析、计数、checkToken、实际装配共用。属性/链接/规则/动作引用的对象不在最终集合中时，应返回定位到候选及引用字段的阻断项，不能自动纳入冲突对象，也不能静默删除依赖项。补真实临时库的预检与 prepare_payload 一致性测试。

另外，`frontend/src/ontology/build/BuildSavePage.vue:224–236` 未接收 conflictExcluded/conflictExcludedItems/notes；仅新增后端排除报告不能证明用户已看到。整改时同步类型和展示，区分人工排除、暂缓和门禁排除，并提供回到对应候选评审的入口，做隔离浏览器验收。

### A3 · P2 · R4：部分成功批重试会把同一候选再次落库

定位：`alignment.py:113–115` 遇到已占用键追加下划线；`pipeline.py:1417–1421` 再按改名后的键排重，此阶段还没有 alignedKey 可兜底。

复现：批1成功保存园区 obj；批2部分失败保留电池 b2:obj；恢复候选后重试批2，返回同样的成功部分，得到：

```text
首次：[('obj','园区'), ('b2:obj','电池')]
重试：[('obj','园区'), ('b2:obj','电池'), ('b2:obj_','电池')]
```

验证方式：从当前源码 AST 提取实际 _flush_batch 闭包，数据库和 runner 用内存替身，真实执行命名空间及判重控制流。此证据证明控制流不幂等；不冒充真实 SQLite 的完整恢复验收。原测试只覆盖无碰撞等较窄路径，不能支持“整批重跑幂等”的全面结论。

整改：持久化拆分树与叶状态，建立由任务/逻辑生成批/叶身份/原始候选键构成的稳定结果身份；同一叶结果原子替换或唯一约束，成功叶不重复生成。如果暂保留父批重跑，也必须证明结果替换和引用稳定，不能依靠“遇重名加后缀”。候选写入与叶检查点应在同一事务提交，事务成功后才更新内存完成状态。补真实临时 SQLite 的连续部分失败、进程恢复、最终成功、取消后恢复及嵌套拆分测试。
