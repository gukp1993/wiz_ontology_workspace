# 输出 Token 膨胀分析：8 KB 的 JSON 为什么产出上万 token

> **文档性质**：单一问题分析。回答「输入才 2000–3000 token，为什么输出会到上万 token，到底做了什么处理」。
> **日期**：2026-09-22
> **代码基线**：`codex/auto_build` @ `578acd7`（`worktree/auto_build`）
> **实测对象**：任务「未命名任务-2026-09-22」的材料 `储能_V20260814_0002.ontology.json`（8,123 B）
> **测量方法**：①直接 POST provider 端点，请求规格与线上单批完全一致（20 条事实、`max_tokens=32000`）；②只读 SQLite 还原真实候选与事实；③读源文件本体。所有数字标注来源。

---

## 0. 结论速览

**输入侧没有问题，膨胀全部发生在输出侧，且有明确的三个来源。**

| 事实 | 数值 | 来源 |
|---|---|---|
| 源文件 | 8,123 B（约 6,153 字符） | 实读 |
| 解析出的事实 | 110 条（`jsonLeaf` 54 + `jsonArraySummary` 56） | 实读 |
| 去重（同片段）后**进模型** | **60 条**（`duplicates=50`） | 实读 checkpoint |
| 分批 | 3 批 × 20 条（`batches={size:20,total:3}`） | 实读 checkpoint |
| **单批输入 token** | **2,432**（请求体 8.0–8.7 KB） | 实调实测 |
| **单批输出 token** | **3,889**（另一样本 5,352） | 实调实测 |
| 其中**模型思考** | 8,676 字符 ≈ **1,961 token（占 50%）** | 实调实测 |
| 其中**正文 JSON** | 3,007 字符 ≈ 1,927 token | 实调实测 |
| 单批耗时 | 81 秒（另一样本 89 秒） | 实调实测 |
| 输入占上下文比例 | 2,432 / 1,000,000 = **0.24%** | 计算 |

**三处膨胀**：

1. **模型思考占输出的一半**——推理模型每次先把 20 条事实逐条「想」一遍（写成英文推理），再输出 JSON。思考计费、耗时，但不产生业务内容。
2. **正文 JSON 里近一半是格式骨架**——每个候选都重复抄写完整字段名、括号、引号；证据引用还要抄 27 字符的 `factId`。
3. **素材本身含 31% 元数据**——版本号、语言标签、布尔标记被当成「事实」送入，模型为它们也要写候选。

**一次完整运行的总输出**：60 条事实分 3 批，按单批实测值推算约 **1.2 万–1.6 万 token**（3 × 3,889 ～ 3 × 5,352）。

> **对上一轮口头的更正**：我此前说「约 3 万 token」，是用**全部 110 条事实**外推的（5,352 × 110 ÷ 20）。但实际**只有 60 条进模型**——解析出的 110 条中有 50 条被「同片段去重」掉（`plan.duplicates=50`）。因此正确量级是 **1.2 万–1.6 万**，不是 3 万。样本外推本身也有局限，见 §7。

## 1. 输入侧核算：为什么不可能是输入的问题

| 环节 | 数值 | 说明 |
|---|---|---|
| 源文件 | 8,123 B | 用户上传的 JSON |
| 解析为事实 | 110 条 | 每条平均 50 字节文本（`snippet` 合计仅 5,608 B = 5.5 KB） |
| 同片段去重后进模型 | **60 条** | `plan.duplicates=50`（实读 checkpoint） |
| 单批 20 条事实的 `facts` JSON | 6,527 B | 含 `id`/`locator`/`snippet`/`kind`/`data`（`llm.py:198-215`） |
| 系统提示词 | 1,861 B | `llm.py:63-83` |
| **单批请求体合计** | **8.2 KB ≈ 2,432 token** | 实调实测 |
| 模型上下文上限 | 1,000,000 token | GLM-5.3-Flash |
| **占用比例** | **0.24%** | 计算 |

**结论**：分批与「上下文放不下」无关。把 60 条事实一次性全发，输入约 7,300 token，仍只占上下文的 0.73%。

## 2. 输出侧核算：钱和时间花在哪

### 2.1 两次真实调用样本

| 指标 | 样本 A | 样本 B |
|---|---|---|
| 输入 `prompt_tokens` | 2,362 | 2,432 |
| 输出 `completion_tokens` | 5,352 | 3,889 |
| 耗时 | 89.0 秒 | 81.0 秒 |
| 输出 / 输入 | **2.3 倍** | **1.6 倍** |
| 生成速度 | 60.2 token/秒 | 48.0 token/秒 |

两个样本输入几乎相同（2,362 / 2,432），输出相差 38%——**模型自身波动，不是代码差异**。

### 2.2 一个反直觉但关键的事实：输出比输入还长

抽取任务的本质是**读一页资料、写一份比资料更长的结构化报告**：

- 读：20 条事实，每条 50 字节的短句（合计约 1 KB 文本）
- 写：25–30 个候选，每个含 `key` / `type` / `name` / `definition` / `fields` / `evidence` / `evidenceStatus` / `conflicts`

**输入 1 KB，输出 3.8 KB。** 生成速度固定（48–60 token/秒），所以耗时几乎全部由输出量决定：3,889 ÷ 48 ≈ 81 秒。

## 3. 输出膨胀的三个来源

### 3.1 来源一：模型的「思考过程」占输出的一半（最大单项）

**实测**：抓取模型原始响应，`message` 实际有三个字段——`content` / `reasoning_content` / `role`。

| 字段 | 字符数 | 折算 token | 占比 |
|---|---|---|---|
| `content`（真正的 JSON） | 3,007 | ≈1,927 | **50%** |
| `reasoning_content`（思考过程） | 8,676 | ≈1,961 | **50%** |
| `completion_tokens`（计费输出） | — | 3,889 | 100% |

思考原文节选（英文推理）：

> *"The user wants me to extract ontology candidate definitions from the given facts. The scope is about 储能... Let me analyze the facts: 1. Metadata facts: uri, name, version, language, source_graph, generated_from, validation... these are metadata, not really candidates..."*

**注意它在做什么**：模型正在**逐条复述我们喂进去的元数据**，并判断这些字段算不算候选。这直接呼应 §3.3——喂进去的噪声，既拖长思考，又可能产出无意义候选。

**性质**：GLM-5.3-Flash 是推理模型，思考是它的固定行为；思考计费、耗时，但**不产生任何业务内容**。这是当前耗时与 token 消耗的最大单项。

### 3.2 来源二：正文 JSON 里近一半是格式骨架

把 55 个真实候选按字段拆开统计（重建模型输出）：

| 组成部分 | 字符数 | 占比 |
|---|---|---|
| **JSON 结构骨架**（字段名、括号、引号、逗号） | 6,490 | **47.9%** |
| evidence 证据引用 | 2,980 | 22.0% |
| definition 业务定义 | 1,274 | 9.4% |
| fields | 970 | 7.2% |
| key | 809 | 6.0% |
| evidenceStatus | 468 | 3.5% |
| type + name | 560 | 4.1% |
| **合计** | **13,551** | 100% |

**真正的业务内容（name + definition + fields）合计不到 17%。**

**骨架为什么这么大**：抽取协议的每个候选都要写全字段名，而字段名本身是英文长词：

```json
{"key":"yuanqu","type":"object","name":"园区","definition":"...",
 "fields":{},"ownerKey":"","evidence":{"definition":["bf-018d128e5e0dff29e1ca3554"]},
 "evidenceStatus":"supported","conflicts":[]}
```

一个候选 246 字符，其中：
- `"evidenceStatus"` 一类的长字段名反复出现
- **`factId` 是 27 字符的哈希**（`bf-018d128e5e0dff29e1ca3554`）；全量 72 次引用 = 1,944 字符 = **输出的 14.3%**
- 空值也要写（`"fields":{}`、`"conflicts":[]`、`"ownerKey":""`）

**这属于协议设计选择，不是模型啰嗦。** 若改用数组 + 短键名 + factId 只传后缀，骨架占比可从 48% 降到约 15%。

### 3.3 来源三：输入里 31% 是元数据，且素材本身是一份已建好的本体

**实测（事实层）**：110 条事实里 **34 条（31%）是低价值叶子值**——`"1.0"`、`"true"`、`"zh-CN"`、空字符串。它们来自 JSON 的元数据字段（版本号、语言标签、布尔标记）。

**实测（素材层）**：读源文件可见，它**本身就是一份本体**：

```
顶层键: uri / name / version / language / source_graph / generated_from /
        validation / classes / object_properties / data_properties / known_issues_found
generated_from: "人工精修（基于 semantica OntologyGenerator 草稿 + 92 条关系全量核对）"
classes: 实体 → {园区, 储能簇, 储能系统, 储能设备, 线路分段, 负荷}
         属性 → {实时量, 累计量, 额定参数}
         规则 → {计算规则, 动作规则, 校验规则, 约束规则, 数据选取规则, 策略类, 其他}
```

**传导链**：一份已建好的本体 → 被拆成 110 条事实（含版本号、布尔值）→ 模型重新组装回本体 → 55 个候选。

**噪声证据**：抽取结果里出现 `实体`、`属性`、`规则`、`业务属性`、`规则类型`、`取值方式`、`来源`、`作用对象`、`实例数据表` 等候选——这些是**描述本体的元语言/字段名**（源文件里 `required_fields: ["name","definition","subtype","instance_table","applicableObject"]` 正是它们的来源），而非储能业务概念。模型要为它们逐条写 definition、evidence、evidenceStatus——**额外输出**。

## 4. 为什么「直接整份丢给模型」不可行

按两次样本外推（**条件性估算，非实测**）。注意：**总输出量取决于进模型的事实总数，与批大小无关**；批大小只影响「单次输出」的大小。

| 方案 | 单次输入 | 单次输出 | 单次耗时 | 风险 |
|---|---|---|---|---|
| 分批（现状 20 条/批，共 3 批，并发 3） | 2,432 | 3,889–5,352 | 81–89 秒（并发后墙钟同样量级） | 单次输出远离上限，失败只赔一批 |
| **不分批（60 条一次）** | 约 7,300 | 约 **1.2 万–1.6 万** | 约 **4–5 分钟** | 单次输出达 `max_tokens=32000` 的 **37%–50%**；4–5 分钟内无任何中间结果，失败全白费 |

> 注：事实若不去重（110 条全发），单次输出会到约 2.1–2.9 万 token，逼近上限的 **66%–92%**——这正是去重带来的额外价值。

**分批的真实目的不是省上下文，而是三条**：

1. **把单次输出压到安全区**——避免撞 `max_tokens` 导致整批被判截断失败（`llm_client.py:69-70`）；
2. **让失败可局部恢复**——只重跑失败批，不重来全部（`pipeline.py:1352-1365` 报错文案即此设计）；
3. **让批次可并发**——默认并发 3（`protocol.py:69`），把墙钟压到接近单批耗时。

## 5. 不是原因的部分（排除项）

| 猜测 | 实测结论 |
|---|---|
| 上下文不够（1M 装不下） | 否。输入仅占 0.24% |
| 文件太大 | 否。源文件 8 KB，解析后文本 5.5 KB |
| 分批策略把输入重复发送 | 否。3 批各自发各自 20 条，无重复（`plan.modelFactIds` 60 个 id 无交集，实读 checkpoint） |
| 解析器产生了冗余事实 | **部分是**。110 条事实中有 31% 是元数据叶子值（见 §3.3），但这是解析层按「不丢材料」原则保留的结果，不是解析错误 |
| 模型配置的 `max_tokens` 太大 | 否。`max_tokens=32000` 是**上限**不是消耗；实际消耗 3,889 |

## 6. 收敛手段与预期影响

| # | 手段 | 预期影响 | 代价 |
|---|---|---|---|
| 1 | **约束模型思考**（提示词要求直接输出，或抽取环节改用非推理模型） | 输出与耗时约**降一半** | 需验证抽取质量是否下降 |
| 2 | **压缩输出协议**（数组代替对象、短键名、factId 只传后缀） | 骨架占比 48% → 约 15%，输出降约 30% | 前后端协议需同步改，涉及镜像文件 |
| 3 | **过滤元数据事实**（版本号、语言标签、布尔标记不进模型） | 输入减约 30%，输出随之减，噪声候选减少 | **须结合字段路径判断**：`enabled=true`、额定值、枚举、主键可能有关键业务意义，不能只看取值形态 |
| 4 | **识别输入已是本体的情形** | 若走直接转换，可跳过整个抽取环节 | 架构级改动，需先确认判定特征与覆盖面 |
| 5 | 调大批次（如 40 条/批） | 批数减半，但单批输出翻倍 → 更易撞 `max_tokens` | 不推荐（历史上 40 条/批正是导致截断的原因，见 `protocol.py:25-27`） |

## 7. 口径与未核实的部分

**测量口径**：
- 「思考 50%」基于**一次**样本（81 秒那次）；另一样本（89 秒）未抓取 `reasoning_content`，无法确认思考占比是否稳定。**结论方向可靠，精确比例未做多次采样。**
- 总输出「1.2 万–1.6 万」是**按 3 批线性外推**（单批实测 × 批数）。未验证：批间输出是否等量、并发是否影响单批输出量。**样本 A（5,352）与样本 B（3,889）本身相差 38%**，故该区间应按「量级」理解，不是精确值。
- 「不分批 4–5 分钟」由外推输出量 ÷ 实测生成速度（48–60 token/秒）得出，未扣除排队与网络开销。

**未核实**：
1. 思考 token 占比在不同批次、不同范围下的稳定性（仅 1 次采样）。
2. 不分批时的真实输出量（未实跑 60 条一次性调用，仅外推）。
3. 各收敛手段的实际收益（均未实施、未验证）。
4. 该素材在分批与不分批两种方式下的抽取质量差异。
5. 「31% 低价值叶子值」是对**全部 110 条**的统计；这 110 条中有 50 条因同片段去重未进模型，故**进入模型的那 60 条里元数据占比未单独统计**。

**明确排除的误读**：本文所有「慢」的归因都是**输出侧**，与输入大小、上下文上限、文件体积无关。之前把「8 KB 小文件却很慢」理解为解析问题是不成立的——解析在 0.04 秒内完成（scan run `94825c10` 于 `05:27:35` 成功），慢的全部是模型输出。
