## 4. 剩余问题与明确修复方案

### R5-01：取消状态被成功收尾覆盖（P2，非阻断）

**位置**：`workbench/ontology_build/runner.py` 的 `finish_success()`（约289行）及 `request_cancel()`。

**影响**：用户已看到取消成功，运行随后又显示成功。最终可能出现 `state=succeeded`、`cancel_requested=1` 的矛盾状态；生成任务还可能被推进到评审阶段，削弱运行状态的可信度。该问题不产生旧响应内容污染。

**独立复现顺序**：

1. 在临时 SQLite 建立任务与运行，以真实 `runner.submit()` 启动 worker。
2. worker 调用 stage 和 content_tx 完成最后一次业务消息写入，然后用线程 Event 暂停，尚未返回 wrapper。
3. 调用 `request_cancel()`，读库得到 `state=cancelled, cancel_requested=1`。
4. 释放 Event，worker 正常返回，wrapper 调用 `finish_success()`。
5. 再读库，实际变为 `state=succeeded, cancel_requested=1`，lease 没有变化。

**原因**：`finish_success()` 的更新只约束执行 lease，没有在同一个写事务中约束取消标记和运行当前状态。同一 worker 的 lease 仍合法，因此取消之后仍能覆盖终态。此次整改没有修改这段收尾逻辑，属于既有相邻缺陷。

**推荐修复**：

- 在 `finish_success()` 的同一个写事务内读取并核对 run 归属、当前 lease、取消标记和当前状态，再决定是否转为成功。不要仅在事务外增加一次检查。
- 已取消或 `cancel_requested=true` 时不转成功；已失败、已中断不转成功。已成功可幂等返回。只允许当前合法执行中的运行成功收尾；若兼容 queued 直达成功，需说明真实调用场景，否则限制为 running。
- 只有成功转换实际成立，才在同一事务内把生成任务推进到 review。拒绝收尾时不得顺带改变任务阶段。
- 采用事务先后顺序确定结果：取消先提交则保留 cancelled；成功先提交则后续取消保持 succeeded，并由接口/界面呈现实际已完成状态。
- 不要通过清空 cancel_requested 抹平矛盾，也不要把此问题扩大成删除已写入内容。保留已完成阶段内容，继续遵循现有重试和候选管理规则。
- 核对失败收尾是否有类似终态覆盖，按同样状态原则约束；这是必要排查，不表示本轮已实证该路径有缺陷。

**修复验收标准**：

| 场景 | 必须满足 |
| --- | --- |
| 最后内容写入后、成功收尾前取消，不发起重试 | 最终仍 cancelled，cancel_requested 保留；收尾不额外推进任务阶段 |
| 成功先完成，再点击取消 | 保持 succeeded，返回/显示实际完成状态 |
| 取消后重试 B，旧 A 再收尾 | A 不修改 B 的状态、阶段、候选或消息 |
| 正常成功及重复成功收尾 | 首次成功正常推进阶段，重复调用幂等，不重复产生业务内容 |
| LLM 返回前取消 | 继续保持现有 content_tx 拦截行为，23项晚写入回归不退化 |

回归应使用 Event/屏障固定时序，不依赖随机 sleep。建议扩展 runner 隔离或晚写入套件，再运行相关测试和后端 all；若改动了接口表现，按仓库约定先同步接口文档，并补前端验证。无需为该问题新建页面或功能模块。
