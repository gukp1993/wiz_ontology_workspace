## 2. 方法

### 2.1 基线快照与三方对照

- **base**：`git show 3dc51dc:workbench/ontology_build/retrieval.py` 导出到 `/tmp/prof/retrieval_base.py`（与工作区文件零接触），`importlib` 按路径加载。
- **head**：工作树当前模块 `workbench/ontology_build/retrieval.py`（O0/O2/O3 已实施版），同样按路径加载（该文件仅依赖标准库 hashlib+re，无包副作用）。
- **inst**：基线的**相位计时副本**——对基线源码做 12 处锚点补丁（每处断言恰好命中一次），仅在函数调用外围累积 `perf_counter` 计时，不改任何逻辑；生成后以三方输出逐字节断言保证其与基线完全一致（§2.3）。

### 2.2 合成夹具（tests/retrieve_fixture.py，本轮新增）

对齐创智源实测形态（开发计划 §11：177MB zip、8190 .java/724 .xml、10,819 份物料解析成功、**276,256 条事实**）：

| 维度 | 取值 |
|---|---|
| 规模 | 默认 276,000 条（可调 `--facts`/count、seed）；约 26 条/份物料（对齐 276,256/10,819） |
| kind | java 55% / xml 10% / markdown 25% / llm-fallback 10%（java 主导对齐创智源占比口径；llm-fallback 同时 `module=llm-fallback`、`quality=low`，对齐生产兜底产物） |
| snippet | CJK 长句 + ASCII 标识符（`key=12345` 形态）混排；字节长度五档：<200B 24%、200–1000B 44%、1–2KB 20%、2–4KB 10%、**>4KB 2.7%**，均值约 1KB |
| data | dict/list 嵌套深度 ≤2（页码/关键字/双层 meta） |
| locator | file/line/symbol；materialId/file/module 同组 |
| 命中分布 | 约 2.4% 强命中 include、0.5% 命中 exclude、弱 gram 部分命中为普遍态；其余为 P2 的「未命中事实」主体 |
| scope | PRIMARY_SCOPE（include/exclude/goal/relations 四字段，中英混合，生产口吻）：include 短词表 + 长尾句切出 **85 个 2–3 字弱 gram**，hints 14 个 → 基线 select 第三循环对每条未命中事实 **99 次子串扫描**（对齐 P2「弱词可达上百」） |
| 确定性 | `random.Random(seed)` 纯函数；同 seed 逐条相等；分批与整建两条生成路径输出相等（自检断言） |

模块**不 import 任何 `workbench.*`**，可同时服务基线快照与当前实现。

### 2.3 等价哨兵（剖析前提）

2000 条 × 3 组 scope（storage-primary / billing-trim / mixed-en）三方对比：

- inst == base：selection 三列表 + reasons 全文 + counts **逐字节一致**（计时副本不改逻辑，相位归因可信）；
- head == base：selection 逐字节一致（对在途实现的 R2 等价金样提供独立旁证）；head 的 `tokens` 桶为空（O0 生效）、其余桶（text/byModule/byFile/order/snippetHash）与基线相等。

### 2.4 测量口径与数据质量

- 每个测量点独立进程；`time.perf_counter` 分相计时；RSS 用 `ru_maxrss`，Python 分配峰值用 tracemalloc（`--mem` 点，拖慢约 3 倍属预期，只取其内存数）。
- **干扰剔除**：初轮矩阵的部分 wall-time 点受并发残留进程干扰（如基线 20k index 测得 22.5s，空机复测 9.1s）。凡本文引用的 wall-time 数字均在空机复测确认；RSS 峰值、tracemalloc 分配量与 cProfile **占比**对 CPU 争用不敏感，沿用原矩阵值。
- cProfile 另行采样（20k，base/head 各一份 dump），用于函数级结构佐证；相位占比以 inst 墙钟为准（cProfile 的逐调用开销会放大高频小函数）。
- 276k 规模：head 为**直接实测**；base 全量需 1 小时级且含相同信息，采用多规模实测点的幂律外推（§4），并给出区间。

## 3. 实测数据

### 3.1 规模扫描（墙钟秒，干净空机复测值）

| N（条） | base index | base select | base 合计 | head index | head select | head 合计 | head 加速 |
|---|---|---|---|---|---|---|---|
| 2,000 | 0.15 | 0.08 | 0.23 | 0.02 | 0.07 | 0.09 | 2.6× |
| 5,000 | 0.68 | 0.21 | 0.89 | 0.05 | 0.19 | 0.23 | 3.9× |
| 10,000 | 2.68 | 0.43 | 3.11 | 0.10 | 0.39 | 0.49 | 6.3× |
| 20,000 | 9.1±0.2 | 0.91 | 10.0 | 0.25 | 0.93 | 1.18 | 8.5× |
| 40,000 | 47.0 | 2.10 | 49.1 | 0.38 | 2.02 | 2.40 | 20× |
| 60,000 | ≈151¹ | 5.4¹ | ≈156¹ | — | — | — | ≈29×¹ |
| **276,000** | **外推 2,369–3,600**（§4） | 外推 40–50 | **外推 2,400–3,650** | **2.59** | **42.70** | **45.29** | **≈53–80×** |

¹ 60k 为 inst 相位副本墙钟（较 base 有 ≈3% 计时开销，已按 40k 实测比例校正口径）。

基线 index 的倍增比：10k→20k ×3.4、20k→40k ×5.2、40k→60k ×3.2——**稳定超线性（幂指数 ≈2.0–2.4）**，非固定二次系数，本文按幂律外推并给区间，不外推单点。

### 3.2 build_index 内部占比（inst 相位计时）

| N | token 倒排桶（P1 死工作） | searchable_text 拼接+casefold | snippet 哈希 | 桶登记/簿记 |
|---|---|---|---|---|
| 20,000 | **96.7%** | 1.8% | 0.9% | 0.7% |
| 40,000 | **98.3%** | 0.9% | 0.4% | 0.4% |
| 60,000 | **98.8%** | 0.6% | 0.3% | 0.3% |

cProfile 佐证（base 20k，总量 28.8s）：`build_index` 自身 tottime 25.38s（88%，即 token 循环体的字典/列表操作与 `in list` 线性查重——后者是 C 级 `sq_contains`，计入调用者 tottime）；`index_tokens` 0.91s + `re.findall` 0.41s + `casefold` 0.31s + `_ASCII_ONLY.match` 0.30s（tokenize 合计 ≈1.9s）；`dict.setdefault` 0.22s（49 万次 posting）。

**注意**：正则切分（P1 叙述的「tokenize」）本身只占基线总耗时的 5–7%；真正的大头是 token 桶的**逐 posting 线性查重**——词表被夹具/生产语料的常用词封顶后，桶长随 N 线性增长，`fact_id not in bucket` 的总比较次数 ≈ Σ(桶长²/2)，呈二次方级。这是本剖析对 P1 的**量级修正**。

### 3.3 select_scope 内部占比（inst 相位计时；三循环 = 基线实现结构）

| N | 循环一：强词命中（12 词/条） | 循环二：依赖扩展（全桶扫描） | 循环三：弱词+hints 扫描（99 词/条） |
|---|---|---|---|
| 20,000 | 9% | 13% | **77%** |
| 40,000 | 11% | 24% | **64%** |
| 60,000 | 8% | **42%** | 49% |

- P2 成立：第三循环的逐词子串扫描在 select 内部始终占约一半或更多（20k 处 77%）。
- **意外热点**：依赖扩展循环对每个 relevant 事实做 `(by_module[module] + by_file[file])` **全桶扫描**（每个模块桶 N/12 条）再截取 5 条 → O(relevant × N/12) 二次项，随规模挤占 select 成本（60k 处已达 42%）。P1–P4 与 O0–O3 均未覆盖此项。
- 基线与优化版的 select 成本对比：20k 0.91 vs 0.93、40k 2.10 vs 2.02（s）——**同量级**（O2/O3 合并正则早停的收益与 reasons 复算的成本相互抵消，见 §6.2/§6.3）。

### 3.4 276k 全量实测（head）与内存

| 指标 | 数值 |
|---|---|
| head 276k 合计 | **45.29s**（index 2.59s + select 42.70s），命中分布 relevant 2.39% / excluded 0.49%（与设计一致，规模外推有效） |
| 峰值 RSS | **919.6MB**（其中 facts 本身约 517MB） |
| tracemalloc | index 阶段分配峰值 321.3MB、select 阶段 391.1MB |
| `text` 文本驻留 | **282.6MB**（casefold 后全量驻留索引，基线与优化版相同——O1 未实施） |
| reasons | 276,000 条全部生成（约 90MB 量级字符串） |

基线 276k 内存为分量估算：facts 517MB + texts 283MB + tokens 桶（20k 实测 8.9MB × posting 线性放大至 ≈90–100MB）+ hashes/materials ≈70MB + reasons ≈90MB ≈ **1.05–1.15GB**。R5 口径：优化后峰值下降约 **15–20%**——tokens 消除的贡献被未实施的 O1（texts 仍全量驻留）摊薄；O1 落地后 282.6MB 驻留与双遍构建才会消除，届时内存水位与 select 耗时应有第二波下降。

### 3.5 文本长度敏感性（20k，全部 ≥4KB 档）

| 实现 | index | select | 备注 |
|---|---|---|---|
| base | 72.35s（标准夹具 9.1s 的 **8×**） | 4.07s | 文本 ×5 → 桶 posting ×1.7、扫描成本 ×5 叠加 |
| head | 0.56s | 3.91s | select 仍与 base 持平 |

texts 驻留 110.8MB（标准 20.6MB）。结论：文本越长，O0 收益越大；select 的「合并正则 vs 逐词 in」平衡点对文本长度不敏感（本夹具范围内）。

## 4. 基线 276k 外推与生产 40 分钟对照

幂律拟合 ln T = c + p·ln N（base index，6 个干净实测点）：

- 全点拟合 **p = 2.01** → 276k ≈ **2,369s（39.5 分钟）**；
- 以 40k 点锚定、p 取 1.86–2.16（残差包络）→ **1,705–3,043s（28–51 分钟）**；
- 60k 点显示高段再抬升（GC 代际回收压力，40k→60k ×3.2），若按高段指数 2.4 外推 → ≈3,600s（60 分钟）。

**本文采信区间：基线 276k retrieve+index ≈ 40–60 分钟，与开发计划 §11 生产实测「27.6 万事实约 40 分钟（CPU 满载）」同量级吻合。** 差异来源（如实列出）：①本夹具词表饱和度高于真实语料，会放大桶长二次项；②生产 snippet 上限 500 字（协议 SNIPPET_LIMIT），较本夹具均值 1KB 更短；③生产机器算力未知。三者在方向上相互抵消，量级结论稳健。

## 5. 基线代码事实核对（P1–P4 逐条）

| # | 需求归因 | 核对结果 |
|---|---|---|
| P1 | token 倒排索引零消费 | **成立且比描述更严重**。全仓 grep（workbench/ + frontend/src/）确认 `index['tokens']` 零读取（pipeline 仅把索引整体传给 select_scope，`calc_functions.py`/`flow_sql.py` 的 tokens 为无关局部状态）；且成本主体是桶内 `fact_id not in bucket` 线性查重的二次方膨胀（§3.2），不只是「正则切分浪费」 |
| P2 | 逐词子串扫描主导 | **在 select 内部成立**（第三循环占 49–77%），但 select 只占基线总耗时的 **1–3%**——对总耗时而言 P2 是次要项。99 次/未命中事实的扫描强度与「弱词上百」叙述吻合 |
| P3 | 双遍构建 + 全量文本驻留 | **成立**。texts 282.6MB（276k）常驻；但双遍遍历本身成本可忽略（searchable+hash 合计 <3%），P3 的实际代价在**内存水位**而非耗时 |
| P4 | `_hits` 无早停 | **成立**（retrieval.py:174–175 全量收集）。基线 select 的循环一确实对每条事实同时算 include/exclude 两组命中；消除后收益体现在优化版 select 的持平结果里（§6.3） |

## 7. 结论与建议（供 R1–R7 验收参考）

1. **R1 达成**：各项优化均对应实测热点——O0 对应基线 97–99% 的总耗时（主导热点，成立）；O2/O3 对应 select 探测份额（成立但收益持平）；无「不对应热点的优化项」需要删除。O2/O3 的价值主要是行为等价下的结构简化与早停，性能上中性。
2. **建议关注（意外热点，O0–O3 未覆盖）**：依赖扩展循环的全桶扫描二次项（select 的 13%→42% 随规模上升）。若 276k+ 规模成为常态，select 的 42.7s 中约一半来自此处；可评估按 material/模块预分组或桶截断，属后续算法轮次，不在本轮需求内。
3. **R5 口径**：内存下降为 15–20%（1.05–1.15GB → 919.6MB），主要来自 tokens 消除；texts 驻留（282.6MB）的消除依赖 O1。
4. **基准基建事实（R7）**：`tests/benchmark_retrieve.py` 已由实施方先期提交（d6ed223，自带一套独立夹具），**本轮未覆盖该文件**（写入归属在途任务线）。实测发现其 `--mode profile` 输出为空表：pstats 表行带前导空格（`'   ncalls …'`），脚本的 `line.startswith('ncalls')` 过滤恒假——一行修复（改用 `'ncalls' in line` 或 lstrip），请脚本 owner 处理；`--concurrency N` 占位（V2-10 并发化复用）亦尚未实现。bench 模式验证可用。
5. 本轮新增 `tests/retrieve_fixture.py`（生产规模对齐夹具 + 三组 scope 样例）可作为后续 O1/V2-10 并发化基准的共用夹具源。

## 9. 已知限制
