## 3. G2 三项判定与依据

CLI 汇总报告（`out-real3/report.json.g2`）给出的三项判定：质量门 `fail`（simple 样本，未过项 criticalObjects / ownershipComplete / endpointsComplete / noStructuralIssues / precisionNotRegressed）；compact 收益门 `not_run`；成本取舍 `unprovable`。以下逐项给出结论与数据。

> 说明：`out-real3/report.json` 的 G2 判定在 A 臂首轮成败状态上生成；其质量门结论（fail）在本报告以 A 重跑数据复核后**不变**（重跑后 precision 回归为 2.10pp 超阈、object/property/link 仍全缺、D 仍有 34 条结构问题）。其余两项（not_run / unprovable）同样不变。

| 子问题 | 结论 | 依据数据（D 臂） |
|---|---|---|
| 关键金样类型/属性归属 100%？ | **否** | object 缺失 6/6、property 缺失 41/41、link 缺失 2/4（金样 51 条，命中 2 条）；对应检查 `criticalObjects`/`ownershipComplete`/`endpointsComplete` 全 fail |

判据与警示（重要，避免把一个 2.10pp 的差读成结论）：
1. 该 2.10pp 是**形式判定结果、且样本极稀**：A 侧只有 **1 个**已知成功调用（8344 completion、14 个候选），D 侧 68 个候选；precision 分母为 1+27（A）与 2+134（D）。以如此小的计数判"下降 2.10pp"距离阈值仅 0.1pp，**不构成统计意义上的质量退化证据**，只能说明"D 的精确率不优于 A"。
2. A 首轮 precision=1.0 是**空集默认值**：A 首轮未产出任何候选（candidateCount 0、extra 0），`precision = matched/(matched+extra)` 在分母为 0 时按 1.0 返回。若误用首轮作基线，会得出"precision 下降 98.53pp"的假结论——**本报告不以首轮作基线**。
3. 两臂都不完整，质量数只在"已完成轨迹"上可比：A 完成 3 个作业中的 1 个（1/3，其中 1 个作业从未派发）、D 完成 41/42 目标后因软限停止派发。A 的 8 条结构问题全部是 `danglingRef`（链接端点落在未完成作业），D 的 34 条全部是 `duplicateIdentity`（同身份跨作业重复）——**两臂的失败模式不同**，原因是 A 走固定 20 批、D 走 v3 语义单元装箱，作业边界不同。
4. 已完成的目标仍存在质量缺陷（D 41 个目标完成仅命中 2 条金样；A 14 个候选仅命中 1 条），且 D 的重复身份集中在对象壳层——"运行成功"不等于"结果可用"。
5. 本轮是 compact-v1 与 v3 装箱的**首次真实测量**；无 C 臂（legacy+v3 装箱）与 B 臂（compact+固定批）对照，**D 的低质量不可归因于 codec**，也不可归因于装箱，二者仍混杂。

### 3.2 compact 收益门（B 较 A 正文 token 中位数降 ≥20%）—— 结论：**未测（not_run）**

- 本轮 `--arms A,D`，**B 臂未跑**，C 臂未跑；CLI 判定 `not_run`，说明"compact 收益门无法判定"。
- 即便以 A/D 替代，也不可形成收益结论：A 侧（重跑）只有 **1 个**已知 completion 样本（8344），无法构成有意义的正文 token 中位数基线与置信度；判定函数 `evaluate.cost_compare` 要求两臂 unknown 计数为 0 且中位数可算才给 `compactBenefitGate` 布尔值，否则返回 None（不可判定，不是"未达到"）。
- **本报告不给出任何 compact 收益（正文 token 降幅）数字——该数字未测。**

### 3.3 成本取舍（D 总 token 较 A 增加 >10%）—— 结论：**不可证（unprovable）**

- A 臂（重跑）：6 次调用中 5 次 unknown（TIMEOUT，`usageSource=absent`），仅 1 次已知（completion 8344 / prompt 2567 / total 10911）→ **A 侧 token 总量未知**，无法作分母。
- D 臂：12 次调用中 11 次已知、1 次未知（TIMEOUT）→ 已知 completion **60318**；已知调用 prompt 11181、已知调用 total 71499（派生求和）。按契约口径，存在 unknown 时 `completionTokens`/`totalTokens` 聚合字段置 null（**不冒充 0、不冒充总数**）。
- 因此 **D 较 A 的 token 增幅无法计算**；CLI（首轮报告）判定 `unprovable`。若只拿已知部分作**非正式参考**（不作判定依据）：D 已知 completion 60318 vs A 已知 8344 = 7.2×；D 已知 prompt 11181 vs A 2567 = 4.4×；D 已知 total 71499 vs A 10911 = 6.6×——但 A 只成功 1 个作业（1/3 轨迹）、D 完成 41/42 目标，**完成的工作量不同，两者不可直接相除**；且 D 的 total 仍将随 1 个 pending 作业继续上升。
- 附带事实：D 的已知 completion 60318 在派发第 12 个作业前即触发 campaign 软限 60000 并停止派发（实际略超线，符合"在途可能使最终值略超线"的契约口径）；A 重跑则受限于 3 个作业 2 个 TIMEOUT 失败，未触及 60000 软限。

## 4. 机制结论（逐条，均有数据或代码出处）

1. **截断拆分链路：本轮真实运行未触发，不能在真实口径下声称"已生效"。**
   实测：A 首轮、A 重跑与 D 三个 run 的 `events.jobSplit` 均为 **0**，ledger 中 **没有任何 `finishReason=length`**（A 重跑 finishReasons 仅 `{stop: 1}`、D 仅 `{stop: 11}`，其余尝试为无 finishReason 的 TIMEOUT）。既有生效证据来自 fake 回归：`tests/test_ontology_token_pilot_cli.py`「注入截断脚本：job split 发生、meta 记录拆分次数、usage 含父+子」用例断言 `jobSplit == 1`、父+子尝试全部入账、`knownCompletionTokens` 含父截断+子调用累计。**结论：链路由回归覆盖，真实运行状态为"未测/未触发"。**

2. **预算守卫（COMPLETION_SOFT_LIMIT）在 60318 达线即停止派发 —— 已验证。**
   实测：D `runState=blocked`、`blocking.code=COMPLETION_SOFT_LIMIT`、message 明示"已知 completion 累计 60318 达软限 60000，停止派发"；计划内第 12 个作业 `j-aab1f27576935e30d854` 保持 `state=queued`、`attempts=0`（未产生任何物理调用）；`coverage` 记录 41/1/42。物理调用 12 次 = 11 个作业（其中 1 个重试），未越界派发第 12 个作业。

3. **unknown usage 如实计 1 次、不冒充 0 —— 已验证。**
   实测：D `unknownUsageCalls=1`（该尝试 `usageSource=absent`，TIMEOUT），`knownCompletionTokens=60318` 只累加 11 次已知调用；存在 unknown 时聚合 `promptTokens/completionTokens/totalTokens` 一律 null。A 重跑 `unknownUsageCalls=5`、`knownCompletionTokens=8344`（只累加那 1 次成功调用），`promptTokens/completionTokens/totalTokens` 同样为 null；A 首轮 3/3 全 unknown、`knownCompletionTokens=0`、`durationMs=0`（未知而非"耗时为零"）。三个 run 均未把未知当零计入总量。

4. **失败叶保留、可续跑 —— 已验证（保留与在-run 重试）；"实际续跑"未执行。**
   实测：TIMEOUT 作业 `j-9361c096e85a50f19502` 在同一次 run 内被重试并成功（attempts=2、`networkRetry=1`、最终 `succeeded`）；被预算挡下的作业以 `queued` 状态保留在状态库中，`pilot_plans` 保留完整 12 作业计划（1 行 plan_json）与 41/1/42 覆盖计数，即"只补未成功部分"的续跑输入齐备。**本轮未真正执行续跑命令，续跑行为属未测。**

5. **v3 装箱使作业数远多于固定批（调度差异，符合预期）。**
   实测：A 计划 3 个作业（42 目标 / 每作业固定 20 事实；重跑实际派发 2 个作业、6 次物理调用全为这 2 个作业各 3 次尝试）；D 计划 12 个作业（实派 11 个、12 次物理调用含 1 次重试），候选产出 1–9 条/作业。作业数 3 vs 12 = 4× 差异，源自固定 20 批与 v3 语义单元装箱的策略不同，属预期调度差异；注意两者物理调用数**不可直接当作"效率"对比**（A 的 6 次中 5 次是 TIMEOUT 重试、D 的 12 次中 1 次是重试）。

6. **（本报告新增观察，仅作事实，不作门槛判定）两臂的失败模式不同，指向不同的机制缺口。**
   - D 侧：68 个候选中 9 个语义身份跨作业重复、冗余 17 份，`ess_station` 出现在 5 个作业中；由此产生 17 条 `duplicateIdentity` 记录（×2 金样 = 34）。同时 D 对同一概念产出多套命名（`ess_station`/"储能电站"、"电站"、"energy_storage_station"；`ess_pcs`/"储能变流器"、"功率转换系统（PCS）"、"储能变流器（PCS）"），而评价对齐使用规范化 key 字符串身份，导致 6 个金样对象全部未命中并计入 extra。

## 6. codec 上线建议

**结论：机制可用；compact 收益未实测前不启用——保持在线默认 `legacy-v1`，`compact-v1` 仅作实验能力保留（默认关闭）。**

依据（按 G2 三项口径）：
1. **质量门未通过**：D 未达"关键金样类型/属性归属 100%"（object 缺 6/6、property 缺 41/41、link 缺 2/4），且存在 34 条重复身份（属"已接受结果无重复ID"红线）。D 命中 2/51、extra 134；A 重跑命中 1/51、extra 27（且 A 自身也有 8 条 `danglingRef`）。
2. **compact 收益门未测**：B 臂未跑，正文 token 中位数降幅无任何可证数据。
3. **成本取舍不可证**：unknown 使 A/D 总量不可比（A 5/6 unknown、D 1/12 unknown）；D 已知 completion 60318 已触及软限量级，成本侧无正面证据。

与 `文档/需求/20260920_从物料自动构建本体/本体生成控输出_整合方案与并行开发计划_v3.md` §12 一致：不满足效果门或真实测试未跑时，交付完整 legacy + 自适应分批能力与实验性 compact（默认不启用），明确受阻项，不宣称 compact 已验收；计划亦规定在线 v2 计划默认 `legacy-v1`，仅在能力摘要明确支持且通过 G2 后才启用 compact。

在考虑启用 compact 之前，本报告认为必须先补齐（按优先级）：
1. 提供原 8KB 真实样本并登记内容 hash，重跑 A/B/C/D；
2. 补跑 C 臂（legacy + v3 装箱）与 B 臂（compact + 固定批），使 codec 效应与装箱效应可分离，同时给出可算的正文 token 中位数；
3. 消除跨作业重复身份（`duplicateIdentity`）与同义词多命名碎片（对象同名归一），并让作业边界不割裂链接端点（A 重跑的 `danglingRef` 已显示该风险）；
4. 让 provider 返回/记录 reasoning 与 completionBytes，补齐成本口径；
5. 排查 TIMEOUT 频发（三轮共 9 次），否则大轨迹真实试验无法收敛——两臂本次都未能跑完。

**本轮已知可用（在真实调用中被行使、未见违背契约）**：campaign 预算守卫（软限即停派发）、unknown usage 如实计账不冒充零、失败叶保留且同 run 内重试可用、v3 装箱按语义单元产出小批作业、CLI 退出码 2 与报告 notes 如实反映受阻原因。
