## 1. 问题

用户实测反馈：抽象本体定义执行很长（创智源 60 条事实、2 批即 190 秒；创智源 zip 全量 13 批需小时级），但执行进度是**黑盒**：

| 编号 | 问题 | 根因 |
|---|---|---|
| P1 | **运行中看不到日志**：不知道模型返回了什么、每批抽出了哪些候选、有没有截断/拆批 | pipeline 每批积累的 notes 列表仅在 Python 内存中，`runner.submit` 丢弃返回值——**notes 从未落库**；`run_view()` 已返回 checkpoint 但 checkpoint 中无 log 数组 |
| P2 | **失败后看不到哪些批成功/失败** | `checkpoint.batches` 只有 `done/failed` 批号列表，没有每批产出的候选名与数量 |
| P3 | **生成中看不到候选产出** | `run_view().progress` 已含 `candidates` 计数（runner.stage 写入），但**没有候选名列表**且前端 progressText 只显示 done/total |

## 2. 行业对标

| 项目 | 做法 | 我们可借鉴的 |
|---|---|---|
| **Palantir Pipeline Builder** | 每个节点有独立实时状态（运行中/完成/失败），用户能看到每个节点的输入输出量 | 批次级状态实时可见 |
| **Neo4j / TigerGraph** | 逐 chunk 持久化：处理完一个 chunk 立即存 ID，恢复时只处理未完成的 | 已有批次检查点，需**把已完成的批次详情也存进去** |
| **行业共识** | 逐 chunk 持久化 + 小批量 + 重试退避 + 后处理校验 | 已实现后两者；**缺前两者的可观测性** |

## 3. 方案

### 3.1 核心思路

**不改执行逻辑，只加可观测性**：现有的批次并发、检查点、重试机制不变，只做一件事——

在 `pipeline.py` abstract 循环内，**每批完成时**向 `checkpoint_json.generate.log` 追加一条人类可读的中文日志行（随已有的 `_checkpoint()` + `update_run(checkpoint=…)` 同一写事务写入，天然持久化）。

`checkpoint_json` 已在 `wb_build_runs.checkpoint_json` 列持久化、`run_view()` 已通过 `run_checkpoint_view()` 返回——**不需要新列、不需要新表、不需要改 `run_view()`**。

不引入消息队列 / WebSocket / SSE——现有 1.5 秒轮询 + checkpoint_json 持久化已足够。

### 3.2 后端改动

| 编号 | 文件 | 改动 |
|---|---|---|
| C1 | `workbench/ontology_build/pipeline.py` | abstract 循环内：①每批完成时向 checkpoint 的 `generate.log` 数组追加一行中文日志（格式见下方）；②截断拆批子批也记；③log 数组上限 500 条（超限移除最早）；④log 随每次 `_checkpoint()` 一并写入 `update_run(checkpoint=…)`（S4：log 必须随每次 checkpoint 写库，不能只在内存追加——否则重启丢失）。`notes` 列表（已有的 `_note()` 积累）也随每批 checkpoint 中的 extra 传入 `generate.notes`，使运行中可见 |
| C2 | `workbench/ontology_build_routes.py` | **无需改动**——`run_view()` 已返回 `checkpoint`（含 `generate.log` 与 `generate.notes`），前端 1.5 秒轮询天然拿到 |

日志行格式设计（服务端生成，中文，追加式）：

```
[批 3/13] 开始抽取（20 条事实）
[批 3/13] 完成：候选 12 个（对象 3、属性 5、链接 2、动作 2）
[批 5/13] 输出截断，已自动拆批重试（20→10+10）
[批 5a/13] 子批完成：候选 6 个
[批 5b/13] 子批完成：候选 4 个
[对齐] 跨批合并：37 → 33 个候选（合并 4 组同名同类型）
[校验] 通过 33 个；3 个候选证据引用被降级（捏造 ID）
```

### 3.3 前端改动

| 编号 | 文件 | 改动 |
|---|---|---|
| F1 | `types.ts` | `RunCheckpoint` 增加 `log?: string[]` 与 `notes?: string[]` |
| F2 | `BuildProgressPage.vue` | 进度条下方新增**可折叠日志区**：逐行渲染 `checkpoint.generate.log` + `checkpoint.generate.notes`（合并按时间序、最新在下、自动滚动到底部）；运行中实时更新（已有 1.5 秒轮询天然覆盖）；**折叠时显示最新一条** |
| F3 | `BuildProgressPage.vue` | 批次检查点区块扩展：已完成的批次显示「批 N ✓（候选 M 个）」而非只有批号；失败批显示具体错误原因 |

### 3.4 不做

- **不引入 WebSocket / SSE / 消息队列**——1.5 秒轮询 + checkpoint_json 持久化已足够；
- **不改 LLM 调用逻辑**——截断拆批、并发收集、瞬态重试等已由 perf 提交实现，本需求纯加观测；
- **不改检查点 / 重试架构**——V2-8/V2-10 已验收，不动；
- **scan 侧逐材料实时日志**（C3 原第三项）：scan 已有 `runner.stage` 逐材料推进进度（done/total），暂不再加逐材料日志行——**移出第一批**，后续如需再做。
