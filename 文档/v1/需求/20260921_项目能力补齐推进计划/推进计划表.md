# 本体工作台能力补齐推进计划表

日期：2026-09-21。版本：v1。状态：推进建议，待逐项确认。

本文将当前功能缺口分析转为可跟踪的推进表。用户本轮要求计划表，因此只交付本文件，不同时生成需求、原型和开发指令。本表不是一次性授权开发清单，不修改既有延期决定。

## 1. 推进原则

- 先用现有能力完成一个储能业务试点，再按实际阻碍补功能。
- 已有自动构建、编排测试、配置迁移等能力不重复建设。
- 区分代码已合入、独立验收通过、主工作台已更新、真实业务验证通过四种状态。
- 所有任务初始均为“未开始”或“待决策”，不把此前功能完成状态写成本计划执行结果。
- 不预排日历日期或承诺工期；每项范围确认后再估时。可由用户填写负责人、目标日期和实际进展。
- Codex负责分析、需求和独立验收；zcode或指定harness负责开发、自测。业务口径由用户或用户指定的业务负责人确认。
- 先完成P00～P03。MCP、历史恢复、动作执行等延期项必须单独确认是否恢复。

## 3. 建议实际推进顺序

```text
P00 基线核对
  → P01 准备样本
  → P02 使用现有能力跑试点
  → P03 确定真正阻碍
  → 用户选择后续批次
```

建议下一批优先讨论P04、P05，同时可以做P07质量评估和P08既有辅助填写需求的范围确认。P09需要用户决定是否恢复。

P10和P11不作为前面试点的强制前置：尚未建立MCP时，试点可以停在配置交付检查，但不能把这一阶段记成端到端问数成功。

P12、P13不因进入本表就自动恢复。先解决实际阻碍，再安排交互优化或动作执行能力。

## 4. 试点场景与验收目标

| 场景 | 检查重点 | 本轮试点期望 |

| 储能系统无实体表 | 虚拟业务对象、登记实例、设备成员 | 不为满足表映射强行虚构数据库表 |

## 5. 每项推进的交付与停止点

### 5.1 需求阶段

对需要开发的条目，先确认范围，再交付交互原型、需求说明、开发计划、执行指令。放在 `文档/需求/YYYYMMDD_需求名称/`；已有同主题目录优先迭代，不另起冲突版本。

正式开发计划必须拆到可独立交付的任务，补齐输入协议、业务代码负责文件、共享文件唯一owner、验证命令和并行组。先冻结协议再并行；不让多个agent同时改同一文件。不具备多agent能力时按依赖顺序实施，不虚报并行。

本表负责产品推进顺序，不替代各条目的代码级实施计划。

### 5.2 独立环境与授权

主仓库：`/Users/gukepeng/Desktop/ZHDL/code/wiz_ai/wiz_kq_builder_v2`。

开发cwd应为该主仓库下 `worktree/<任务名>/`，不是主目录。创建前核对git状态、已登记工作树、最新已提交本地main及remote；不自动复制未提交内容，不盲目pull。登记实际base SHA、分支、工作树、空闲端口、数据根、Python环境与运行命令，不提前虚填。

使用独立 `WIZ_WORKBENCH_PORT`、`WIZ_WORKBENCH_ROOT`，核对或移除继承的 `WIZ_DATABASE_URL` 等覆盖项。主服务18765及8765不可占用。依赖、构建产物、凭据、数据和测试账号按任务隔离，默认合成数据；真实数据使用另获授权。分支浏览器测试使用隔离会话。

可直接使用的阶段指令模板：

| 阶段 | 用户指令模板 | 执行者与停止点 |

| 创建 | 为【任务ID／需求路径】创建worktree，从最新已提交main建立独立分支与目录，登记端口和数据目录。先不要开发。 | 默认实施harness；只建环境登记，不安装依赖、不启动服务 |

可在同一指令明确创建并开发，或验收通过后集成；没有明确授权的阶段不得自动推进。

### 5.3 验证、集成和收尾

分支运行相关测试；前端有改动时完成构建与页面验证。记录真实命令、结果、未测范围，不把mock结果写成真实业务通过。

Codex作为集成负责人串行处理获授权任务。跨工作树资源登记使用Git公共目录下 `workbench-tasks/` 并加锁，不用各自.runtime充当全仓锁。临时集成目录也位于主仓库 `worktree/` 下。从最新main组合已验提交，普通代码冲突自行处理，需求冲突交用户决定；核对接口、迁移链和依赖，并验证组合后的实际提交。

main存在其他未提交内容时不stash/reset清场；main前进则重新组合并补验。条件满足才更新main。主服务构建重启另按授权，代码合入不代表运行已更新。

合并成功后，按已授权默认清理本任务开发和临时集成环境：先保存SHA与证据，核对进程、路径、未提交及未合入内容；只删除归属明确且可丢弃的工作树、分支、依赖、端口和隔离数据。遇未知数据或他人写入保留并报告，不强制清理。回退优先git revert；数据库与附件单独处理。

每项最终报告：分支、实际SHA、URL、验证结论、合并状态、主服务是否更新、清理和保留项。通过协作脚本read/record更新共享上下文，不手改自动摘要。
