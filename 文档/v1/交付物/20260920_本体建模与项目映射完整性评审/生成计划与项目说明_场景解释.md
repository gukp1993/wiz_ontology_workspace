# 生成计划与项目说明：场景解释

日期：2026-09-20  
状态：讨论说明。以下示例不代表真实业务数据；建议的消费原则尚未确认为实施需求，也不代表已经实现。

## 1. “生成计划”为什么需要区分？

以用户问“明天储能怎么充放电”为例，实际上可能有四种意思。以下都是假设场景：

| 用户说的话 | 系统应该做什么 | 是否改变业务数据或设备 |
|---|---|---|
| “查一下明天的充放电计划” | 查询业务系统已经保存的计划 | 不改变 |
| “根据当前情况，帮我算一份明天的计划” | 查询必要数据，运行算法，返回一份候选计划 | 可以不改变，只返回计算结果 |
| “把这份计划保存下来” | 在业务系统创建计划记录 | 改变业务数据 |
| “把这份计划下发执行” | 向 EMS 提交计划，并查看受理和执行状态 | 可能影响设备运行 |

例如，算法得到一个候选结果：

> 00:00—06:00 充电，18:00—21:00 放电，其余时间待机。

**把这个结果显示给用户，不代表已经保存，更不代表设备会执行。** 具体时段和功率必须由真实数据与算法得到，不能由大模型随意编造。

对应到我们的建模：

- **已有计划**：如果需要查询日期、状态、明细、关联设备，可以建“充放电计划”对象。
- **计算候选计划**：可以由计算函数或编排提供，不一定立即创建计划实例。
- **保存、下发计划**：属于明确的业务操作，可以定义为动作并映射业务接口。

之前提到的 Java 计划生成逻辑，究竟只计算、会写计划表，还是还会下发，需要查看其实际行为才能判断，不能仅凭名称认定。

**针对智能问数，建议默认先支持查询已有计划；用户明确要求试算时生成候选结果。保存和下发单独处理，不因为问一句“明天怎么充放电”就自动执行。**

## 2. “项目说明”是什么意思？

就是我们现在对象映射中，放在具体配置上方的那个**说明文本框**。它描述“这个项目中，业务概念怎样对应实际数据和处理规则”。

先区分两种内容：

| 位置 | 储能簇 SOC 示例 |
|---|---|
| 本体业务定义 | SOC 表示电池的剩余电量百分比 |
| 项目映射说明 | 本项目实时 SOC 从 Redis 获取，Key 为 `m_storage_cluster_phase-{id}-soc`，返回值范围为 0～100 |

本体解释“是什么”，项目说明解释“在这个项目里怎么得到”。

关键在于：**说明中的某些句子会直接改变查询结果，不能都当作普通备注。**

看三个例子：

| 项目说明 | 对智能问数有什么影响 |
|---|---|
| “额定功率来自设备台账” | 主要帮助理解；如果已绑定明确字段，按绑定读取即可 |
| “只统计 `del_flag=0` 的设备” | 是查询条件；忽略它就可能把已删除设备算进去 |
| “先查 `s_attr_scada` 定位测点，再查 `s_yc` 定位采样表和字段，最后返回时间和值” | 是完整取值步骤；消费者需要按步骤真实查询 |

假设你问：

> 储能系统的额定容量是多少？

项目说明写：

> 统计当前园区所有未删除储能设备的额定容量之和。

但结构化 SQL 配置却是：

```sql
SELECT SUM(capacity) FROM m_storage_phase;
```

这个 SQL 没有园区和删除条件。此时说明与配置可能不一致，系统不能悄悄忽略说明，也不能擅自猜测园区字段和范围。

这就是此前需要确认的问题：**你写的说明，是帮助人理解，还是也要作为智能问数执行的依据？**

结合之前的需求，目前的理解是：希望它也能成为执行依据。例如：

> 我暂时不搭编排，把 SOC 的取值步骤写清楚，智能问数也能理解并通过工具查询。

这个方向可以保留。建议具体原则是：

- **已经有完整、经过验证的配置**：直接调用，不必每次重新推理。
- **只有说明**：智能问数理解步骤，再通过 MCP 提供的受控能力真实查询、计算。
- **说明补充了过滤或计算条件**：执行时必须考虑。
- **说明与配置冲突，或缺少必要信息**：明确提出问题，不能猜数据、猜字段或静默选择一方。

界面仍然可以只有一个“说明”文本框，**不需要再让用户选择“备注模式”“执行模式”**。但在消费端，需要明确哪些内容已经具备执行条件、哪些还需要澄清。

这部分是建议的消费原则，目前不能把它说成已经实现的能力。
