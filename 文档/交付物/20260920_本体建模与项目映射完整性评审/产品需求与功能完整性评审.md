## 1. 整体判断与评审边界

**本体建模的基本框架已经具备，当前最大的不足是“配置完成之后，能否可靠地得到业务结果”，以及配置变化后如何保证结果仍然可信。**

不建议现在继续增加大量本体概念或新菜单，优先把已有的对象、属性、链接、动作与项目实现贯通。

本轮核对了共享上下文、需求文档、前后端实现和接口路由，没有调用真实业务数据或设备接口。以下是产品与源码层面的评审，不等同于完整运行验收。正在进行的图谱迁入改动不纳入本轮验收结论。本文件记录评审时点的事实，后续实现变化需重新核对。

本评审以当前项目为依据，未使用未经核实的 Palantir 功能对比作为建议理由。

首先需要确定：**工作台负责输出配置给其他系统消费，还是自身也负责查询属性、生成计划、调用业务动作？**

- 如果只负责配置交付，执行能力可以在外部，但必须有明确的消费协议和验收方式。
- 如果希望直接在工作台得到业务结果，下面的执行断点就需要补齐。
- 不能把尚未建设运行时，直接判定为配置平台必须立即补齐的缺陷。

## 3. 本体建模：语义口径和生命周期

优先级：P1 表示直接影响业务正确性或闭环；P2 表示影响复用与维护；P3 表示可暂缓。优先级仍受工作台运行边界影响。

| 问题或缺失能力 | 当前事实与依据 | 受影响的业务场景 | 建议方案 | 所属层级 | 优先级 |
|---|---|---|---|---|---|
| 数值的业务口径没有充分贯穿计算 | 已有百分比、后缀等显示格式；尚未看到统一的单位换算与计算量纲约定 | SOC 是 0.8 还是 80；容量是 kWh 还是 Ah；功率是 kW 还是 W | 明确属性值的标准口径、来源转换和显示格式三者的区别，不一定立即增加单位管理菜单 | 本体语义＋项目映射 | P1 |
| 实时值的有效性描述不足 | 时间序列有时间字段、编码、时区等配置；未发现统一的新鲜度和结果质量约定 | Redis 返回昨天的 SOC，仍被当作当前值 | 取值结果除 value 外，应能提供采集时间、质量状态、来源；允许配置过期判定 | 项目取值 | P1 |
| 业务规则与实际实现缺少可追溯关系 | 规则主要是名称、业务定义、内容、输出及对象关联 | 修改设备 SOC 计算规则后，不知道哪些编排需要调整 | 增加可选的“实现此规则”引用关系及影响提示；不强制把每条规则编译为程序 | 本体与项目衔接 | P2 |
| 动作的动态业务输入表达有限 | 本期简化动作没有输入参数，属于此前明确暂缓 | 修改名称需要新名称；生成计划需要计划日期 | 零参数动作保持简单；确有场景后再支持可选业务输入，项目负责映射接口参数 | 本体动作＋项目映射 | P2；动作落地时升 P1 |
| 复杂类型与映射通道没有完全对应 | 本体有数组/结构体；当前编排属性绑定拒绝对象输出，列表主要放行为时间序列 | 将完整计划作为结构化结果返回 | 明确目前可建模但不能绑定的范围，再决定支持复杂值，还是将其建为独立对象 | 本体与项目衔接 | P2 |

### 3.1 显示格式不能替代数据口径

把数值 `80` 显示成 `80%`，不能告诉计算引擎乘容量时是否需要除以 100。也不意味着必须恢复繁杂的属性表单，可以先在映射转换与计算输入检查中解决。

容量还需要区分能量容量与电荷容量，例如 kWh 与 Ah 不可直接作为同一量纲相加。字段名称相同不意味着业务口径一致。

### 3.2 四类概念的职责

| 概念 | 职责 |
|---|---|
| 业务规则 | 业务要求怎样计算、判断或约束 |
| 计算函数 | 一个具体、可调用的计算实现 |
| 函数编排 | 组织查询、计算和调用步骤 |
| 动作 | 业务上希望完成的操作 |

一条规则可以有多个项目实现；一个动作可以调用接口或编排。它们不应成为四个重复填写相同说明的地方。

| 本体更新后升级项目 | 已有版本比较及升级预检 | 全依赖影响定位、编排版本固定、受影响业务样例重验 |

### 6.1 设备 SOC

可先明确业务公式：

```text
设备 SOC = Σ(簇 SOC × 簇容量) ÷ Σ(簇容量)
```

这需要业务确认 SOC 数值范围、容量口径、参与的簇、缺失/过期 SOC 的处理以及分母为零的情况。公式能写出来，只完成一部分设计。不同容量口径是否适合加权，也应由业务确认。

“剩余电量”是否单独建为属性，取决于它是否需要独立查询、展示或复用；仅为计算中间结果时，留在编排内部即可。

### 6.2 充放电计划

- 查询已有计划：读取计划对象及其明细，不应隐式触发重新生成。
- 生成明天计划：如果只是试算，可以返回候选结果；如果会创建、保存或下发计划，则属于有业务效果的操作，应通过明确动作完成。
- 是否需要计划对象与明细对象、是否保存候选版本，取决于后续查询、审批和执行需求；本轮不强制新增这些模型。

## 7. 最值得优先解决的五个问题

1. **属性绑定后的统一取值验证。** 回答“这个实例的这个属性能不能取出来”，是最多现有配置共同缺少的出口。
2. **确定性计算、值口径与质量检查。** 优先覆盖 SOC、容量汇总，避免结果看似合理却无法信任。
3. **项目发布固定编排依赖。** 多项目复用越多，公共编排变化越需要控制。
4. **说明与结构化配置的执行关系。** 当前可以填写两者，但消费规则不完整，容易出现能写、能发布、不能用。
5. **统一的影响提示与重验机制。** 本体、编排或表结构变化后，应明确哪些配置需要重新检查。

如果近期必须从工作台实际控制设备，动作执行与结果确认应提升到前三位；如果仍由业务系统负责执行，可以暂缓工作台内执行。

## 8. 可以暂缓的能力

- 对象继承、复杂接口体系、多重分类等高级本体能力，当前没有足够明确的阻塞场景。
- 更多数据源类型，先完成 MySQL、Redis、HTTP 的现有链路。
- 大规模图算法、自动本体推理、复杂权限审批体系。
- 计划自动调度，先明确生成结果及保存方式。
- Python 沙箱不必立即建设，可以先用确定性的集合计算满足实际需要。

## 9. 建议简化或收敛的设计

1. 业务规则库保留语义职责，执行能力统一在编排维护。旧取值规则与契约保持兼容，不继续扩展成平行产品线；当前菜单已向此收敛。
2. Python 节点明确标识为 LLM 求值，避免误以为运行了 Python。
3. 简单 SQL 求和不要求再建独立规则或关联聚合模块。
4. 项目说明允许为空，字段直取不必重复写说明。
5. 保存、校验、发布页面避免让用户误以为配置发布等于业务上线。

## 10. 待用户确认的产品选择

| 选择 | 需要确认的问题 | 当前建议 |
|---|---|---|
| 运行边界 | 工作台是否负责实际业务运行？ | 先补齐只读取值验证，写操作另设明确边界；不急于做完整生产调度系统 |
| 说明语义 | 说明是辅助解释，还是可直接执行的实现依据？ | 此前倾向后者；保持该目标就需要解释与冲突处理机制，不能当普通备注或被结构化配置悄悄忽略 |
| 值口径 | 是否接受统一的内部值口径？ | 例如 SOC 内部统一一种范围，映射负责转换，显示允许不同，保证跨项目计算可靠 |
| 动作目标 | 近期只配置接口，还是执行并确认完成？ | 前者已有基础；后者需要明确范围升级，不能只增加执行按钮 |

以上建议等待确认，不自动授权任何功能实施或真实数据修改。
