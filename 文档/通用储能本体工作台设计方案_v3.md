# 通用储能本体工作台设计方案（V3）

日期：2026-09-10
状态：修订稿。在 V2 基础上修正契约、校验、版本与保存规则，尚未实施。已确认方向与待确认细节分别标注。
配套交互图：[本体建模与项目绑定交互图](本体建模与项目绑定交互图.html)

## 0. 本版修订说明

相对 V2 的主要变化：

1. 删除必填的“公式型／取数型”分类，避免将项目实现方式带回通用本体。
2. 保留结构化输入输出，界面通过引用自动填充名称和类型，技术标识自动生成，说明选填。
3. 输入参数类型与适用对象分别描述，取消两者不一致即报错的规则。
4. 首期仅支持固定版本、主动升级；新增必需输出属于破坏性变更。
5. 区分配置校验与执行验证，不用自然语言实现说明代替实际输出验证。
6. 明确草稿、基础文件和发布版本的读取边界，以及多文件整体保存机制。
7. 将语义变化纳入兼容性审查，不把显示名称变化直接视为破坏性变更。

配套 HTML 仍为第一版流程草图；字段与版本细则以本文为准，确认后再同步细化交互图。

## 1. 已确认的目标

建设一份可被多个实际项目复用的通用储能本体。不同项目使用不同数据库、Redis 或接口，不应因此复制或修改本体定义。

本体包含四类内容：对象类型、链接类型、属性、计算定义。计算定义在本体中表示通用业务契约，具体处理规则由各项目实现。

工作台明确划分为两个区域：

| 区域 | 主要使用者 | 负责内容 |
| --- | --- | --- |
| 本体建模 | 储能业务专家、本体维护人员 | 通用定义、业务含义、输入输出约定 |
| 项目绑定 | 开发／实施人员，项目业务人员协助核对 | 数据映射、属性来源、计算实现、项目连接与参数 |

这些是维护职责划分，第一阶段不默认增加账号角色和权限系统，但文件结构预留归属信息字段，避免后期迁移历史数据。

本方案借鉴统一契约和多种实现的思想。"计算契约"是本工作台的设计概念，不将它直接等同于 Palantir Interface。契约的适用对象单独描述，不由输入类型强制推导；不引入独立接口层，见 3.2。当前不新增一个与计算定义重复的"接口契约"菜单。

## 2. 现有功能与调整范围

以现有 Vue 工作台、列表详情布局及图编辑器为基础，保持管理后台风格，不重写全部页面。

| 现有功能 | 拟议调整 |
| --- | --- |
| 新建、切换本体 | 保留，作为本体建模入口 |
| 对象类型、链接类型 | 保留现有字段及列表／图编辑能力 |
| 属性管理、共享属性 | 保留；把"值的来源"、函数选择、输入来源移到项目绑定 |
| 计算定义 | 保留列表与详情；从五项混合描述调整为通用契约，本版细化为结构化签名与通用业务约定 |
| 项目数据映射 | 扩展为项目绑定；保留对象列表与映射详情，增加独立项目选择和计算实现 |
| 校验、草稿、发布快照 | 保留交互习惯，拆分本体校验与项目校验，分别保存和发布；发布增加变更类型标记 |
| 实例与计算预览 | 放在项目上下文中；继续明确真实执行与内置示例的区别 |
| 动作、接口、值类型的隐藏内容 | 不在本次主动恢复或删除，历史数据兼容保留 |
| 历史导入材料、教学示例 | 保持独立，不自动成为新本体或新项目的内容 |

现状限制：当前草稿将本体和项目内容保存在一起；发布是本地 ZIP 快照。自然语言计算规则尚不能自动执行任意 Redis、SQL 或函数编排。新方案不能把"填写完成"显示成"已可运行"。

## 3. 页面组织与操作流程

### 3.1 本体建模区域

顶部展示当前本体与草稿／版本状态；左侧按以下顺序组织主要功能：

1. 对象类型。
2. 链接类型。
3. 属性管理。
4. 计算定义。
5. 校验与版本。

本体画布和建设流程作为辅助入口保留。对象、链接列表与画布编辑同一份定义。画布节点仍以对象类型为主，属性通过详情维护；本轮不要求把属性全部变成图节点。

建议流程：新建／选择本体 → 对象与链接 → 属性 → 计算定义 → 校验 → 发布版本。该顺序提供指引，不强制逐步完成；可以随时返回修改或保存未完成草稿。

### 3.2 项目绑定区域

进入后先选择或新建项目，再展示该项目引用的本体及版本。

保留现有"左侧对象列表、右侧详情"的方式。右侧按对象分为：

| 详情区域 | 用户操作 |
| --- | --- |
| 对象数据映射 | 配置数据源、表、主键和标题属性 |
| 链接映射 | 配置链接对应的关联字段或关联方式 |
| 属性来源 | 选择直接字段来源或计算实现的输出 |
| 计算实现 | 查看适用于该对象的计算契约，填写本项目的具体实现 |

项目基本信息、数据连接、参数和校验作为项目级入口，避免在每个对象下面重复填写。

计算契约的输入类型与适用对象分别维护：

- 输入类型描述调用所需的信息，不等于能力所属对象。例如输入设备和储能簇，不意味着能力必须同时归属于两类对象。
- 适用对象用于对象详情中的能力展示与筛选。系统可根据输入给出建议，也可在从对象详情创建时预填，但不会因其与输入类型不同而报错。
- 输入参数仍须逐项绑定；选择适用对象不能替代输入绑定，也不能使不匹配的参数变为合法。
- 无对象归属的计算在项目级“全部计算实现”中维护，避免只在对象详情展示导致入口缺失。
- 适用对象建议为可选多选项，具体表单位置待确认。

### 3.3 跨页面跳转

| 起点 | 操作与落点 |
| --- | --- |
| 对象类型 | 打开该对象的属性或定位画布 |
| 本体对象 → 项目绑定 | 已有明确项目上下文时定位对应对象；否则先选择引用此本体的项目 |
| 项目属性来源 | 选择计算实现，并定位该实现详情 |
| 项目计算实现 | 查看只读的本体契约，可跳转到对应本体版本 |
| 计算契约 | 按需查看哪些项目实现了它，不在此编辑项目实现 |
| 校验结果 | 点击问题定位到对应页面和字段 |

本体和项目各自拥有保存状态。切换本体、项目或版本时，沿用未保存修改提示，不静默丢弃编辑。

## 4. 本体层填写内容

### 4.1 对象类型与链接类型

沿用现有简洁表单，暂不增加对象边界、身份规则等额外字段。

| 类型 | 填写内容 | 示例 |
| --- | --- | --- |
| 对象类型 | 名称、业务定义 | 储能簇：由多个电池模块组成、能够识别和监测的电池集合 |
| 链接类型 | 正向名称、业务定义、起点、终点、数量关系 | 储能设备—包含—储能簇；一对多 |

稳定标识由系统生成并维护引用，不增加业务专家必填项。

### 4.2 属性

必填沿用名称、业务定义、基础数据类型。保留共享属性复用及已有可选格式化设置，不在本轮重新扩展枚举和约束系统。

示例：储能簇的 SOC，表示荷电状态，数值采用 0～100 百分数口径。此处描述单位口径不意味着已经实现运行时数值校验。

本体属性不保存数据库字段、Redis Key、项目函数实现标识或输入取值方式。同名共享属性的业务语义仍由本体维护，实际取值方式可以因项目、对象类型而不同。

### 4.3 计算定义：通用契约

输入输出采用双轨制：**结构化签名**（机器可校验）加**自然语言补充**。签名结构化是项目校验（检查契约与实现匹配、输入输出绑定完整性）的前提，不依赖是否引入执行器。

建议字段：

| 字段 | 建议要求 | 说明与示例 |
| --- | --- | --- |
| 名称 | 必填 | 查询储能簇实时 SOC |
| 业务说明 | 必填 | 获取指定储能簇最新采集的 SOC |
| 输入参数 | 明确有无；选择类型或语义引用，名称自动带出，说明选填 | 储能簇：引用储能簇对象类型 |
| 输出 | 必填，至少一项；选择类型或语义引用，名称自动带出，说明选填 | SOC：属性引用，数值，0～100 百分数口径 |
| 通用业务约定 | 按需填写，默认折叠 | 无有效数据时不使用 0 冒充有效 SOC |

输入、输出的类型引用优先引用已定义的对象类型或属性，允许使用基础数据类型；自然语言说明作为补充，不重复承载类型和单位信息。输出为具名列表，多输出是其自然结果，不预设所有计算只能输出一个属性。

不设置必填的公式型／取数型分类。一个通用能力在项目 A 可以直接取数，在项目 B 可以由多个数据源计算得到；只要满足契约语义，就可以采用不同实现。

通用业务口径仍可集中维护，例如“剩余电量＝额定电量×SOC÷100”。具体 SQL、Redis 访问、公式执行和组合调用步骤放到项目实现中，不根据本体分类推断执行方式。项目不得改变通用口径。

表单建议：每行先选择已有对象或属性，自动带出名称和类型；允许修改显示名称，说明选填。选用基础类型时填写一个业务名称即可。技术标识由系统生成，用于稳定绑定；名称修改不改变标识。同一参数列表或输出列表内标识唯一。后端保留结构化引用，页面不要求业务专家填写技术参数名。

首期所有声明的输入和输出均按必需项处理；无输入须明确声明。可选参数、默认值、可空输出等暂不隐式引入，后续按需要扩展。

"实时"涉及数据新鲜度。采集时间作为可选输出处理，采用**可选声明、声明即必须**规则：契约不强制包含采集时间输出；一旦声明该输出，项目实现必须返回它，且不得用查询时间替代缺失的采集时间。属性来源绑定引用该输出时同样遵守此规则。

不在此填写 SQL、Redis Key、外部连接地址和项目调用步骤。

## 5. 项目层填写内容

### 5.1 新建项目

建议最少填写项目名称、引用本体和引用版本。项目标识自动生成。项目并不复制一份可自由修改的本体，而是引用本体定义。首期固定引用已发布版本，升级由项目人员主动发起，见第 8 节。

### 5.2 对象与链接映射

复用现有数据表、主键、字段映射交互。数据库外键可以实现本体链接；如果现有字段式映射无法覆盖关联表或复杂关联，应明确提示暂不支持，不能仅填写文本就声称已执行。

### 5.3 计算实现

由项目人员选择本体计算契约，上方只读展示结构化签名（输入参数、输出）及业务约定，下方填写：

| 内容 | 示例 |
| --- | --- |
| 使用的数据连接 | 已配置的实时遥测 Redis |
| 项目处理规则 | 根据储能簇标识读取 soc_{id}，将结果转换为 SOC 数值 |
| 必要的项目参数 | 数据新鲜度阈值等，按实际实现需要配置 |
| 所属环境 | 预留字段，区分测试／生产规则；首期默认单一环境，不强制填写 |

沿用用户已选择的自然语言描述方式，不恢复查询／公式／编排三种复杂表单。没有外部数据需求的实现不强制选择连接。密码与密钥保存在受保护配置中，不写入自然语言规则。

初期建议同一个项目对同一个计算契约只配置一份有效实现；多个实现及条件选择是否需要支持，另行确认。环境字段为将来的测试／生产分离预留，避免两套规则挤在同一条记录里。

包含通用公式的契约同样由项目配置实现。通用公式只读展示，项目描述输入获取和具体处理，不重复维护另一份可独立修改的业务口径。

为支持配置校验，实现记录须包含结构化的输入绑定及输出声明：由契约预填并关联稳定标识；来源可以是当前对象、字段、常量或其他计算输出。首期不支持的来源应明确提示。自然语言处理规则只描述处理过程，不作为类型匹配或已返回结果的证明。具体绑定控件待确认。

### 5.4 属性来源

从现有属性管理迁移到项目内，针对具体对象类型的属性配置：

| 来源方式 | 维护内容 |
| --- | --- |
| 数据字段 | 已配置对象数据源中的字段 |
| 计算结果 | 计算契约对应的本项目实现、输出字段及输入来源 |

示例：储能簇 SOC → 查询储能簇实时 SOC → 输入取当前储能簇 → 使用 `soc` 输出。

本方案不强制每个计算都关联属性，计算可以作为独立能力使用。属性来源与计算实现允许来回维护，不要求严格先后。

## 6. 完整储能示例

| 内容 | 通用本体 | 项目 A | 项目 B |
| --- | --- | --- | --- |
| 储能簇 | 对象类型定义 | 映射项目 A 的簇表 | 映射项目 B 的簇表 |
| 设备包含簇 | 链接类型定义 | 使用设备关联字段 | 使用本项目的关联字段 |
| SOC | 数值及荷电状态语义 | 绑定本项目计算输出 | 绑定本项目计算输出 |
| 查询实时 SOC | 通用契约：输入储能簇，输出 SOC（可选声明采集时间输出） | Redis 查询实现 | 数据库查询实现 |
| 计算剩余电量 | 通用口径：额定电量×SOC÷100 | 输入取本项目 SOC 实现与额定电量字段 | 输入取本项目 SOC 实现与台账字段 |

项目 A 修改 Redis Key，不改变通用本体和项目 B。改变本体 SOC 的业务口径或现有契约要求时，需要进行兼容性审查并由各项目主动升级；不以显示文字是否变化作为唯一判断依据。

## 7. 文件与保存方案（建议，待确认）

保留 JSON 描述本体、YAML 描述项目配置的现有约定，不要求业务专家编辑文件。沿用 `ontology` 父目录。

建议逐步统一目录，以下是目标结构，不代表当前已经存在：

```text
ontology/
  models/<ontology-id>/
    manifest.yaml           # 本体身份与元信息；预留 owner/maintainers 信息性字段
    ontology.json           # 对象、链接、属性、共享属性
    workflow.json           # 通用计算契约（结构化签名、业务约定）；兼容保留历史隐藏定义
  projects/<project-id>/
    project.yaml            # 项目信息、引用本体与版本、固定引用的本体版本；预留 owner/maintainers
    connections.yaml        # 连接配置或受保护配置的引用
    bindings.yaml           # 对象、链接映射及属性来源绑定
    implementations.yaml    # 项目计算实现和处理规则；预留环境字段
    parameters.yaml         # 项目采用的参数
  drafts/                   # 与发布同构的多文件草稿，发布工具统一读写同一形态
    models/<ontology-id>/（同 models 文件布局）
    projects/<project-id>/（同 projects 文件布局）
  releases/
    models/<ontology-id>/<version>/    # 不可变快照，含版本号与变更类型标记
    projects/<project-id>/<version>/
```

保存草稿分别保存本体状态与项目状态，不自动覆盖已发布版本。发布产生不可变快照，并在快照中记录版本号与相对上一版本的变更类型标记（兼容性／破坏性，判定规则见第 8 节）。项目引用明确的本体版本。草稿与发布采用同构的多文件形态，便于使用同一序列化与校验规则；多文件本身不保证无损，需要迁移往返验证。新增 `implementations.yaml` 的目的是避免把长计算规则堆入字段映射文件。

数据权威与读取规则：

- 编辑只读取对应的最新完整草稿；不存在草稿时，从指定发布版本或旧基础文件初始化一次。
- `models/`、`projects/` 基础目录保留为初始化与历史兼容输入，不在每次加载时覆盖草稿，也不与草稿双向同步。
- 项目引用的本体定义只从指定的不可变发布版本读取，不能用当前本体草稿或基础目录替代。
- 发布只打包某一完整草稿修订并记录内容摘要；基础目录不随发布自动更新。
- 草稿采用多文件形态时，每次写入独立修订目录，完成所有写入和校验后再原子替换当前修订指针。发布也先在暂存目录完成，再整体对外可见。失败时保留上一完整修订，不允许逐个覆盖当前文件。
- 本体和项目分别维护修订号，保存时检查客户端基于的修订，拒绝旧页面覆盖较新的内容；画布布局也随所属本体草稿保存。

现有 `metrics.yaml`、`rules.yaml`、默认本体草稿和新增本体 `workspaces` 目录有历史兼容用途，不能直接删除或整体搬移。应提供兼容读取或经过验证的迁移；先保存原始材料。

## 8. 校验、状态与版本

### 本体校验

检查必填、引用存在性、链接端点、类型定义及计算契约完整性。契约完整性包括：签名中引用的对象类型／属性是否存在、签名项标识是否唯一、适用对象引用是否存在。通用口径的业务正确性由业务人员核对，结构校验不能证明自然语言公式完整或正确。缺少项目映射或数据连接不应阻止通用本体发布。

### 变更类型与发布标记

每次发布本体版本时标记变更类型：

| 变更类型 | 判定（示例） | 对引用项目的影响 |
| --- | --- | --- |
| 兼容候选 | 显示名称调整、纯文字修订、新增独立契约或非强制属性，且稳定标识、既有语义与要求未改变 | 需检查对本项目的实际影响，不能仅凭分类保证兼容 |
| 破坏性 | 删除或改变稳定标识、改变数据类型／单位口径／链接端点／数量约束、增加必需输入或输出、删除或改变既有签名项 | 旧绑定或实现可能不再满足要求，必须处理后升级 |

系统根据结构差异提出分类建议；业务语义变化由维护人员确认，例如 SOC 从 0～100 改为 0～1，即使只修改业务说明也属于破坏性变更。缺乏判定依据时标记“待确认”，不自动判为兼容。

新增输出按新增必需输出处理，与“声明即必须”一致。输入输出引用的共享属性发生变化也须纳入传递影响分析。已检测出的引用失效不能通过人工改成“兼容”来跳过校验。

### 项目引用与升级策略

首期只支持固定引用已发布版本。新版本发布仅提供可升级提示，不自动改变项目的有效版本、草稿或已发布配置。“跟随兼容升级”暂不实施。

主动升级流程：选择目标版本 → 对比本项目当前引用版本与目标版本 → 生成影响报告 → 在项目升级草稿中修复 → 校验 → 保存／发布。

每次升级都执行预检，包括标记为兼容的版本。跨多个版本升级时比较实际起点与终点，不能只采用目标版本相对上一版本的标签。报告列出受影响的对象、链接、属性、契约、绑定及实现。

未处理的引用或配置错误阻止发布新项目版本，但不影响仍引用旧本体版本的既有项目发布快照。取消升级保留原引用；保存升级草稿也不会改变已发布项目配置。

### 项目校验

校验分为两个层次：

| 层次 | 可以检查的内容 | 不能据此声称的内容 |
| --- | --- | --- |
| 配置校验 | 引用版本、对象与属性归属、签名引用、类型匹配、输入绑定完整性、实现对全部必需输出的结构化声明 | 自然语言规则已经正确执行、输出值真实有效 |
| 执行验证 | 在有执行器时运行测试输入，检查实际输出项、类型、缺失和错误处理；业务样例核对单位与含义 | 一次成功试运行能保证所有数据和业务场景正确 |

未使用的本体能力不必全部实现。项目使用范围由已启用映射、属性来源和明确启用的独立计算构成，并包括其可识别的依赖。仅在自然语言中提及的调用无法可靠校验，应标记待核对；结构化依赖需检查循环引用。

状态区分“未配置”“配置有误”“配置校验通过／未执行验证”“执行验证通过”。后者记录测试输入、验证时间及对应配置修订；规则或依赖改变后验证状态失效。没有执行器时允许保存和发布配置快照，但必须标明未执行验证，发布不等于上线或可运行。

## 9. 旧数据处理与实施顺序

1. 确认本体与项目两区的页面入口，以及新建本体的最简交互。
2. 确认计算契约的结构化签名表单、适用对象交互、项目实现详情和属性来源绑定。
3. 确认文件边界、变更类型判定、升级策略和首期执行范围。
4. 备份现有草稿与快照，增加兼容读取与本体／项目独立状态。
5. 复用已有页面，迁移项目相关字段，新增项目管理与计算实现。
6. 用 Redis 与数据库两个配置示例验证同一本体的复用和项目隔离。
7. 验证版本传导：一次破坏性发布能被影响预检正确捕获。

旧计算说明可能同时含有通用规则和项目细节，不能自动准确拆分。建议保留原文并生成迁移待核对项，不静默删除业务内容。属性 `valueSource` 迁移后需保留对象、属性及函数引用对应关系。

## 10. 验收要点

- 新建空本体后，不预置当前项目的对象、连接或计算实现。
- 不配置任何项目时，完整的通用本体可以独立校验和发布。
- 两个项目可以引用同一本体版本，分别维护 Redis 与数据库处理规则。
- 修改项目 A 的规则不影响本体或项目 B。
- 项目属性来源引用正确的对象属性和计算输出；错误引用能定位。
- 新增必需输出触发破坏性变更提示；升级预检列出需要补充输出的实现。
- SOC 单位口径变化进入语义确认，显示名称变化不使稳定标识引用失效。
- 跨版本升级比较当前与目标版本；未升级项目仍能使用旧发布版本。
- 自然语言规则非空不能获得执行验证通过状态；修改实现后旧验证结果失效。
- 多文件保存中途失败，重新加载仍得到上一完整草稿；旧修订提交不会覆盖新修改。
- 未配置执行器时，明确展示尚不可试运行。
- 原有已发布快照可以追溯，历史数据不因迁移丢失。

## 11. 需要用户确认的事项

按以下顺序逐项讨论，不要求一次回答全部问题。V3 已修正规则冲突，以下产品细节仍需确认。

| 顺序 | 待确认事项 | V3 建议 |
| --- | --- | --- |
| 1 | 新建本体是否沿用仅填写名称 | 沿用，进入空白建模区，不增加向导（未变） |
| 2 | 计算输入输出表单细节 | 已改为结构化签名＋自然语言补充，名称和类型自动填充、技术标识自动生成、说明选填；需确认详情页布局 |
| 3 | 实时 SOC 是否必须输出采集时间 | 已改为"可选声明、声明即必须"，见 4.3 |
| 4 | 项目是否固定引用已发布版本 | 首期只固定引用，主动升级，所有升级均执行影响预检，见第 8 节 |
| 5 | 首期是否包含真实函数执行 | 维持先完成契约、规则与绑定管理，执行器另定范围；签名结构化先行，不与执行器绑定 |
| 6 | 同一项目同一契约是否需要多种实现 | 维持首期一份有效实现；实现记录预留环境字段（测试／生产） |
| 7 | 数据连接是否也要提供可编辑页面 | 维持先沿用文件维护，待项目配置详情讨论 |
| 8 | 文件组织与旧数据迁移方式 | 分离草稿与发布，采用完整修订整体提交；基础目录仅用于初始化兼容 |
| 9 | 适用对象表单与无归属计算入口 | 可选多选，系统建议；项目级提供全部计算实现入口 |
| 10 | 项目输入绑定控件与首期来源范围 | 当前对象、字段、常量、其他计算输出按已支持能力开放，不要求技术参数名 |

当前仅交付设计方案和交互草图，未对工作台功能进行修改。
