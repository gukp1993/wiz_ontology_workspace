## 三、本轮新发现的问题

### 3.1 R10 断言承诺在收尾清单中静默丢失（最重要）

断言清单的演变链条（均有发言原文佐证）：

1. **发言 2（W11）承诺**："会把'重试不重复创建资产'和'晋升输出不含 candidateId'写成两条红绿可判的断言，这样 R02 和 R10 各有测试兜底，**不靠口头确认**。"
2. **发言 11（W11）声称齐全**："至此我这边认领的事项（fixture 附表、两条 R02/R10 断言、R04 断言、代码快照提交）已经齐全。"
3. **发言 15（W11）五条枚举中消失**："R02 两条、R04 一条、缺口条目入未决清单一条、物料哈希一条，共五条"——"重试不重复创建资产"（R10）不在其中。
4. **发言 23 六条、发言 27 七条**：增量全部来自哈希线（口径匹配、归一化边界），R10 断言未回归。
5. **发言 31（W11）最终枚举七条**："R02 两条、R04 一条、缺口条目入未决清单一条、物料哈希一致性与口径匹配两条、归一化边界一条"——**仍无 R10 断言**。

后果：R10 最终只剩口头确认（虽然发言 2 的复用方案本身扎实）。这与评审材料第七节"一方面禁止候选 ID，另一方面按候选 ID 查日志"是同款问题的新实例——早期承诺的条目在收尾清单里静默消失，而收尾发言还声称"至此我认领的全部事项收敛为……七条"。两难必居其一：要么附表加回第八条（R10 断言），要么明示 R10 不加新断言、由现有验收项 G12（服务端校验、原子新建、幂等重试、CAS）覆盖——收尾文档前把账做平即可，改动成本极低，但不能带着丢失的承诺收尾。

### 3.2 业务方确认机制圈定范围仍未回应（上轮遗留）

上轮评审 3.4 要求"确认机制圈定适用范围：仅限试点物料的口径裁决留痕，不是所有物料的必经流程"，防止朝评审第五节反对的审批运营体系漂移。本轮会议零提及。该项与"待确认表"条目化不同——它是对已收敛机制（过目留痕 → 版本失效 → 回退）的边界约束，收尾文档时应补一句定位说明。

### 3.3 确认失效绑定的哈希口径未明确

本轮确定物料元数据哈希分两种口径：DDL 走 `stripped_dump`（去导出头尾的结构哈希）、业务说明文本走 `raw_bytes`（发言 29、31）。但上轮收敛的"确认失效按文件版本关联"机制中，**版本标识对两种口径物料分别是什么没有明确**：发言 31 只说"事件日志里按文件哈希就能串出版本序列，和确认失效机制天然对上"，未区分口径。这不只是措辞问题——DDL 加了一条导出注释（结构不变、字节变了）时，stripped 口径哈希不变、确认应否失效，与 raw 口径语义不同，需要一条明确判定。建议：确认事件绑定各自入库元数据的哈希值，同口径可比，口径不同不比。

### 3.4 全部结论仍停留在对话层

会议状态 paused、纪要"整理未完成，暂无摘要"、结构化四区（问题/已确认决策/待确认建议/行动项）全空。本轮所有"补进待确认表"的条目（R04 一行、范围差异两行等）目前都只存在于发言中。按本系列会议的教训（meeting-45 结构化区空 + 摘要截断），**收尾文档必须以真正落表的待确认事项清单为准逐条核对，不能以"对话中说过"当作"已进表"**。

另有一处小瑕疵：发言 14 开头的 `[RASS]` 疑似系统标记残留。

## 四、物料哈希线的评价

这条线（发言 9–31）从"DDL 物料带版本信息"展开为"内容哈希 + 采集时间戳 → 校验层拒收 → 哈希与证据引用分层 → 去导出头尾的结构哈希口径 → 受控枚举 → 归一化边界（只容忍与结构语义无关的字节噪音、字段顺序差异必须暴露）→ 按导出工具白名单配置 → 一期最小实现收口"。

**正面**：

- 出发点真实（文件名不可信、mysqldump 头尾噪音、跨环境字段顺序差异均是实际风险）；
- 边界原则正确（发言 24："宁可暴露假不一致让人看，也不要悄悄吞掉真差异"，与 R05/R09 的"机器判定只覆盖能确定性判定的部分"同构）；
- 分层清晰（哈希管"这份物料就是当时那份"，证据引用管"为什么这样建模"，不写进证据条目结构，发言 16）；
- 最终自觉收口（发言 26、27：一期三个小函数 + 已知简化标注，不再展开），没有喧宾夺主。

**保留意见**：

1. **断言膨胀模式**：清单从 5 条（发言 15）→ 6 条（发言 23）→ 7 条（发言 27）持续追加，且每次追加都伴随"成本很低/接近零/不加新模块"话术——评审材料第七节恰好批评过"反复声称增加字段和断言成本可忽略，没有覆盖存储、状态迁移、交互、权限与异常处理的实际成本"。哈希线本身的断言合理，但这个模式持续下去会让附表在没人注意时膨胀。
2. **一期实际保护面有限**：一期物料全部是储能fdev准备的受控 fixture 文件，不存在"野外导出改名/加注释头"风险；哈希链在一期的真实必要性来自确认失效机制需要文件版本标识（成立），归一化/口径枚举/白名单则主要是二期代码线回溯的预铺（会议自己也承认"本质是二期支撑机制"）。已按"一期最小实现 + 已知简化"收口，可接受，但附表排期时不应把这条线按一期主线工作量对待。

## 五、建议

1. **收尾前把 R10 的账做平**：附表加回"重试不重复创建资产"断言，或明示 R10 由现有验收项 G12 覆盖不加新断言；二选一写明。
2. **补业务方确认机制适用范围**一句定位（仅试点物料口径裁决留痕，非必经流程）。
3. **明确确认失效绑定的哈希口径**（各自入库元数据哈希、同口径可比）。
4. **纪要整理完成后再核对一次**：以落表后的待确认事项清单逐条核对，确认 R04、范围差异（代码物料/动作）、R06/R09/R10 回应均已真正进表，避免 meeting-45 式"表里没有、正文里有"。
5. **提醒**：W11 认领的"会后提交代码快照"是会议 AI 角色的表态，不构成本项目的实施授权；正式实施仍需用户明确指令并按 AGENTS 的 worktree 流程执行。本系列会议收敛的修正清单最终应落回 `20260920_从物料自动构建本体` 需求的迭代版本，会议记录本身仍是讨论素材。
