日期：2026-09-15；验收人：Codex。

## 结论

**结构整理主要已落地，但不能认定“全部验收通过”。** 本次独立执行的已有测试与前端构建全部通过，补充复现仍发现保存失败被调用方视为成功，以及导出接口返回 404。前者是遗留问题未完成收尾，后者是本轮路由拆分引入的回归。

## 1. 需要修复的问题

### P1：保存失败或冲突后，调用方仍继续执行成功逻辑

位置：

- `frontend/src/app/saveCoordinator.ts`：`pumpOne` 捕获异常后只设置状态；`commitNow` 等待结束后正常返回，已有冲突时也直接正常返回。
- `frontend/src/App.vue:204`：`commit-now` 注入直接返回该 Promise，没有补充结果检查。
- `frontend/src/project/PropertySources.vue:281`：等待之后直接显示“已保存”，900ms 后关闭编辑器。
- `frontend/src/ontology/OntologyRelease.vue:81`、`frontend/src/project/ProjectValidation.vue:94`：等待之后继续读取服务端草稿并发布。

**最小复现已执行**：使用真实 `createSaver`，提交函数分别模拟 HTTP 500 和 409。两次结果均为：

| 模拟响应 | Saver 状态 | 调用方是否进入 catch | await 后是否继续成功分支 |
| --- | --- | --- | --- |
| 500 | error | 否 | 是 |
| 409 | conflict | 否 | 是 |

因此状态栏虽然显示失败，表单仍可能显示成功并关闭。按两区发布代码的后续调用路径，保存未成功时仍可能发布服务端旧草稿或另一页面已保存的草稿；该发布后果是源码链路分析，本轮未做浏览器故障注入发布实验。

对比 P0 快照，正常返回的行为已存在。本轮修好了 retry、revision 和关闭页面保护，但遗漏了原方案 §4.2 明确要求的“返回值必须可区分成功、错误和冲突”。

建议：保留自动保存的错误状态处理，让显式提交通过抛错或结构化结果明确表达失败；所有表单与发布调用方统一检查。若改变 Promise 语义，同时检查快捷键、撤销等 `void commitNow()` 调用点，避免新增未处理拒绝。不要让自动保存为了报错而引入无界重试。

必要验收：保存失败保留表单与输入、不显示成功；409 不自动覆盖；两区发布在前置保存失败时不调用发布接口；保存正常时继续成功流程。

### P2：导出接口被路由白名单检查提前拒绝

位置：`workbench/server.py:65`、`:115`。

`POST_ROUTES['/api/export'] = None`，随后 `if handler is None` 直接返回 404，后面的专用 ZIP 分支永远不能执行。

**真实 HTTP 复现已执行**：临时根、18869 端口，新建空本体并读取有效 state，以同一 payload：

- 直接调用 `model_routes.export_bytes` 得到合法 ZIP（`PK` 文件头）。
- `POST /api/export` 返回 `404 {"error":"接口不存在"}`。

对比 `.runtime/snapshots/arch_p0_20260915.tar.gz` 中原 `server.py`：旧白名单包含 export，且能进入打包分支。这是本轮路由拆分回归。

建议：区别“路由不存在”与“已登记的二进制路由”。仍须经过 Origin、Content-Type 和请求大小检查，不能把导出提前到安全检查之外。

必要验收：有效请求返回可解压 ZIP；未知接口保持 404；非法 Origin 和超限请求仍被拒绝。

## 4. 之前65分钟主要花在哪里

以下来自用户粘贴的 GLM 回复，不是 Codex 独立读取到的运行日志。

| GLM 报告阶段 | 分钟 | 占比 |
| --- | --- | --- |
| 探索 + 契约设计 | 7 | 10.8% |
| Wave A 实现 | 30 | 46.2% |
| Wave B 表单 + 集成测试 | 19 | 29.2% |
| Wave C 集成收尾 | 9 | 13.8% |
| 合计 | 65 | 100% |

**可以判断的部分**：实现和测试开发两波合计49分钟，约75%；主要墙钟时间在这两段。那次涉及来源协议、校验、旧数据兼容及 UI，并不是一个单纯改标签的小需求。规则集中在大文件和跨前后端格式同步，确实会增加理解、修改及集成成本。

**不能据此确认的部分**：49分钟里模型生成、工具等待、编写测试、运行测试、代理空等和返工分别占多少。测试代码1050行、生产代码700行不能证明“测试执行占了大头”；代码行数不是耗时测量。9个 agent 的数量也不能直接说明并行是否有效。

本次同项目构建和现有回归为秒级，结合实施方记录的历史基线也在秒级，支持“常规构建/测试运行不是几十分钟的主要来源”。但无法排除上次另有长超时、依赖安装、外部网络或重复执行，应查看原始事件时间线后再细分。

50并发只是上限。对于少数互相依赖的文件，增加代理可能产生更多协调成本。合理做法是先确定必要数据结构，然后按文件所有权并行 UI、后端、失败场景测试；无需等全部后端实现完才开始前端和测试。

还有需求范围因素：此前方案把一个来源需求扩展成多条件定位、依赖检测、类型检查、时序规则和兼容验证，实际上增加了实现量。这其中部分规则是必要的，但规划者（包括 Codex）也应控制当轮范围，不能全归因于 GLM 或旧架构。

## 5. 后续怎么减少小需求耗时

1. 小需求先限定用户行为和涉及模块，优先使用本次已建立的目录定位；无需每次重新探索全部项目、重新设计协议和生成一套文档。
2. 区分文案/样式、局部表单、存储协议三种改动。前两类不强行改底层协议；协议变更才做针对性的兼容与集成验证。
3. 现有全量自动回归很快，可以在最终交付运行一次；中途先运行对应模块测试，有新增失败才扩大验证。避免每个代理重复跑同一套安装/构建。
4. 并行只给相互独立的文件任务；公共契约和共享文件固定一个负责人。测试作者可和实现者同时工作，优先覆盖保存失败、冲突、导出等实际后果。
5. 新增最少量的行为测试，不用测试代码行数作为工作量或质量指标。机械拆分的金样适合检查行为等价，不能用来证明原行为没有错误。
6. 使用一份共享上下文和任务板维护当前状态，减少重复探索及重复“完成报告”。下一次记录每段起止时间、工具运行时间、等待原因和返工原因，才能准确归因。
