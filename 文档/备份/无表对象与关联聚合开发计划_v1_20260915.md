# 无表对象与关联聚合开发计划 v1

实施依据：[设计方案](无表对象与关联聚合设计方案_v1_20260915.md)。本文件只规划开发，没有改动生产代码或项目数据。

## 阶段 0：协议冻结与基线（主负责人）

- 读 AGENTS.md；核对 identity、relation、property 的现有适配、校验和引用升级逻辑。
- 冻结 registered identity、membership relation、registered/aggregate property 的类型、空值枚举和预览 response。
- 统一稳定标识规范：沿用现有 bindings 键，不另造显示名引用；明确 mg: 前缀只在既有边界转换。
- 用临时目录准备一份系统、两台设备、一个一对多链接的数据 fixture，设备值 200 和 300；另备非项目设备、逻辑删除设备、缺失容量和重复主键案例。
- 只冻结必需协议，不把整个 bindings 重写成新版本。预计这是最重要的串行前置，后续任务不得自行更换协议。

## 阶段 1：分文件并行

|---|---|---|
| A：前端适配与来源表单 | project/bindingModel.ts、ObjectSources.vue；必要的新小组件 | 新联合类型、unknown 保留；登记实例 CRUD、无表识别、切换影响提示 |
| B：后端校验与引用 | project_validation.py、project_mapping.py、必要的 projects.py | 新分支校验、实例／链接引用保护、聚合限制、旧 golden 兼容；给 A/C 提供接口约束 |
| C：只读执行 | 新增 workbench/project_property_reader.py 等最小模块、project_routes.py、server.py | 已保存草稿读取、revision 检查、连接复用、白名单参数化读取、求和与数据质量结果 |

## 阶段 2：前端关系与聚合（依赖 A 的适配接口）

- LinkMappings.vue：成员规则列表、按起点实例编辑、字段条件选择、范围摘要。
- PropertySources.vue：登记信息与关联聚合来源、链接／属性联动、单位口径确认、错误提示。
- project/api.ts：添加预览请求封装，页面不能自写 fetch。
- 负责人集成成员预览及聚合预览，不创建新主菜单；保留当前单页保存交互。
- 核对 ProjectBinding、ProjectValidation、ProjectVersion、对象数据浏览及演示 merged 等使用方，不让旧代码默认所有对象必有表。

这一阶段可由完成任务的 agent 承担独立组件，但不要让多人同时改 PropertySources.vue。

## 阶段 3：测试与发布验收（主负责人）

1. 运行新增纯逻辑测试：实例唯一性、引用失效、聚合类型限制、输入条件、空值／冲突语义。
2. 增加校验金样，通过 tests/make_validation_golden.py 和 tests/test_validation_split.py 保持原样例输出稳定；按仓库实际调用方式运行。
3. 测试数据库执行器：使用本地临时测试库或驱动 fixture；单独验证生成 SQL 的标识引用和参数分离。没有真实测试库时明确记录，不能将 mock 结果称为真实数据库验收。
4. HTTP 集成测试通过 WIZ_WORKBENCH_ROOT 和独立 WIZ_WORKBENCH_PORT；验证保存重读、revision 409、只读预览、不执行用户 SQL、发布快照不变。
5. 测试旧数据库/Redis/采样配置与 unknown 格式不丢失、演示路径安全过滤。
6. 浏览器验证登记系统 → 成员过滤 → 容量求和 → 预览 → 保存重开；条件变化后旧异步响应不覆盖。
7. frontend 执行 npm run build。只有触及保存协调器时才按 AGENTS.md 增加对应队列测试，不无故重复全量测试。
8. 后端修改需重启时用 start.sh；禁止直接杀所有 Python 进程。真实项目不自动初始化或发布。

## 耗时控制

这不是单纯表单新增，需要修改身份、关系、属性来源和查询校验。按“协议冻结 → 并行底层 → 页面集成 → 验收”执行，最多 3 个并行任务足够，不追求 50 并发。每阶段只汇报新进展、阻塞和下一步，不反复扫描全仓或重复写方案。

若时间不足，必须标注未完成的运行能力，不能只交配置页面并声称已可查询系统容量。阶段性提交允许，但最终目标仍是方案限定的完整闭环。
