## 1. 目标与结论

工作台继续分成本体建设和项目映射两块。优化目标是让小需求只影响少量明确模块，开发者能够快速找到入口，修改后有可靠且适量的验证。

采用**单体应用、按业务模块组织、集中基础能力、逐步迁移**。保留 Vue3＋TypeScript＋Vite、Python 标准库 HTTP 服务、文件存储、现有 JSON／JSON-LD／YAML 协议。不引入微服务、数据库替换、通用插件框架、复杂依赖注入或新的前端状态库。

目录整理是职责分离的结果，不以文件越少越好为目标。不能通过合并成几个巨型文件、删除校验或撤销能力来简化。

## 3. 优化后职责边界

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| 页面／组件 | 输入、局部草稿、错误定位、展示和用户操作 | 直接决定磁盘布局、重复实现 HTTP 错误与保存队列 |
| 工作区协调 | 当前资源、编辑基线、提交、撤销、切换保护 | 属性来源的业务校验细节 |
| 前端 API 模块 | 请求编码、响应解析、错误类型、调用具体接口 | 控制页面选择、修改其他工作区状态 |
| 前端模型辅助 | 有效属性、来源适配、就地校验 | 网络请求、保存文件、操作浏览器页面 |
| HTTP 层 | 路由、输入边界、安全检查、状态码 | 长篇业务规则、拼接持久化快照 |
| 后端校验 | 结构、引用、形态、依赖、升级影响 | 写入修订目录、读取网络数据库 |
| 后端存储 | 完整修订、原子指针、加载与发布快照 | 决定页面交互或解释某种指标算法 |
| 外部连接能力 | 凭据使用、真实连接测试、目录读取 | 任意业务 SQL／函数执行 |
| 演示模块 | 明确支持的储能演示执行 | 定义全项目基础路径或成为核心存储的依赖 |

调用方向：页面 → 工作区／API → 后端 HTTP → 校验与存储。校验尽量依赖传入数据，存储不反向导入 HTTP Handler，避免循环依赖。

## 4. 前端目标架构

保留一个 Vue 应用、一个 App 入口。最终建议结构如下，允许按实际代码合并职责相近的小文件：

```text
frontend/
  src/
    main.ts
    App.vue                 # 应用壳层，装配工作区和页面
    app/
      navigation.ts         # 两区菜单、hash 兼容、结构化定位
      workspace.ts          # 创建本体/项目工作区、切换、撤销及生命周期
      saveCoordinator.ts    # 串行提交、失败、冲突和响应代数
      http.ts               # 唯一请求与错误解析基础层
    ontology/
      api.ts                # 本体读取/保存/校验/发布/版本请求
      modelFormat.ts        # 保留现有格式转换，与后端镜像
      propertyModel.ts       # 属性有效定义与共享继承
      ...Vue / TS            # 本体对象、属性、契约、共享库、画布、发布
    project/
      api.ts                # 项目、连接、目录和实现相关请求
      bindingModel.ts        # 新旧绑定适配、类型与纯辅助逻辑
      ...Vue / TS            # 项目概览、来源、链接、实现、连接、发布
    shared/
      ...Vue / TS / CSS      # AppSelect、Field、Layout、通用图样式和快捷键
    tools/
      ...Vue / TS            # 辅助浏览、历史导览、实例演示、动作/接口等
```

### 4.1 页面归属和依赖

- 本体业务页从 ontology/api 获取能力，项目业务页从 project/api 获取能力；API 模块均复用 app/http。
- 页面不能再复制请求失败处理、catalogs 剥离、409 解析或快照转换。导出 ZIP 等二进制响应有明确专用方法，不强行按 JSON 解析。
- 纯模型工具不反向依赖 Vue 页面或网络层。依赖图出现循环时调整职责，不通过多个 re-export 文件掩盖。
- 保留现有控件；目录改名先做导入更新，不同时改表单行为。
- 辅助页可按需加载，但作为可选加载优化，不把首屏体积改善当成开发时间提速的主要证据。

### 4.2 工作区与提交接口

每个工作区持有明确的资源身份、已确认的服务端 revision 和编辑状态。使用 Vue composable／普通模块即可，不引入新的全局状态库。

不再通过“当前 UI 处于哪个区”在提交完成时推断写入目标。创建编辑表单时就绑定 `{space, resourceId}`，开始请求时固定 URL、请求体、基线和资源身份；切换页面后，旧响应不能覆盖新工作区。

建议统一提交语义：

```text
表单打开：从已保存状态创建局部草稿，并记录编辑基线
保存：提交本次局部改动 → 资源队列 → API → 成功更新确认状态与 revision
取消：丢弃局部草稿
发布：使用已保存的明确草稿修订，执行独立发布动作
```

内部接口名可以复用现有方法，但返回值必须可区分成功、错误和冲突。Promise 正常结束不能被一律解释为保存成功。

### 4.3 保存可靠性属于本轮必做

目前 saveCoordinator 中存在需要用测试明确的风险：待发队列携带入队时 revision；retry 在 error 状态下调用 drain，而 drain 会停止；beforeunload 未把 error 状态列入阻止离开的条件。这些是源码审查发现，尚未在本轮实际复现，不直接宣称全部已造成数据丢失。

目标行为：

- 同资源最多一个在途写请求；后继快照使用此前本客户端成功确认的新 revision，而不是旧的入队 revision；不能用任意服务端最新 revision 自动重提来绕过外部冲突。
- 409 不自动覆盖他人的修改。保留本地输入，提供读取最新后核对；显式覆盖必须由用户明确选择。
- 保存失败后重试能够实际发起请求；若失败后又编辑，明确重试最新确认提交的内容，不能静默把新内容换成旧失败快照。
- 网络结果不确定时通过资源身份和修订／内容核对恢复；不无界自动重试。
- 表单保存成功后立即刷新和重启仍保留。失败保持表单与输入，不显示已保存。
- 保存一个表单不能把另一个未提交表单顺带落盘。
- 画布只在完整编辑操作结束后入队，zoom/pan 不保存；撤销／重做产生新修订，不修改历史版本。
- 定时器、事件监听、在途响应都跟随工作区生命周期清理；多个项目之间不能串写。

## 5. 后端目标架构

保持 workbench 为单一后端包，优先增加少量有明确职责的模块，不建立 controller/service/repository 三套空层级。

```text
workbench/
  server.py                 # HTTP 服务和安全边界、路由分派
  paths.py                  # 代码资源与可覆盖数据根的唯一解析
  model_routes.py           # 本体接口处理（仅在路由抽取阶段增加）
  project_routes.py         # 项目接口处理（仅在路由抽取阶段增加）
  projects.py               # 项目加载、草稿、发布；保留兼容公开入口
  project_validation.py     # 项目校验组织及各类纯校验函数
  project_mapping.py        # 来源/属性/链接解析辅助，双方确实共用时才抽出
  workspaces.py             # 本体草稿与工作空间
  versions.py               # 本体发布与版本
  contracts.py              # 契约、结构差异与升级影响
  model_format.py           # 本体协议转换
  properties.py / ...       # 既有独立业务规则
  dbdrivers.py / catalogs.py / secrets.py
  demo/                     # 后续从 service/ 迁入的演示代码
```

### 5.1 先分离项目校验

将 validate_project 拆成连接、对象来源、计算实现、属性来源、链接、依赖检查等函数，由一个短的组织函数汇总。

第一步只做机械提取，保持输出的错误级别、item.kind/id、排序、旧编码和业务语义。当前校验会调用 derive_display_names 修改派生字段，不能在提取时无意改变行为。

第二步才明确规范化和校验边界：在显式规范化步骤或副本上派生显示名，校验本身不产生持久化副作用。新增不可变输入断言前，应先验证所有调用者是否依赖旧行为。

projects.validate_project 可暂时作为兼容入口转发，便于现有 HTTP 与测试渐进迁移；不要同时让 validation 导入整个 projects 再造成循环。公共来源解析辅助放在低层模块，或者显式传入必要上下文。

前端仍保留填写提示与结构检查，后端仍做最终权威校验。避免同端重复实现同一套规则，但不能为了“去重”删掉后端校验。

### 5.2 再分离 HTTP 路由

保持原 URL、HTTP 方法、请求字段、状态码和响应结构。Handler 统一完成 Origin、白名单、大小限制及错误序列化；再调用本体或项目处理函数。

不要在路由模块再创建全局 LOCK。需要写入时仍在既有事务边界校验 revision 和提交；连接测试和目录网络读取仍不能占用全局写锁。

路由拆分前必须有接口兼容快照，尤其覆盖保存、发布、恢复、导出、连接凭据、目录和旧辅助接口。不要仅因接口“属于更多工具”就移除。

### 5.3 统一路径并隔离演示

paths.py 区分：

- CODE_ROOT：应用代码、静态构建和随代码分发资源的位置。
- DATA_ROOT：真实 ontology 数据根；兼容 WIZ_WORKBENCH_ROOT 语义，测试时可替换。
- 运行日志与临时输出路径：由运行工具管理，不成为业务数据来源。

逐个审计现有 ROOT 的用途，不能全局文本替换。隔离测试不能因某个模块自行 Path(__file__) 定位而读取真实 ontology 作为默认业务数据。确需只读的分发示例应使用明确资源路径。

核心存储、凭据和目录不再从 service.demo 导入路径。演示可以依赖通用模型工具，核心模块不依赖演示初始化。`python3 -m service.demo` 可保留短期兼容入口。

## 6. 数据与格式：本轮不迁移

以下全部保留：本体与项目两条独立状态／发布线；多文件修订目录＋current.json 原子指针；不可变发布版本；初始化基础目录只读；schema 与 JSON-LD 镜像；固定本体版本引用；稳定 ID 与 definitionOrder。

`ontology/` 下所有数据保持原位，不因代码整理搬移或改写。不重新生成用户 ID，不更换 YAML/JSON 格式，不导入原型样例，不统一重写全部历史草稿。

数据库直选表、Redis 直连、时间序列、共享形态和未知来源无损保留已有协议。目录缓存不进入保存载荷、快照或 revision；凭据保持受保护存储，不出现在日志和交付资料中。

## 7. 目录整理目标与迁移分类

目录收敛分两层：先整理源码和索引；最后才搬移有历史依赖的非数据目录。

最终建议根目录：

```text
frontend/       前端代码、依赖与构建输出
workbench/      后端代码，包含明确隔离的 demo 子包
ontology/       用户业务数据，保持原位
tests/          自动化验收和非敏感固定样例
tools/          开发/检查工具；legacy/ 存历史一次性脚本
resources/      教学示例与历史导入材料，保持原文件内容
文档/           当前规范、交付物、原型和归档资料
.runtime/       可再生成日志、临时验证产物，不保存用户资产
README.md       当前项目使用与结构入口
AGENTS.md       稳定开发约束，保持简洁
session_context.md  最新状态、待办和交接索引
start.sh / requirements.txt / .gitignore 等根配置
```

| 现有内容 | 目标／处置 | 前置条件 |
| --- | --- | --- |
| frontend、workbench、tests | 保留根目录，内部按职责整理 | 导入图与测试通过 |
| ontology | 全部原位保留 | 不属于目录清理范围 |
| service | 实现迁入 workbench/demo；旧命令短期转发 | 去除 ROOT 反向依赖，演示回归通过 |
| scripts | 日常工具进 tools，历史脚本进 tools/legacy | 更新内部路径，不执行历史脚本来验证 |
| imports、examples | 后期迁入 resources 对应子目录 | 服务端旧路径、脚本及文档引用审计；逐文件摘要一致 |
| outputs | 后期归入 文档/交付物，原型放其 prototypes | 交接双方已更新入口；全部相对链接和浏览器原型路径有迁移清单 |
| 文档中的旧版本 | 归档或索引标明历史 | 不让旧方案继续冒充当前事实，不删除原文 |
| work/server.log | 新日志写 .runtime，旧日志按保留策略归档 | 新启动脚本管理自己的进程，不误停其他服务 |
| work/refactor | 归档其中备份和验证资料 | 先区分备份资产与可再生成编译产物，不能整个 work 当缓存删除 |
| node_modules、dist、__pycache__ | 标明生成物，忽略日常源码检索 | 不靠删除依赖来优化开发速度 |
| 无引用组件／依赖 | 复核后删除 | 源码入口、动态加载、旧 hash、测试、工具链均未使用 |

目标目录允许分阶段达到，不能为达成“根目录只有八个文件夹”破坏旧命令、链接或用户打开的原型。遇到仍被使用的旧位置，可暂留最小转发入口／索引并记入迁移清单，不能长期维护两份会分叉的实现。

移动前生成旧路径→新路径清单和内容摘要，移动后验证。当前项目不是 Git 仓库，不能用 git reset/clean 当回退方案。代码备份只包含本轮涉及文件，排除 ontology、vault、依赖和密钥；用户资料搬移保留可逆清单，不做不可追溯删除。

## 8. 开发与验证流程提速

### 8.1 开发模式与交付模式分开

- 前端日常调试使用现有 Vite dev 与 API 代理，修改即时查看；不为每次调样式重启 Python 和安装依赖。
- 依赖安装采用明确 setup 命令或检测缺失／锁文件变化；锁文件未变时构建不运行 npm install。
- 前端正式交付仍执行 npm run build，符合现有规则。纯后端改动不重建前端，纯文档改动不跑应用测试。
- rebuild 先构建成功，再执行必要的服务切换；只管理自己启动的进程，不再用端口上的所有 PID 作为可杀进程集合。
- 后端开发重启可以先保留手动命令；没有测量证据前不增加复杂文件监听系统。

### 8.2 分层测试

| 改动 | 最少必要验证 |
| --- | --- |
| 文案／样式／展示 | 相关页面检查；前端代码交付 build |
| 单个表单或来源规则 | 相关纯函数／组件场景、对应页面、前端 build |
| 保存／revision／上下文 | 确定性的前端队列测试＋隔离 HTTP 保存与重启＋双页面冲突验收 |
| 协议／存储／发布 | 编码往返、旧版本兼容、隔离 API、发布与升级关键链路 |
| 目录／导入迁移 | 引用和导入检查、相关模块测试、旧入口兼容、链接检查 |

保留已有四组 Python 回归。整理重复服务启动／请求助手为一个共享测试夹具，测试数据采用非敏感最小样例，不依赖用户真实发布目录作为常规 fixture。

目前集成脚本存在固定端口，应改为受控独立端口分配；并行测试使用各自临时根、进程与浏览器会话，进程退出须清理。失败可选择保留脱敏材料，但不能遗留大量未知目录。

前端保存队列测试优先用现有 TypeScript/Node 能力和可控提交 Promise；确需新测试依赖再说明用途，不为四五个用例引入整套测试平台。

## 9. 验收与衡量

不预先承诺“提速百分之多少”。P0/P5 使用同一环境分别记录依赖准备、typecheck、build、相关测试和完整测试耗时，至少区分首次与已有依赖两种情况。

架构验收：

- 更改一个页面标签不需要编辑保存／发布或模型转换模块。
- 增加一种已有协议范围内的来源校验主要落在对应规则函数和测试；不再阅读／修改 635 行大函数。
- 页面使用统一 API／提交方法，不自行复制响应与 409 处理。
- 核心后端路径和存储导入不再触发演示模块加载。
- 源码中没有确认无用的旧实现；README 能解释所有一级目录和当前数据读写位置。
- 同一业务规则只有一个后端权威实现；前端即时校验与其有一致性测试。
- 所有已发布／草稿结构兼容，真实 ontology 数据未改动；功能、交互基准和安全边界不退化。

## 10. 不在本轮范围

不重新设计页面，不改变本体概念，不新增业务查询执行器，不切换 React/FastAPI/数据库，不追求 100% 类型重写，不给每个文件新增抽象层，不全面重排全部源码格式。

JSON-LD 编辑模型是否将来改成直接编辑 schema，是更大的协议设计问题，本轮保留镜像转换并补测试，避免与结构整理混做。

拆分计划中的阶段门禁通过后逐步继续；发现真实功能缺陷先最小复现，修复与机械搬移分开提交记录，便于定位回归。
