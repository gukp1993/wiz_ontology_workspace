# 储能示例阅读指南

## 1. 本例解决什么问题

查询“创智园南区储能电站在 2026-09-08 10:00 的 SOC”。示例把本体定义、项目表映射、模拟数据、规则和计算函数连接起来，最终返回 SOC 及参与计算的成员。

不依赖大模型猜公式。全部演示数据在本地文件中。用户仅提供了 `m_storage_phase` 表名，其他表名和全部字段、设备、测点与数值均为示例，未经真实数据库验证。

## 2. 文件结构

```text
ontology/models/storage/
  manifest.yaml          模型包清单与版本
  ontology.jsonld        OWL语义：对象类型、属性、关系
  metrics.yaml           SOC指标、单位、时间语义、适用类型
  rules.yaml             SOC输入、成员选择、计算实现、异常政策
ontology/projects/chuangzhi/
  project.yaml           项目、时区、模型版本和配置版本
  connections.yaml       本例的JSON文件适配器
  bindings.yaml          表→对象、字段→属性、外键→关系、SOC观测映射
  parameters.yaml        新鲜度与时间对齐容差
service/
  demo.py                加载、有限契约校验、对象解析、计划与执行入口
  calculations/soc.py    容量加权计算函数
 tests/
  fixtures/chuangzhi.json 模拟业务表和观测记录
  acceptance/chuangzhi.yaml 标准查询及期望值
  test_demo.py           11项验证测试
```

为了让例子容易读，原先推荐的 loader、resolver、planner、executor、fixture adapter 合并在 `service/demo.py` 中；后续逻辑变多再拆分。没有创建空的 MCP、数据库适配器、actions 或 schema 文件来冒充已实现能力。

## 3. 建议阅读顺序

1. `ontology/models/storage/ontology.jsonld`：只看三种对象类型和两个归属关系，不包含项目表名。
2. `ontology/projects/chuangzhi/bindings.yaml`：看 `StorageDevice` 怎样绑定 `m_storage_phase`，以及 `station_id` 如何建立归属关系。
3. `ontology/projects/chuangzhi/data/chuangzhi.json`：看真实实例如何由模拟表记录生成。
4. `ontology/models/storage/metrics.yaml`、`rules.yaml`：看 SOC 指标引用什么规则，规则要求哪些输入。
5. `service/calculations/soc.py`：看规则背后的实际算法。
6. 运行示例，核对结果中的 `lineage` 与输入记录。

## 4. 实例结构

| 对象ID后缀 | 类型 | 名称 | 父对象 |
|---|---|---|---|
| south | StorageStation | 南区储能电站 | 无 |
| d1 | StorageDevice | 南区1号柜 | south |
| d2 | StorageDevice | 南区2号柜 | south |
| c1 | BatteryCluster | 1号电池簇 | d1 |
| c2 | BatteryCluster | 2号电池簇 | d2 |

完整身份是 `项目:对象类型:源主键`，例如 `chuangzhi:StorageDevice:d1`。名称只是展示字段。

另有一个无设备的北区电站，用于验证空范围返回不可用。

## 5. 项目映射如何生效

`bindings.yaml` 中 `object_bindings` 指定数据表、主键、属性字段和关系字段。执行器加载 fixture 后，按这些映射构建对象，而不是硬编码两台设备。

`observation_binding` 指定 SOC 数据表、簇关联字段、数值、时间和质量列。配置中 `connection: demo` 对应 JSON fixture 连接。

额定能量与 SOC 容量基准分别映射。二者在本例恰好数值相同，不表示生产中总是可以等同。

## 6. 计算过程

查询电站时，沿归属关系反向查找设备和电池簇；查询设备时只选其下的簇；查询簇时只计算自身，因此共用加权实现。

| 簇 | SOC | 容量基准 | 采样时间 |
|---|---:|---:|---|
| c1 | 50% | 100 kWh | 10:00 |
| c2 | 80% | 200 kWh | 10:00 |

`(50 × 100 + 80 × 200) / (100 + 200) = 70%`

SOC输入本来就是0—100的百分数，因此这个加权平均不再乘100。若计算剩余能量，则需要除以100；本例没有实现剩余能量指标。

每个簇选择“不晚于查询时间的最新观测”。fixture 特意包含 c1 的 11:00 观测，10:00 查询不会读取未来数据。最新观测质量坏时不会默默退回更早的好值。

## 7. 质量处理

- 所有必要成员都必须有有效数据，不缺失补零、不默默剔除成员。
- 容量基准必须为正数，且所有成员使用同一种基准代码。
- SOC必须是有限数值，范围为0—100。
- 观测距查询时间不超过300秒；成员时间差不超过60秒。
- 查询时间必须显式包含时区；本例尚未实现自然语言“昨天”的解析。
- 同一对象主键重复、同一时刻重复观测、关系悬空均不产生正常结果。

这些时间阈值仅为演示。容量基准代码一致是示例中的最小检查，不足以独立证明真实设备的物理基准可比。

## 8. 验证方式

在项目根目录运行：

```bash
python3 -m service.demo
python3 -m unittest discover -s tests -v
```

11项测试覆盖业务验收、未来数据排除、缺失、过期、时间不齐、坏质量、容量基准不同、重复身份、非法数值、空范围、时区缺失。

`rdflib` 用于实际解析 JSON-LD，证明文件可被标准处理器读取；这不代表已经完成 OWL 推理或 SHACL 校验。

## 9. 哪些内容已经实现，哪些需要后续接入

已实现：文件加载、JSON-LD解析、SOC契约有限检查、项目映射、实例构建、范围选择、时点取样、质量检查、SOC计算、命令行输出及测试。

未实现：生产数据库读取、MCP服务器、前端编辑器、JSON Schema全量校验、OWL推理、SHACL、历史成员有效期、充放电量与收益、预测、审批及控制下发。

特别是历史查询：本例使用当前fixture的静态资产归属。真实项目如果设备曾转移电站，需要按查询时刻解析成员有效期。

## 10. 如何替换成真实项目

1. 核实 `m_storage_phase` 一行究竟代表设备还是设备阶段，确定稳定设备身份与有效期。
2. 核实电站、簇的真实表和关联键，更新 bindings。
3. 确认 SOC 原始表示、时间字段、质量码和容量基准。
4. 实现只读数据源适配器，保留同样的业务对象和计算契约。
5. 用经业务确认的数据快照替换或补充验收样例。
6. 在此基础上提供 MCP 工具，不让智能体自行改写算法。

通用本体无需因为表名变化而复制一套；主要变化应留在项目绑定及适配器中。
