# 架构优化拆分计划

日期：2026-09-15  
方案：[前后端架构优化方案 V1](前后端架构优化方案_v1_20260915.md)

## 1. 执行原则

分六个阶段，每阶段可验证、可回退、可独立交付。先拆职责再搬目录，先保护行为再修复缺陷。不把架构整理和新业务功能开发一起做。

用户允许 GLM 高并发，但共享文件和接口约束决定本任务适合阶段性 2～4 个开发包并行，另配独立只读审查／测试准备；满足独立性后可扩大。不是排满 50 个任务，也不是让一个任务串行完成所有独立工作。

任务所有权包括文件而不只是功能：同一文件同一时间一个负责人。总协调者负责任务板、接口冻结、集成和共享上下文，其他包提交结果而不抢写这些文件。

## 2. P0：事实基线与回退准备

目标：避免用过期上下文重做已实现功能，得到可对比的基线。

并行只读包：

- A：前端导入图、页面/API/保存依赖，核实无用组件与依赖候选。
- B：后端模块导入、HTTP 入口、校验与存储边界、路径使用清单。
- C：脚本／目录／文档链接、当前服务和生成物分类；仅查看，不删除。
- D：回归测试与性能基线，先核对所有写入是否隔离。

总协调者产出 `文档/交付物/架构优化任务板_20260915.md`：列包、文件所有权、状态、基线、备份位置及下一阶段依赖。受影响代码生成独立快照与摘要；不复制真实业务数据或凭据。

门禁：已记录当前失败，不把已有失败归因于后续重构；隔离样例能够启动并调用必要接口。未通过的相关行为需先定位，不能隐藏或跳过。

## 3. P1：稳定基础入口

| 包 | 内容 | 写入范围 | 验收 |
| --- | --- | --- | --- |
| F1 | 提取统一 HTTP 错误及编码基础、两区 API 方法 | 新 app/http、两区 api；API 调用点由前端负责人统一改 | 状态码、409、JSON／导出响应和 catalogs 剥离一致 |
| B1 | 统一 CODE_ROOT／DATA_ROOT，去除基础模块对 demo.ROOT 依赖 | paths.py、根路径导入调用者 | 临时根不读写真实 ontology；演示仍可通过兼容入口使用 |
| T1 | 补保存状态机最小复现和服务夹具设计 | 独立测试文件 | 能确定性覆盖等待队列、重试、冲突和切换 |
| D1 | 建立当前 README／文档入口、源码目录索引草稿 | 文档；不与总协调者抢写 session_context | 当前结构和历史资料明确区分 |

F1 不改保存队列语义；B1 不同时搬 service 或目录。已有 api 帮助函数逐一接入，不留两套分叉的请求实现。

门禁：前端构建、相关 API 与路径测试通过；外部接口和数据布局零变化。

## 4. P2：核心职责拆分与保存可靠性

| 包 | 内容 | 所有权约束 | 验收 |
| --- | --- | --- | --- |
| F2 | navigation、workspace、App 壳层提取；类型化工作区上下文 | App.vue 及新 app 模块统一归一人 | 两区、深链、撤销、对象定位和旧入口不退化 |
| F3 | 保存协调器修复与提交结果协议 | saveCoordinator 归一人；与 F2 先固定接口 | retry 实际发送；后继 revision 正确；409 不自动覆盖；错误不假成功 |
| B2 | projects 校验提取为各职责函数 | projects.py、project_validation.py及必要公共辅助由一人负责 | 同输入得到相同有效输出、错误等级和结构化位置 |
| T2 | 兼容样例与差异比较测试 | 测试文件分配给独立负责人 | 旧／新来源、形态、共享、发布和修订兼容 |

F2/F3 只有在 API 稳定后并行。需要变更互相文件时交给所有者处理，不能相互同时补丁。B2 先机械提取，单独记录由测试证实的规则修复。

门禁：小表单保存→刷新→重启、双页面冲突、取消和未提交草稿隔离、连续保存及撤销通过；校验兼容回归通过。只通过 Python 保存测试不代表前端队列已验证。

## 5. P3：业务模块与 HTTP 边界

| 包 | 内容 | 验收 |
| --- | --- | --- |
| F4 | 前端本体页及辅助模型按业务归属，表单改用已固定提交接口 | 页面中不再重复实现请求和保存状态机 |
| F5 | 前端项目页归属；PropertySources 拆出确有必要的来源／定位／结果子视图或纯辅助 | 三步共享一个局部草稿，取消和最终提交语义不变 |
| B3 | 由 server 提取本体／项目路由处理，保留安全入口和原 URL | HTTP 契约回归、锁边界、异常序列化、导出与恢复一致 |
| Q3 | 独立审查依赖方向、循环导入、类型与结构化校验位置 | 无页面→存储等越层依赖，无循环依赖掩盖 |

移动组件前由协调者划清 shared 与业务模块归属；跨模块组件不得在两边各复制一份。组件文件归属与导入路径更新作为一个可构建批次集成。

门禁：完整前端构建；两区主链路、辅助入口和关键旧 hash 的浏览器检查；后端接口和版本回归。

## 6. P4：开发工具与目录收敛

允许并行处理互不重叠部分：

- F6：复核并移除无引用组件／vue-router，更新锁文件，不进行无关依赖升级。
- B4：演示实现迁到 workbench/demo，保留旧命令转发；更新必要资源定位。
- DX：启动／构建工具改为依赖显式准备、热更新开发、构建成功再切换服务、只管理自身进程。
- DOC：整理文档索引和旧资料清单，准备输出文件路径迁移表。

目录搬移作为本阶段最后一个**集中串行步骤**：按方案迁移 tools、resources、文档交付物、运行产物，逐文件校验摘要并更新引用。ontology 始终不动。不能边让多个任务开发旧路径边搬整个目录。

如果当前协作工具仍在读取旧 outputs/ 指令，先完成交接并留最小索引，再迁移其文件；不能迁移后让正在执行的任务失去指令或形成两个版本。

门禁：普通构建不再无条件 npm install；开发热更新可用；旧命令／文档／原型可定位；迁移摘要一致；没有删除用户备份。

## 7. P5：最终回归与交付

1. 同环境复测 P0 的构建／测试耗时，区分已改善、无明显变化和未测项目，不虚报加速比例。
2. 完成保存错误／冲突／撤销／重启、公共采样表、Redis、函数输出形态、共享继承、版本升级、导出恢复和旧辅助入口验收。
3. 对照当前正式界面与已接受原型，确认本轮未自行重新设计页面；旧原型二次保存按钮仍不是目标。
4. 审计数据边界与引用，确认真实 ontology 未被任务写入；目录与文档链接完整，临时测试进程不残留。
5. 输出最终目录说明、模块职责、日常修改定位表、耗时对比和未完成项，更新 AGENTS.md、README、session_context。

最终交付：`文档/架构优化实施说明_20260915.md`。若阶段目录迁移改变其他报告路径，在本文和上下文记录实际位置。

## 8. 回退方式与阶段停止条件

- 每阶段记录代码文件摘要和快照；回退只恢复本阶段负责且确认无人再改的代码，不能覆盖另一开发工具的新修改。
- 文件迁移按清单逆向恢复；禁止恢复／清理整个用户数据目录。
- 新模块可以先通过旧公开函数／命令转发接入；门禁通过后再清理无调用的兼容包装。
- 保存有丢内容、串资源、冲突覆盖、未知字段丢失风险时停止依赖集成，先修复；独立文档与只读审查仍可继续。
- 不因某个包困难就取消错误检查、写入锁、版本预检或全部测试。

## 9. 日常需求在优化后的处理方式

| 需求 | 优先修改位置 | 默认工作方式 |
| --- | --- | --- |
| 改名称／提示／样式 | 对应业务组件／shared 样式 | 单任务＋页面验证 |
| 改一个属性编辑字段 | 本体属性组件；确需存储时同步协议 | 单任务为主，必要时前后端两包 |
| 改属性来源规则 | project 纯辅助＋后端对应校验函数 | 两包共享用例，针对性回归 |
| 改保存行为 | app 保存／workspace | 保存负责人＋独立测试，其他页面不各自补丁 |
| 新接口 | 对应 api 与后端路由／业务模块 | 明确契约后前后端并行 |
| 改目录或版本协议 | 先影响分析再迁移 | 分阶段，不和普通表单修改混做 |

用户的 50 并发能力作为资源上限，不能把每次小需求都复制成整体改造的十二包流程。
